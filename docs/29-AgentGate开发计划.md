# 29 · AgentGate 开发计划（执行版 v4）

> **定位**：被服务的真实研发项目 + DevMate 的评测/观测模块。**不是评测平台。**
> **v4 改动**：删掉能力清单，改用「场景 × 技术点 × 验收 × Phase」范围矩阵。
> 日期：2026-11-20

---

## 0. Harness 与自检

### 0.1 算不算自研 Harness

**算，限定为“任务级”。**

| 能力 | 现在 | 完成后 |
|---|---|---|
| run_id / 生命周期 | ✅ | ✅ |
| 工具注入 | ✅ | ✅ |
| 异常隔离 | ✅ | ✅ |
| trace | 节点级 | span 树 |
| 超时 / 重试 | ❌ | 每工具独立 |
| 状态机（外层） | ❌ | created/running/succeeded/failed |
| 限额 | ❌ | 步数 / Token |
| 容器隔离 / 并发 / 多租户 | ❌ | 不做 |

### 0.2 自检：旧能力清单错在哪

| 问题 | 说明 |
|---|---|
| 层级混 | “运行底座”和“轨迹评测”不是同一层：前者是基础设施，后者是评分器 |
| A0 / A6 重叠 | trace 和 usage 被写了两遍 |
| 轨迹评测不在 Harness 内 | Harness 产 trace，轨迹评测消费 trace |

**结论**：能力清单不是必须的；用下面这张矩阵表达范围。

## 1. 范围矩阵（场景 × 技术点）

> 格子 = 验收标准（Phase）。**空格 = 不在范围。**

| 场景 | 评测数据 | 任务评测 | 轨迹评测 | BadCase 归因 | 回归对比 | 运行与观测 | judge |
|---|---|---|---|---|---|---|---|
| **S1 故障排查** | 13 条带证据锚点（P1） | 根因 ≥80%、证据 ≥90%（P1） | 步级/工具/恢复（P1） | 5 类 + 修复（P1） | 逐 case diff（P1） | span ≥3 层、超时重试、限额（P0–P1） | 一致率 ≥80%（P1） |
| **S2 转测范围** | 9 条（P2） | 模块召回 ≥85%、误报 ≤15%（P2） | — | 3 类（P2） | 分场景 diff（P2） | 复用（P0） | 一致率（P2） |
| **S3 需求澄清** | 8 条（P2） | gap 召回 ≥80%（P2） | — | 3 类（P2） | 分场景 diff（P2） | 复用（P0） | 一致率（P2） |
| **S4 新人上手** | 8 条（P3） | SOP 完整 ≥85%（P3） | — | — | 分场景 diff（P3） | 复用（P0） | 人工 4/5（P3） |

**读法**：

- 7 列 = 评测模块的 7 个技术点；
- 4 行 = 支持的 4 个场景；
- 空单元格 = 明确不做（比如 S2–S4 不做轨迹评测）；
- 每格都有验收和 Phase，没有“以后再说”。

## 2. 深度门槛

| 技术点 | 浅做法（禁止） | 深做法（必须） | 证明 |
|---|---|---|---|
| 运行与观测 | print / 单层日志 | span 树、trace_id 贯穿、错误分类、可回放 | ≥3 层 span；100% 日志带 trace_id；按 trace 还原 run |
| 评测数据 | 随手写几条 | 分层、带证据锚点、dev/held-out 拆分 | 每场景 8–13 条，锚点可定位 |
| 任务评测 | 通过/失败计数 | 根因命中、证据链、逐条锚点 | 两类指标有数 |
| 轨迹评测 | 只看最终结果 | 步级成功、工具选择、恢复率 | 能指出哪步错、选错哪个工具 |
| BadCase | 列失败清单 | 5 类归因 + 修复建议 | 每条有类别、有修复 |
| 回归对比 | 只比总分 | 逐 case diff | 能指出哪几条变好/变坏 |
| judge | 直接信 | 人工一致性校准 | 20 条 ≥80% |

## 3. 反砍规则（发现即回滚）

| 禁止 | 必须 |
|---|---|
| 固定流程冒充轨迹 | 记录每步决策与理由 |
| fixture 冒充真实数据流 | 从 store / 产物读 |
| print 冒充日志 | 结构化、带 trace_id |
| 总分冒充评测 | 分场景、分轨迹 |
| 跳过边界测试 | 超时/空结果/超长/重复有用例 |
| 主链路留 TODO | 主链路不允许 TODO |

**任何简化写 §7，标注“降低了哪条深度”，等确认；没记录就回滚。**

## 4. 评测侧指标（与 DevMate 对齐）

### 4.1 评测系统本身要可信

| 指标 | 定义 | 目标 |
|---|---|---|
| 场景覆盖 | 已支持场景 / 计划 4 个 | 4/4 |
| 能力覆盖 | 矩阵非空格已验收 / 非空格总数 | 100% |
| 负例占比 | 负例 / 总用例 | 15–25% |
| judge 一致率 | 人机一致 / 抽检 | ≥80% |
| 评测可复现率 | 同 case 同配置两次结果一致 | ≥95% |
| 区分度 | 已知好版本 vs 坏版本的指标差 | ≥10pp |
| 证据锚点覆盖 | 有锚点结论 / 总结论 | 100% |
| 单 case 评测成本 | tokens + latency | 记录 |

### 4.2 与 DevMate 指标对齐

| DevMate 指标（见 `30` §4） | AgentGate 提供 | 评测侧前提 |
|---|---|---|
| 质量加权成功率 | 任务成功率 × 证据完整率 | judge 校准、指标可复现 |
| 步长 / 鲁棒性 | 轨迹指标（步级/工具/恢复） | span 完整、步级可判 |
| Token 效率 | usage 聚合 | usage 采集完整 |
| 数据闭环 | badcase / 回归 | 用例可追溯、回归 100% |

### 4.3 闭环指标

| 指标 | 目标 |
|---|---|
| badcase 闭环率 | ≥80% |
| 回归覆盖 | 100% |
| 复发率 | ≤5% |
| 用例增长 | 记录 |

> 评测指标不是越高越好，是**可信 + 能区分 + 能闭环**。

## 6. 各 Phase 详情

- [ ] 100% 日志带 trace_id；
- [ ] 报告有单次与单步 token/latency；
- [ ] 错误分类：timeout / validation / upstream / internal；
- [ ] 能用 trace 还原一次 run；
- [ ] 单 case 失败不中断批量；
- [ ] 注入一个假工具，能被调用并写 trace；
- [ ] 新增测试 ≥10。

## 9. 可选轨道：Sandbox Runner（不阻塞）

> **不一定做**；不影响 P1–P3。触发条件：目标岗明确看重“沙箱跑 coding agent（Claude Code / DSH）”的实战。

### 9.1 目标

在容器里跑 Claude Code 或 DeepSeek Harness（DSH），完成一个编码任务，留痕并评测。

### 9.2 最小方案

| 项 | 做法 |
|---|---|
| 环境 | Docker + python:3.12-slim + git + node；非 root |
| 隔离 | `--network none`；CPU/内存限额；超时 5 分钟；只挂载 repo 目录 |
| 任务 | 修一个失败单测 / 小改动 |
| 留痕 | 命令日志、`git diff`、退出码、耗时 |
| 评测 | 测试通过、未改禁止文件、未尝试联网 |

### 9.3 DoD

- [ ] 容器跑通，断网验证；
- [ ] Claude Code 或 DSH 完成 1 个任务；
- [ ] diff + 测试结果落 trace；
- [ ] 生成评测报告；
- [ ] 超时能杀掉容器。

### 9.4 不做

- 不做多语言、并行、生产级隔离；
- 不接真实仓库；
- 不与四个业务场景合并——它是独立轨道。
