## 0. 文档导读

### 0.1 这份文档的目的

用一条**假设依赖链**重审整套方案，回答一个问题：**这套方案成立吗？**

不是问"做了多少功能"，也不是问"代码写没写"。是逐层检验：

- 问题是不是真问题；
- 边界划得对不对；
- 抽象跨不跨得过去；
- 机制解决的是不是它声称要解决的问题；
- 评测结果能不能支撑决策；
- 这门生意在成本上成不成立。

### 0.2 读者与使用方式

| 读者 | 怎么用 |
|---|---|
| 产品经理 | 按步骤逐条审，每步填四栏 |
| 面试准备 | 审查结论直接变成防守题的答案 |
| 后续迭代 | 不成立的环节进 backlog，不以"部分完成"含糊过去 |

### 0.3 本文包含什么

```
§1 审查方法（顺序、规则、产出格式）
§2 第一步：问题与场景
§3 第二步：边界与准入
§4 第三步：抽象——行为分类（承重墙）
§5 第四步：核心机制
§6 第五步：评测体系
§7 第六步：门禁与验收
§8 第七步：价值与规模化
§9 审查进度与变更记录
```

### 0.4 核心结论

> **待七步完成后回填。**
> 当前仅有一条预判：第三步（行为分类）是全案承重墙，最可能暴露真问题。

### 0.5 本文不解决什么

- 不重写方案，只做审查与判断；
- 不评价代码质量与工程实现；
- 不做竞品对比（见 `02`）；
- 不产出简历措辞（审查完再谈）。

## 1. 审查方法

### 1.1 为什么按假设依赖链，不按文档章节

文档章节是按写作顺序排的；审查要按**依赖关系**排。

> 每一步的结论是下一步的前提。前面塌了，后面不用看。
> 如果问题定义不成立，架构再漂亮也没意义。

### 1.2 七步顺序

| # | 审什么 | 只回答一个问题 | 依据 | 这步不成立会怎样 |
|---|---|---|---|---|
| **1** | 问题与场景 | 谁在什么场景下卡住？现有方案为什么不够？ | `01`、`17` | 后面全部作废 |
| **2** | 边界与准入 | 平台该做什么、不该做什么？哪些 Agent 才需要它？ | `01` §4–5、`05-1` | 产品变成"什么都做" |
| **3** | 抽象：行为分类 | B1–B6 能不能跨业务统一？意图 / 行为分层成立吗？ | `06`、`05-2` §1.2 | 跨范式复用不成立，平台退化为单场景工具 |
| **4** | 核心机制 | 接入、编排、围栏、人机协同、trace 各解决什么、代价是什么 | `05-2`、`06` | 方案退化成功能堆叠 |
| **5** | 评测体系 | 用例能不能代表？指标能不能判？evaluator 可信吗？ | `08`、`20`–`23` | 分数不可信，门禁没有依据 |
| **6** | 门禁与验收 | 谁定阈值、谁签字、不通过怎么办？ | `24`、`18` | 平台只能"测"，不能"决策" |
| **7** | 价值与规模化 | 成本、接入、运营闭环成立吗？ | `19`、`25`、`23` | 只能是 POC，不能是产品 |

### 1.3 为什么是这个顺序

- **1 → 2**：问题是需求，边界是取舍。没有边界的平台一定会膨胀。
- **3 是全案承重墙**：B1–B6 如果只在研发协作里成立，"跨范式"就是话术；它成立，后面才有复用可言。
- **4 在 5 之前**：评测消费的是机制产出的 trace，机制不成立，指标就是空中楼阁。
- **6 在 5 之后**：先确认"能不能判"，再谈"判完怎么决策"。
- **7 最后**：成本和接入只有在方案成立后才值得算。

### 1.4 三条贯穿规则

| # | 规则 | 说明 |
|---|---|---|
| 1 | 每步只回答一个问题 | 不提前跳进实现细节 |
| 2 | 结论只允许三种状态 | **成立 / 有条件成立 / 不成立**，不写"部分完成" |
| 3 | 区分"设计了"和"实现了" | 设计成立但没实现，不算方案错误，只标证据等级 |

### 1.5 每步的产出格式

```
结论：一句话，三态之一
证据：文档 / 代码 / 数据
代价：这个设计牺牲了什么
待定：需要业务方或数据才能回答的
```

### 1.6 一条预判

第三步大概率会暴露一个真问题：

> **B1–B6 是按"动作语义"分的，不是按"业务语义"分的。**
> 这带来跨业务的可能，但也带来跨任务形态的困难——多步任务、长链路任务，现有六类描述不了。
> 到时候要决定：是扩类，还是承认边界。

**四个读法**：

1. **指标都分三层**：结果（解决率、% Resolved、诊断正确率）、过程（转人工率、AHT、引用覆盖率）、风险（重大风险条款召回率、越权拒绝率）。与 `18` 的三层分法能对上。
2. **评测方案骨架高度一致**：各业务 Agent 评测底层流程框架趋同：构造测试用例（常规场景、边界场景、越权、无答案场景）→ 选择评估方式（规则判定、LLM 自动评判、专家人工核验或组合）→ 设定对比基线 → 按风险等级差异化设准入门槛 → 版本迭代做回归复测。主要差异体现在：测试用例来源、风险指标权重、是否需要业务效果联动核验、是否增加环境隔离 / 可复现约束。
3. **官方覆盖度差异大**：客服、RAG、研发、医疗、营销有国标/行标/官方 benchmark；合同、数字员工、招聘、政务指标只有厂商文档或官媒；外呼指标与电商商家只有行业实践。
4. **对结论的修正**：问题不是"行业没有评测"，而是"评测方案绑行业、绑平台，自研栈拿不到、跨业务不可迁移"。这会把第一步结论从"问题成立"收窄为"**问题成立，但必须限定在自研 Agent 团队**"。

> **一处待核**：智能客服行的 70% / 85% 等数值来自 GB/T 47746—2026 的公开解读，不是标准原文；引用前需核对条款。

**未证的部分**：

| 缺口 | 现状 | 影响 |
|---|---|---|
| 痛点是否真实发生 | `17` §5 的 E4/E5/E7 为 **C 级推断** | 只能论证"可能存在"，不能论证"确实严重" |

### 2.3 代价

| 代价 | 说明 |
|---|---|
| **问题规模与产品规模不匹配** | "标准割裂、口径不一"是**组织级**痛点（多团队、多 Agent）；而本产品是单机 POC。两个 Agent 能证明机制成立，证明不了痛点规模 |
| **承诺范围 > 交付范围** | `01` §2 列了 8 类瓶颈，产品只覆盖 P1–P4 的一部分；G 成本、H 组织被映射进去但没实现。§3.2 有注释缓解，但读者容易跳过 |
| **用构造替代观察** | `17` §2.3.1 的时间线是构造示例，不是真实事故；说服力弱于一手案例 |

### 2.4 待定

1. **目标用户到底是谁**：是"自建 Agent 的团队"，还是"买 Agent 的业务方"？只有前者需要评测底座。
2. **一次越权 / 一次回归失败的实际损失**是多少钱、多少人天？
3. 同时满足"**自建 + 有写入工具 + 要上线**"三个条件的团队，规模有多大？

### 2.5 什么会改变结论

| 若发现 | 结论变为 |
|---|---|
| 3–5 个访谈确认痛点发生过，且能给出损失量级 | 成立 |
| 业务方基本不自己评测（都买现成 Agent） | 不成立 |
| 多数 Agent 是只读/不上生产 | 不成立（退化为例外场景） |
| 痛点只在 10+ Agent 的组织出现 | 有条件成立，但产品定位要改成"企业级"，与单机 POC 冲突 |

### 2.6 建议动作

1. 在 `01` 开头加一句适用范围：**适用于自建 Agent、有写入类工具、需要上线的团队**；
2. 访谈时优先问损失量级（补 E7），而不是"你需要评测平台吗"；
3. 把"组织级痛点 vs 单机产品"的张力写进 `14-简化点`，面试时主动说。
