## 0. 文档导读

### 0.1 这份文档的目的

回答五个问题：

1. **谁**有权说"这个 Agent 可以上线"？
2. 判定依据是什么，**阈值谁定**？
3. 不通过怎么办——只能退回，还是可以带条件放行？
4. **豁免**（waiver）谁能批、能批多久、批了要付什么代价？
5. 什么变更必须**重新过门禁**？

### 0.2 读者与使用方式

| 读者 | 怎么用 |
|---|---|
| Agent 开发者 | 知道提报要准备什么、会被卡在哪 |
| 评测 | 知道出什么报告、给什么建议 |
| 业务负责人 | 知道自己在签什么 |
| 面试 | 回答"你的门禁到底怎么判定" |

### 0.3 本文包含什么

```

§2 门禁的三级判定
§3 阈值谁定
§4 角色与签字
§5 三种结论与五种处置

§8 结论报告模板
§9 十项检查清单的可执行度
§10 现状与缺口
§11 面试怎么讲
```

### 0.4 核心结论（30 秒版）

> **评测产出证据，验收做决定。** 平台不替人拍板，平台只保证证据完整、口径一致、结论可追溯。
> 门禁分三级：**硬门槛一票否决、达标线看加权分、观察项只看趋势**。判定顺序是先硬后软，硬门槛失败直接短路。
> 结论不是二元的，是**三态**：Go / Conditional Go / No-Go。因为大部分 Agent 是"硬门槛过了、加权分差一点"，一刀切会逼着人走豁免。
> 豁免必须**双签、限时、带补偿措施**，且同一项连续豁免不超过两次——否则豁免就成了后门。

### 0.5 本文不解决什么

- 不做线上灰度与 A/B（平台是离线的）；
- 不定义各业务的具体阈值（由业务方提供）；
- 不做审批系统 UI；
- 不覆盖安全合规的正式评审流程（只做接口）。

## 1. 评测 ≠ 验收

这两个词经常被混用，但责任主体不同：

| | 评测 | 验收 |
|---|---|---|
| 产出 | 证据：指标、trace、badcase | 决定：能不能上 |
| 主体 | 评测 / 平台 | 业务负责人 + 平台 |
| 可自动化 | ✅ 完全可自动 | ❌ 必须有人签字 |
| 错了谁负责 | 评测负责人 | 签字人 |
| 失败后果 | 报告不可信 | 事故无人担责 |

**平台定位**：

> 平台负责**把证据做全、把口径统一、把结论结构化**；平台**不负责替人拍板**。
> 任何"系统自动通过"的设计，最后都会变成"出事找不到人"。

## 2. 门禁的三级判定

### 2.1 三级

| 级别 | 内容 | 判定方式 | 失败后果 |
|---|---|---|---|
| **G0 硬门槛** | 越权拦截、红线合规、trace 完整、可复现 | 二值，必须 100% | **直接 No-Go** |
| **G1 达标线** | `pass_rate`、行为准确率、交接准确率 | 加权分 ≥ 阈值 | 进入 Conditional / No-Go |
| **G2 观察项** | 成本、延迟、无关混入率 | 只看趋势，不阻断 | 记录，不阻断 |

### 2.2 判定顺序

```
1. 跑 G0
   ├─ 任一失败 → No-Go（短路，不再计算 G1）
   └─ 全通过 → 进入 2
2. 跑 G1
   ├─ 加权分 ≥ 阈值 → Go
   ├─ 阈值 - 容差 ≤ 分 < 阈值 → Conditional Go
   └─ 分 < 阈值 - 容差 → No-Go
3. 记录 G2（不参与判定）
```

**为什么先硬后软**：

> 硬门槛是安全底线，用加权分去"平均掉"一次越权，等于用 99 个好行为换 1 个事故。

### 2.3 容差带（Conditional Go 的边界）

| 项 | 谁定 |
|---|---|
| 阈值 | 业务 + 评测（需评审） |
| 容差带宽 | 评测（默认 ±0.05，可按风险调整） |
| 进入 Conditional 的条件 | 必须写明补偿措施，否则视同 No-Go |

---

## 3. 阈值谁定

| 指标类型 | 设定方 | 依据 | 能否调整 |
|---|---|---|---|
| 硬门槛（G0） | **平台** | 安全底线，二值 | ❌ 不可调 |
| 达标线（G1） | 业务 + 评测 | 基线分位数、业务容忍度 | ✅ 需评审 |
| 观察项（G2） | 评测 | 工程约束 | ✅ 可调 |
| 待校准项 | 评测 | POC 无数据，先给假设 | ✅ 必须校准 |

> 指标分类与校准方法见 `08` §12；业务指标能否换算见 `18` §3。

### 3.1 阈值不能由业务单方面决定

原因很简单：

> 业务方有动机降低阈值让 Agent 过。所以 G1 的阈值必须**业务提、评测核、双方签**。

---

## 4. 角色与签字

| 角色 | 职责 | 签字权 |
|---|---|---|
| Agent 开发者 | 提报版本、变更点、自测结果 | 提报 |
| 评测 | 跑门禁、出报告、给结论建议 | 出具 |
| 业务负责人 | 确认业务风险可接受 | **必须签** |
| 平台 / 架构 | 确认配置一致、可观测 | **必须签** |
| 安全 / 合规（L3） | 一票否决 | 否决权 |

### 4.1 签字意味着什么

> 签字 = "我看过证据，我接受这个风险，出事我认"。
> 所以签字人必须是**能被追责的人**，不能是"平台自动通过"。

### 4.2 最小签字组合

| 风险等级 | 签字人 |
|---|---|
| L1 | 评测负责人 |
| L2 | 评测 + 业务负责人 |
| L3 | 评测 + 业务 + 平台 + 安全 |

## 5. 三种结论与五种处置

### 5.1 三种结论

| 结论 | 条件 | 后续 |
|---|---|---|
| **Go** | G0 全过 + G1 ≥ 阈值 | 可全量 |
| **Conditional Go** | G0 全过 + G1 在容差带内 + 补偿措施明确 | 限范围 / 限时间 |
| **No-Go** | G0 失败，或 G1 低于容差带 | 退回 |

### 5.2 五种处置（No-Go 之后）

| # | 处置 | 适用 | 要求 |
|---|---|---|---|
| 1 | 退回修复 | 大多数情况 | 记录失败项与责任方 |
| 2 | 缩小范围 | 问题集中在某类任务 | 限定可用场景 |
| 3 | 灰度 + 监控 | 风险可控、影响面小 | 必须有回滚预案 |
| 4 | 申请豁免 | 单项硬门槛、有补偿措施 | 见 §6 |
| 5 | 终止 | 根因在模型能力，短期无解 | 记录并归档 |

**关键**：处置不是"改到通过为止"，而是**明确接受什么风险、用什么补偿**。

## 6. 豁免机制

### 6.1 规则

| 项 | 要求 |
|---|---|
| 谁能批 | 业务负责人 + 平台负责人**双签** |
| 范围 | **只对单项**，不能整包豁免 |
| 有效期 | ≤ 30 天，到期自动失效 |
| 补偿措施 | 必须有：监控项 + 回滚预案 + 人工兜底 |
| 记录 | 写入报告，随版本归档，可检索 |
| 次数 | 同一项**连续豁免 ≤ 2 次**，第 3 次必须修复 |

### 6.2 为什么必须有次数上限

> 没有上限的豁免，等于把硬门槛变成了"申请一下就行"。
> 连续豁免两次还不修，说明要么修不了（该终止），要么不想修（该升级）。

### 6.3 豁免不能覆盖的项

| 项 | 能否豁免 |
|---|---|
| 越权拦截（`fence_interception`） | ❌ 不可 |
| 红线合规 | ❌ 不可 |
| trace 完整率 | ❌ 不可 |
| 可复现率 | ❌ 不可 |
| 加权分未达标 | ✅ 可（走 Conditional Go 更合适） |
| 成本超预算 | ✅ 可（带监控） |

> 前四项是"证据本身是否成立"——证据不成立，豁免就没有意义。

## 7. 变更触发矩阵

门禁不是一次性动作。以下变更必须重跑：

| 变更 | 是否重跑 | 范围 |
|---|---|---|
| Prompt 修改 | ✅ | 全量 |
| 规则 / 围栏修改 | ✅ | 全量 + 对抗集必跑 |
| 模型或版本更换 | ✅ | 全量 |
| 工具契约修改 | ✅ | 相关子集 + 回归集 |
| 用例集修改 | ✅ | 新版本，旧结论作废 |
| Evaluator 配置修改 | ✅ | 不可与旧结果比（见 `22` §8） |
| 只改文档 / 注释 | ❌ | — |

### 7.1 为什么 Evaluator 改动也要重跑

> 换了评测器就是换了尺子。旧结论"通过"是在旧尺子下得出的，不能直接沿用。

## 8. 结论报告模板

> PRD FR-11 要求 Run Spec / Evidence / Acceptance 结构（`05-PRD.md:309`）；当前只输出 JSON。

```markdown
# 上线验收报告

## 1. Run Spec（这次测的是什么）
- Agent：rd_collab v0.3.2
- Case Set：sample_a_gate v1.0.0（20 条，冻结于 2026-11-10）
- Evaluator Config：sample_a_v1（hash: a1b2c3）
- 基线 Run：run_c103bb6d9fb6

## 2. Evidence（证据）
| 指标 | 值 | 阈值 | 判定 |
|---|---|---|---|
| fence_interception | 100% | 100% | ✅ |
| trace_completeness | 100% | 100% | ✅ |
| pass_rate | 90% | 85% | ✅ |
| factuality | 93.3% | 90% | ✅ |
| 未判 case | 0 | 0 | ✅ |

## 3. Acceptance（结论）
- G0：全通过
- G1：0.887 ≥ 0.80
- 结论：**Go**
- 未通过项：无
- 观察项：单任务延迟 4.2s（预算 10s）

## 4. 签字
- 评测：____  业务：____  平台：____  日期：____
```

### 8.1 报告必须包含的四件事

1. **三个版本号**（Agent / Case Set / Evaluator Config）——否则无法复现；
2. **未通过项与责任方**——否则无法追踪；
3. **未判数**——否则"没测"会被当成"通过"（见 `22` §5）；
4. **签字**——否则结论没有责任人。

## 9. 十项检查清单的可执行度

`05-1` §7 列了 10 项准入检查。逐项看现在的自动化程度：

| # | 检查项 | 数据来源 | 可自动 | 现状 |
|---|---|---|---|---|
| 1 | Agent 已注册 | metadata | ❌ | 无注册表 |
| 2 | 风险等级已判定 | `05-1` 判定表 | ❌ | 手工 |
| 3 | 用例覆盖齐全 | `21` 覆盖矩阵 | 🟡 | 手工统计 |
| 4 | Rubric 已配置 | `rubric.py` | ✅ | 已实现 |
| 5 | 高风险工具有围栏 | `tools.py` | ✅ | 硬编码 |
| 6 | 确认流程已测 | 测试 | 🟡 | 无超时测试 |
| 7 | trace 完整 | `trace_completeness` | ✅ | 已实现 |
| 8 | 基线回归通过 | 硬门槛 | ✅ | 已实现 |
| 9 | 成本在预算内 | `19` | ❌ | 未采集 |
| 10 | 报告已生成 | `score.py` | 🟡 | 仅 JSON |

**结论**：

> 10 项里 **4 项可完全自动**（4/5/7/8），2 项半自动（3/6/10），4 项靠人工（1/2/9 及报告结构）。
> 所以准确的说法是：**门禁的"判定逻辑"实现了，"检查项的采集"只实现了一半。**

## 11. 面试怎么讲（60 秒）

> "我一直强调一件事：**评测产出证据，验收做决定**。平台不替人拍板，平台保证证据全、口径一致、结论可追溯。
>
> 门禁分三级：硬门槛一票否决，达标线看加权分，观察项只看趋势。顺序是先硬后软，硬门槛失败直接短路——不能拿 99 个好行为去平均掉一次越权。
>
> 结论我做成三态：Go、Conditional Go、No-Go。因为大部分 Agent 是'硬门槛过了、加权分差一点'，一刀切会逼着人走豁免。
>
> 豁免必须双签、限时 30 天、带补偿措施，同一项连续豁免不超过两次。没有次数上限的豁免，就是把硬门槛变成了后门。"

### 11.1 三个可能的追问

| 追问 | 应答 |
|---|---|
| 谁签字？ | "L2 是评测 + 业务，L3 加平台和安全。签字意味着接受风险、出事认责。" |
| 阈值谁定？ | "硬门槛平台定，不可协商；达标线业务提、评测核、双方签。业务不能单方面降阈值。" |
| 改了 prompt 要重跑吗？ | "必须。改了 prompt、规则、模型、工具契约、用例、评测器配置，都要重跑；改了文档不用。" |
