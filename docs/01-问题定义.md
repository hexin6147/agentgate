## 0. 文档导读

### 0.1 这份文档的目的

本文是 `00-立项书.md` §1「问题假设」的展开，回答一个问题：**AgentGate 到底要解决什么业务问题，凭什么值得做？**

具体要产出四个结论：

1. 业务 Agent 从 Demo 走到生产，瓶颈到底在哪；
2. 这些瓶颈里，哪些是平台能解的、哪些必须由业务方自己解；
3. 平台由此收敛出的四个核心缺口是什么；
4. 用什么指标判断"问题被解决了"，以及这些指标凭什么这么定。

### 0.4 核心结论（30 秒版）

> 业务 Agent 投产的瓶颈，集中在**管控、观测、回归、复用**四件事上，而不是"模型不够强"。
> 成品 SaaS 只开放业务配置层，执行链路封闭；大厂平台面向企业采购；自建脚本重复造轮子。
> AgentGate 的价值不是提供万能测试用例，而是提供一套**统一的评测基础设施**：沙箱、流水线、trace、badcase 归集、评审流程、通用安全插件。**用例内容和判定标准由每个业务方自己提供。**
> 平台能否成立，取决于两件事：接入是否足够轻、回归是否足够可复现。

### 0.5 本文不解决什么

- 不证明"平台能提升模型能力"——模型能力不在平台范围内；
- 不提供业务领域知识与 SOP 内容——由业务方提供；
- 不验证线上真实流量——只有离线仿真；
- 不承诺指标目标值是最终结论——G4/G6 会用基线数据校准。

## 1. 一页摘要

### 1.1 问题陈述

> 业务 Agent 从 Demo 走到生产，瓶颈不在"能不能生成"，而在**能不能被管住、被看见、被回归、被复用**。
>
> 团队缺少一套轻量的评测基础设施：能接入不同业务的 Agent、隔离执行、记录完整轨迹、承载业务方自己的用例与判定标准、支持版本回归。结果是上线靠人工试用，迭代靠事故发现。

### 1.2 目标用户

| 用户 | 核心诉求 |
|---|---|
| Agent 开发者 / 业务团队 | 快速验证自己的 Agent 能否上线，问题出在哪 |
| 评测 / 效能 / AI 平台团队 | 统一运行、观测、回归、评审的基础设施 |
| 管理层 / 合规 | 看到可解释的风险拦截与评测报告 |

### 1.3 现状方案与不足

| 方案 | 角色 | 不足 |
|---|---|---|
| 人工试用 + 聊天记录 | 现状 | 不可复现、不可比、无中间状态、无法回归 |
| 各团队自建脚本 | 替代方案 | 重复造轮子、口径不一、没有统一门禁 |
| 大厂平台（火山 / 美团 / 腾讯 / 阿里 / 华为） | 直接竞品 | 能力强，但面向企业采购，重、定制成本高 |
| 评测 / 观测工具（LangSmith / LangFuse） | 直接竞品 | trace 与离线评测成熟，但不做执行前拦截，无门禁判定 |
| 成品 SaaS（Claude Tag / 豆包工作伙伴） | **需求侧证据** | 业务配置可调，但执行链路封闭——说明需求存在，**不构成替代方案** |

> **类别提醒**：成品 SaaS 是 Agent 产品，不是管控/评测平台。把它当竞品是类别错误；它的作用是证明"业务 Agent 已在规模化部署，外部管控层有需求"。

### 1.4 我们的解法

> 统一评测基础设施 + 业务方自有内容：
> **平台提供** Adapter 接入、沙箱、流水线、trace、badcase 归集、评审流程、通用安全插件；
> **业务方提供** 自己的用例、golden、Rubric 权重、业务 SOP 与红线。

### 1.5 成功标准（摘要）

- 技术接入 ≤ 30 分钟（Adapter 跑通第一个 case）；业务就绪 ≤ 5 人日（用例 + Rubric + 围栏 + 门禁）；拆分依据见 `25-Agent接入SOP.md` §5；
- trace 完整率 100%；
- 回归自动化率 100%；
- 同一 Mock 环境下运行可复现率 100%；
- 业务方能在平台上管理自己的用例与 Rubric，不需要改平台代码。

### 1.6 边界

只做离线仿真与 Mock 工具；不做多租户、线上流量、真实变更、真实系统集成；不提供万能用例库。

## 2. 业务 Agent 投产的 8 类瓶颈

> 这一节回答你的问题：**为什么一个业务 Agent 要在意"管控、观测、回归、复用"？**
> 因为它们不是抽象的架构概念，而是 Agent 从 Demo 到生产时真实会卡住的地方。

### 2.1 从 Demo 到生产的鸿沟

Demo 阶段的成功标准是"能跑通一次"；生产阶段的标准是：

- 同一输入能否稳定给出可接受的结果；
- 出错时能否发现、定位、拦截；
- 改了一处之后，其他场景会不会坏；
- 出了问题谁负责、怎么追溯。

这四条对应四类工程能力，而不是模型能力。

### 2.2 八类瓶颈

#### A. 能力与确定性

| 项 | 说明 |
|---|---|
| 表现 | 同一输入多次运行结果不同；长链路误差累积；编造事实、来源或工具返回 |
| 典型场景 | 汇总里出现群聊没有的风险；故障根因定错；多步任务中途跑偏 |
| 业务后果 | 不敢把关键任务交给 Agent；输出需要人工逐条核对 |
| 平台能做什么 | 用 trace 暴露不确定性；用回归量化漂移；用 golden 约束行为 |
| 平台不能做什么 | 提升模型本身的推理能力 |

#### B. 业务约束与合规

| 项 | 说明 |
|---|---|
| 表现 | 业务 SOP 难被稳定遵守；高风险动作被自主执行；权限边界不清；操作无法追溯 |
| 典型场景 | 故障未定级就发起变更评审；越权读取其他项目；Agent 声称"已提交"但实际没有 |
| 业务后果 | 一次越权就是流程事故或合规风险 |
| 平台能做什么 | 规则引擎、权限围栏、人工确认、审计日志 |
| 平台不能做什么 | 替业务定义 SOP 和红线内容 |

#### C. 人机协同

| 项 | 说明 |
|---|---|
| 表现 | 什么时候自动、什么时候转人工没有标准答案；交接、追问、拒绝的时机不稳定 |
| 典型场景 | 该转人工时继续执行；不该插话时乱插话；信息不足时编造而不是追问 |
| 业务后果 | 责任边界不清，用户不信任 |
| 平台能做什么 | 可配置的交接规则、确认节点、超时处理 |
| 平台不能做什么 | 替业务决定"什么算高风险" |

#### D. 上下文与知识

| 项 | 说明 |
|---|---|
| 表现 | 长对话/群聊噪声大；多源知识冲突；跨项目越界检索；上下文窗口有限 |
| 典型场景 | 把 A 项目讨论混进 B 项目；检索到其他服务的方案；关键决策被闲聊淹没 |
| 业务后果 | 输出污染、结论冲突、幻觉增加 |
| 平台能做什么 | 上下文筛选、检索、重排、trace 记录筛选结果 |
| 平台不能做什么 | 替业务提供领域知识与文档治理 |

#### E. 工具与系统集成

| 项 | 说明 |
|---|---|
| 表现 | 工具契约不稳定、参数错误、超时、失败重试；多工具串联的链路鲁棒性 |
| 典型场景 | 参数缺失仍调用；前一步错误传导到下游；工具失败后不降级 |
| 业务后果 | 任务中断、数据不一致、错误动作 |
| 平台能做什么 | Mock 工具、Schema 校验、权限围栏、超时/重试/降级 |
| 平台不能做什么 | 替业务维护真实系统与接口 |

#### F. 评测与迭代

| 项 | 说明 |
|---|---|
| 表现 | 没有 golden set；评测标准是行为而非文本；badcase 无法归因；版本迭代无法回归 |
| 典型场景 | 改 prompt 后不知道是否变差；修 A 坏 B；badcase 只能靠猜 |
| 业务后果 | 迭代慢、质量不可控、上线风险高 |
| 平台能做什么 | 用例管理、批量运行、trace、badcase 归集、回归对比 |
| 平台不能做什么 | 替业务写用例、定 golden、判断业务对错 |

#### G. 成本与性能

| 项 | 说明 |
|---|---|
| 表现 | token 成本、延迟、并发；长任务多步调用成本失控 |
| 典型场景 | 单任务成本不可预估；高峰期延迟不可接受 |
| 业务后果 | 规模化落地成本高 |
| 平台能做什么 | token/时延统计、步数上限、预算告警 |
| 平台不能做什么 | 替业务做模型选型与架构优化 |

#### H. 组织与协作

| 项 | 说明 |
|---|---|
| 表现 | 业务、算法、工程、评测多方协作；口径不一；责任边界模糊 |
| 典型场景 | 每个团队一套评测脚本；验收标准不一致；出问题互相推诿 |
| 业务后果 | 平台化难、规模化难 |
| 平台能做什么 | 统一流程、统一报告格式、统一指标口径 |
| 平台不能做什么 | 替组织定义责任与上线流程 |

### 2.3 瓶颈的影响链

```
模型不确定性 ──┐
上下文噪声   ──┼──→ 输出不可信 ──→ 人工逐条核对 ──→ 效率收益消失
工具/链路错误 ──┘

管控缺失     ──→ 越权/误放行 ──→ 流程事故 / 合规风险
不可观测     ──→ 无法归因     ──→ 修复靠猜
不可回归     ──→ 行为退化     ──→ 版本上线后事故
不可复用     ──→ 重复建设     ──→ 平台成本高、口径不一
```

### 2.4 平台能解 vs 不能解

| 瓶颈 | 平台能解 | 平台不能解 | 对应平台能力 |
|---|---|---|---|
| A 能力与确定性 | 暴露、量化、约束 | 提升模型能力 | trace + 回归 |
| B 业务约束与合规 | 规则、围栏、审计 | 定义业务 SOP | 规则引擎 + 围栏 |
| C 人机协同 | 可配置交接、确认 | 决定风险阈值 | 规则 + 人工确认 |
| D 上下文与知识 | 筛选、检索、记录 | 提供领域知识 | 上下文模块 |
| E 工具与系统 | 契约校验、围栏、重试 | 维护真实系统 | Mock 工具层 |
| F 评测与迭代 | 用例管理、运行、归因、回归 | 写用例、定 golden | 平台工作台 |
| G 成本与性能 | 统计、上限、告警 | 模型选型 | trace 统计 |
| H 组织与协作 | 统一流程与口径 | 定义责任与流程 | 报告 + Rubric |

> **一句话**：平台解的是"**评测与管控的基础设施**"，不是"业务 Agent 的全部生产问题"。

## 3. 从瓶颈到平台缺口

### 3.1 四类现状方案及其失效点

| 方案 | 角色 | 典型做法 | 失效点 |
|---|---|---|---|
| A 人工试用 | 现状 | 群里发消息、看输出、人工判断 | 不可复现、不可比、无 trace、无法回归 |
| B 成品 SaaS | **需求侧证据** | Claude Tag / 豆包工作伙伴 | 执行链路封闭：无结构化 trace、不可替换调度、不可编程交接、无批量回归 |
| C 大厂平台 | 直接竞品 | 火山 / 美团 / 腾讯 / 阿里 / 华为 | 面向企业采购、重、定制成本高、个人难用 |
| D 评测 / 观测工具 | 直接竞品 | LangSmith / LangFuse / Braintrust | 有 trace 与离线评测，不做执行前拦截与门禁判定 |
| E 自建脚本 | 替代方案 | 各团队自己写评测脚本 | 重复造轮子、口径不一、无统一门禁、难复用 |

> 成品 SaaS 是 Agent 产品，不是管控/评测平台；放在这里是为了说明"业务方现在怎么解决"，不是把它当竞品。

### 3.2 四个平台缺口（P1–P4）

> 注意：这四个缺口是**平台侧能力的缺口**，不是业务 Agent 的全部瓶颈。它们是从 §2 的 8 类瓶颈中，收敛出的"平台应该标准化、但现状没人做好"的部分。

| 编号 | 缺口 | 对应瓶颈 | 具体表现 | 平台模块 |
|---|---|---|---|---|
| **P1** | **管控规则不可配置** | B、C、E | 交接、权限、工具边界写死在产品里 | 规则引擎 + 权限围栏 |
| **P2** | **过程不可观测** | A、D、E | 拿不到结构化中间状态，badcase 无法归因 | Harness + trace |
| **P3** | **结果不可回归** | A、F | 无用例管理、无批量运行、无版本对比 | 用例管理 + 回归对比 |
| **P4** | **评测不可复用** | F、H | 每类 Agent 单独做一套评测，口径不一 | 统一 Adapter + Rubric 引擎 |

### 3.3 瓶颈 → 缺口 → 平台能力

| 瓶颈 | 主要缺口 | 平台能力 |
|---|---|---|
| B 业务约束 | P1 | 规则引擎、权限围栏、人工确认 |
| C 人机协同 | P1 | 交接规则、确认节点 |
| E 工具链路 | P1 / P2 | Mock 工具、Schema 校验、重试、trace |
| A 确定性 | P2 / P3 | trace、golden、回归 |
| D 上下文 | P2 | 上下文筛选、trace |
| F 评测迭代 | P3 / P4 | 用例管理、批量运行、归因、Rubric |
| H 组织协作 | P4 | Adapter、统一报告、统一口径 |
| G 成本 | P2（部分） | token/时延统计 |

> **完整链路**（瓶颈 → 痛点 → 缺口 → 模块 → FR → 代码 → 测试 → 指标）见 `16-全链路映射.md`。
> 平台只解这 4 个缺口；模型能力、领域知识、组织责任不在平台范围内。

### 3.4 为什么是现在

1. **市场验证**：火山 AgentKit、美团评测平台、腾讯 ADP、阿里 Sandbox、华为 AgentArts、Pyra 都在建这套能力；
2. **技术条件**：LangGraph 支持 interrupt / checkpointer / trace；function calling 稳定；LLM 成本可承受；
3. **招聘信号**：46 份 JD 中 23 份提到 Agent、10 份要求评测能力；
4. **成品缺口**：成品 SaaS 短期不会开放执行链路。

## 4. 用户、平台边界与场景

### 4.1 用户分层

| 层级 | 角色 | 与平台的关系 | 与 Sample A 的关系 |
|---|---|---|---|
| 直接用户 | Agent 开发者 / 业务团队 | 实现 Adapter、注册 Agent、跑评测 | 开发/维护 Sample A |
| 直接用户 | 评测 / 效能 / AI 平台团队 | 维护**自己业务的**用例与 Rubric、批量回归、看报告 | 评估 Sample A |
| 间接用户 | 管理层 / 合规 | 看报告、确认风险拦截、做上线决策 | 关注 Sample A 风险 |
| 终端用户 | 研发工程师 / SRE | 不直接使用平台 | 在飞书群与 Sample A 交互 |

> **关键区分**：平台的核心买家是「Agent 开发者 + 评测方」；终端用户不是平台用户。

### 4.2 平台统一什么 vs 业务方自有什么（重要修正）

> **平台不提供万能测试用例。** 不同业务 Agent 的 SOP、判定标准、红线完全不同，用例内容必须由业务方自己拥有。

| 类别 | 平台统一提供 | 业务方自己负责 |
|---|---|---|
| **用例** | 用例 Schema、分类标签、版本管理、批量执行、结果存储 | **具体 case 内容、golden answer、业务场景** |
| **Rubric** | Rubric 引擎、配置格式、运行与对比 | **评分维度、权重、判定标准** |
| **沙箱** | 隔离执行、Mock 工具注入、trace | 业务工具契约、Mock fixture |
| **流水线** | 批量运行、并发调度、版本绑定、回归任务 | 何时跑、跑哪些、验收门槛 |
| **观测** | trace 存储、看板、badcase 归集 | 业务语义解释、根因判断 |
| **评审** | 人工标注入口、标注流程、权限 | 谁来标、标什么、争议仲裁 |
| **安全** | 通用插件：幻觉检测、敏感内容、越权检测 | 业务红线、合规规则 |

**平台能提供的是"骨架"，不是"内容"：**

- ✅ 提供三类用例模板：正常协同 / 边界交接 / 对抗越权；
- ✅ 提供用例 Schema 与示例，降低业务方上手成本；
- ❌ 不提供跨业务通用的 golden 集；
- ❌ 不替业务判断"这个输出对不对"。

> 面试表述：**"平台统一的是评测基础设施，不是评测内容。每个业务方带着自己的用例和标准进来，平台负责让它们可运行、可观测、可对比。"**

### 4.3 用户画像

**画像 A：业务团队的 Agent 开发者**

- 目标：两周内把内部 Agent 推到可用；
- 痛点：不知道上线前该测什么，出问题只能看聊天记录；
- 诉求：给我沙箱、trace、用例模板，别让我从零搭。

**画像 B：评测 / 效能工程师**

- 目标：保证多个 Agent 行为稳定、可回归；
- 痛点：每个团队口径不同，版本迭代无法对比；
- 诉求：统一运行与报告，但用例由各业务方自己维护。

**画像 C：AI 平台负责人**

- 目标：建立公司级 Agent 上线门禁；
- 痛点：没有统一标准，风险不可控；
- 诉求：可配置准入规则、可审计 trace、可汇报报告。

### 4.4 Jobs-to-be-Done

1. **上线前验证**：当我要上线一个新 Agent，我想在仿真环境验证越权、交接、漂移，避免上线后出事。
2. **变更回归**：当我改 prompt / 规则 / 模型，我想用**我自己业务的用例**跑全量，知道有没有变差。
3. **badcase 归因**：当出现错误行为，我想定位是上下文、规则、工具、规划还是模型的问题。
4. **新 Agent 接入**：当我要接入一个新 Agent，我不想重写一套运行与评测基础设施。
5. **风险汇报**：当管理层要验收，我想看到可解释的拦截记录和评测报告。

### 4.5 用户旅程

```
接入 Agent（Adapter）
  → 导入/编写本业务用例与 Rubric
  → 批量运行（沙箱 + Mock 工具）
  → 查看 trace（中间状态、围栏、工具调用）
  → 对比回归（版本 diff、case 变化）
  → 输出报告（通过/失败/风险项）
```

### 4.6 场景优先级

| 优先级 | 场景 | 理由 |
|---|---|---|
| P0 | Sample A 接入 + 用例 + 运行 + trace | 平台最小闭环 |
| P0 | 越权拦截与交接判定 | 平台核心价值 |
| P1 | 版本回归对比 | 证明"可回归" |
| P1 | Rubric 引擎（内容由业务方提供） | 证明"跨范式" |
| P2 | Sample B 接入 | 可选，跨范式证据 |
| P2 | Streamlit 视图 | 演示体验 |
| P3 | 多 Agent 并发、权限体系 | 超出 POC |

## 5. 场景边界与准入判定

### 5.1 平台覆盖范围

| 覆盖 | 不覆盖 |
|---|---|
| 离线仿真执行 | 线上流量、灰度、A/B 实验 |

### 5.2 V1 只读 vs V2 工具调用

| 版本 | 能力 | 准入判定 | 是否需要评测底座 |
|---|---|---|---|
| V1 只读 | 读群、查文档、生成摘要 | 仅草稿/参考，人最终审核，无变更动作 | ❌ 不需要 |

## 6. 产品定义

### 6.1 价值主张

> **统一接入、统一沙箱、统一观测、统一回归；用例与标准归业务方。**
>
> 业务方只关心 Agent 的业务意图；运行、观测、评测、回归的基础设施由平台兜底。

### 6.2 平台 vs 应用

| 维度 | 应用 | 平台（本项目） |
|---|---|---|
| 核心对象 | 一个 Agent | 任意 Agent + 评测基础设施 |
| 价值来源 | 这个 Agent 做得好 | 平台能接入、观测、回归不同 Agent |
| 复用性 | 单场景 | 多 Agent / 多范式 |
| 内容归属 | 应用自带用例 | **用例与标准归业务方** |
| 成功标准 | 用户觉得好用 | 接入快、trace 全、可回归、可跨范式 |

### 6.3 核心能力（MVP）

| 能力 | 平台提供 | 业务方提供 | 对应缺口 |
|---|---|---|---|
| Agent 接入 | Adapter 接口、注册、能力声明 | Agent 实现 | P4 |
| 沙箱执行 | 隔离、Mock 注入、环境控制 | 工具契约、fixture | P1 |
| Harness 管控 | task_id、状态、超时、重试、异常 | 无 | P1 / P2 |
| trace | 全链路结构化记录、查看 | 业务语义解释 | P2 |
| 用例管理 | Schema、分类、版本、执行、结果 | **用例内容、golden** | P3 |
| Rubric 引擎 | 配置格式、运行、对比 | **维度、权重、判定标准** | P3 / P4 |
| 回归对比 | 指标 diff、case 级变化 | 验收门槛 | P3 |
| 安全插件 | 幻觉/敏感/越权通用检测 | 业务红线 | P1 |

### 6.4 差异化

| 对比对象 | 差异 |
|---|---|
| 大厂平台 | 轻量、可运行、个人可复现；双范式示例；公开实现 |
| LangSmith / LangFuse | 额外提供执行前围栏与硬门槛门禁，且与 trace 同链路 |
| Guardrails / NeMo | 同时提供评测、回归与门禁判定，不只做拦截 |
| 自建脚本 | 统一基础设施与口径；用例/Rubric/回归一体化 |

> 成品 SaaS 不在差异表里：它是需求侧证据，不是竞品。

### 6.5 一句话防守

> "成品把交互形态做出来了，但没有把可观测、可回归的评测基础设施开放出来；大厂平台有，但重；我做的是这两者之间缺失的轻量底座——**平台管基础设施，业务方管用例内容**。"

## 7. 目标与成功指标

### 7.1 指标设定原则（回应"是不是拍脑门"）

> 原文档的百分比目标确实有拍脑门成分。这一版改为**先分类、再定值、后校准**。

指标分五类，每类有不同的设定依据：

| 类型 | 定义 | 设定方式 | 是否允许调整 |
|---|---|---|---|
| **硬门槛** | 安全/工程底线，不满足就不能上线 | 二值约束（100% / 0） | 不允许降低 |
| **基线相对** | 与现状方案对比 | 先测基线，再定相对提升 | 允许按基线调整 |
| **业务推导** | 由错误成本/用户容忍度推导 | 与使用者校准 | 允许调整 |
| **工程约束** | 由可用性/成本约束决定 | 实测后定 | 允许调整 |
| **待校准** | POC 阶段无数据，只能先给假设值 | 标注"假设"，G4/G6 校准 | 必须校准 |

**校准时点**：G4（评测体系冻结）前，所有"待校准"指标必须要么被基线数据替换，要么降级为方向性目标。

### 7.2 平台级指标

| 指标 | 类型 | 设定依据 | 初设目标 | 校准时点 |
|---|---|---|---|---|
| Agent 接入耗时 | 工程约束 | 个人 POC 的易用性要求；需实测 | ≤ 30min | G6 |
| trace 完整率 | 硬门槛 | 没有完整 trace，评测与归因不成立 | 100% | G5 |
| 回归自动化率 | 硬门槛 | 平台核心价值；手工回归不可持续 | 100% | G5 |
| 运行可复现率（Mock） | 硬门槛 | Mock 确定性的前提；否则回归不可信 | 100% | G5 |
| 用例管理能力 | 工程约束 | 支持正常/边界/对抗三类 Schema、版本、批量执行 | 三类齐全 | G4 |
| Rubric 可配置数 | 业务推导 | 至少覆盖两类范式，才能证明"通用" | ≥ 2 | G4 |
| 版本对比可输出率 | 硬门槛 | 回归的核心交付物 | 100% | G6 |

> 注意：这里的"用例管理能力"是**能力指标**，不是"覆盖了多少条通用用例"——平台不提供通用用例。

### 7.3 Agent 级指标（Sample A）

| 指标 | 类型 | 设定依据 | 初设目标 | 校准时点 |
|---|---|---|---|---|
| 越权拦截率 | 硬门槛 | 一次越权放行即可能导致流程事故 | 100%（不允许漏拦） | G6 |
| 误拦截率 | 业务推导 | 误拦过多会导致使用者绕过平台；具体阈值需与使用者校准 | 初设 ≤ 10% | G6 |
| 上下文召回准确率 | 基线相对 | 先测"全量上下文"基线，再测筛选后；目标为满足任务可完成 | 初设 ≥ 85% | G6 |
| 无关混入率 / 漂移率 | 基线相对 | 同上 | 初设 ≤ 15% | G6 |
| 规则路由与确认判定 | 基线相对 | 与纯 LLM 分类对比 | 初设 ≥ 90% | G6 |
| 交接时机准确率 | 业务推导 + 人工复核 | 交接时机无唯一答案，以人工复核一致率为准 | 初设 ≥ 80%，需 2 人复核 | G6 |
| 不必要介入率 | 业务推导 | 由用户容忍度推导 | 初设 ≤ 15% | G6 |
| 事实忠实度 | 业务推导 | 研发场景对错误技术结论敏感 | 初设 ≥ 90% | G6 |
| 来源标注率 | 工程约束 | 可追溯的基本要求 | 初设 ≥ 90% | G6 |
| 平均步数 | 工程约束 | 控制 token 与延迟 | 初设 ≤ 6 | G6 |
| 单任务 token / 时延 | 工程约束 | 成本预算 | 在预算内 | G6 |

### 7.4 指标口径与校准计划

| 指标 | 定义 | 数据来源 | 校准方法 |
|---|---|---|---|
| 接入耗时 | 从拿到 Adapter 模板到第一个 case 跑通 | 记录 | 实测 2 次取平均 |
| trace 完整率 | 必填字段齐全的 step / 总 step | trace | 脚本校验 |
| 回归自动化率 | 自动执行的 case / 总 case | 运行记录 | 脚本统计 |
| 运行可复现率 | 同 case 同 Mock 下关键字段一致次数 / 总运行次数 | trace diff | 重复运行 3 次 |
| 越权拦截率 | 被拦截的越权尝试 / 总越权尝试 | 围栏日志 | 对抗集全量 |
| 误拦截率 | 合法调用被拦截次数 / 总合法调用 | 围栏日志 | 正常集全量 |
| 上下文召回 | 命中标注 relevant 的消息 / 总 relevant | 标注比对 | 人工标注 + 脚本 |
| 交接准确率 | 正确交接决策 / 交接类 case | 人工复核 + judge | 2 人独立标注，计算一致率 |
| 事实忠实度 | 有来源支撑的陈述 / 总陈述 | judge + 抽检 | 抽检 20% |
| 来源标注率 | 带来源的陈述 / 总陈述 | 代码 + judge | 脚本统计 |

### 7.5 指标优先级

| 优先级 | 指标 | 理由 |
|---|---|---|
| P0 | 越权拦截率、trace 完整率、回归自动化率、可复现率 | 平台核心价值与可信度 |
| P0 | 上下文召回、规则判定 | Sample A 主链路 |
| P1 | 交接准确率、误拦截率 | 行为质量 |
| P1 | 用例管理能力、Rubric 可配置数 | 平台通用性 |
| P2 | 事实忠实度、来源标注率 | 输出质量 |
| P2 | 接入耗时、平均步数 | 易用性与成本 |

## 10. 问题定义结论

### 10.1 最终问题陈述（可直接用于 README / 面试）

> 业务 Agent 从 Demo 走到生产，瓶颈不在"能不能生成"，而在**能不能被管住、被看见、被回归、被复用**。
> 成品 SaaS 只开放业务配置层，执行链路封闭；大厂平台面向企业采购、重且定制成本高；自建脚本重复造轮子。
> AgentGate 提供一套轻量的评测基础设施：统一 Adapter、沙箱、Harness、trace、用例管理、Rubric 引擎、badcase 归集与回归对比。
> **平台统一的是基础设施，不是测试内容**——每个业务方带着自己的用例与判定标准进来，平台负责让它们可运行、可观测、可对比。
> 我用研发协作 Agent（Sample A）和可选的售后工单 Agent（Sample B）两类不同范式，验证这套基础设施的通用性。

### 10.2 本阶段边界

- 不解决：线上流量评测、多租户、真实系统集成、模型训练；
- 只验证：离线仿真、Mock 工具、越权拦截、交接判定、trace、回归、跨范式；
- 不提供：跨业务通用用例库、通用 golden 集。

### 10.3 下一步

进入 **G2 调研与对标**：

1. 补齐大厂平台能力矩阵；
2. 完成飞书长连接 spike（本地 SDK 启动）；
3. 验证 LangGraph trace / interrupt；
4. 盘点公开数据源与用例 Schema 参考；
5. 输出 `02-竞品对标.md`、`03-可行性预研.md`、`04-数据源盘点.md`。
