## 0. 文档导读

### 0.1 这份文档的目的

把"这次错在哪"升级成"**这类错会不会再犯、怎么提前发现**"。

具体要给出：

1. Agent 有哪几类失败模式，各自在链路的哪个节点发生；
2. 每类模式在 trace 里长什么样（检测信号）；
3. 归因应该找**第一个**异常节点，而不是最后一个；
4. 哪些模式能离线发现、哪些必须线上、哪些现在完全没测。

| 读者 | 怎么用 |

| 评测 | 按模式补用例、补指标 |
| 面试 | 回答"你对 failure mode 的理解" |

### 0.4 核心结论（30 秒版）

> 我归因过 27 条 badcase，**其中 25 条是同一个根因**：意图分类器用 LCS 匹配，既误命中"一下"这种通用词，又覆盖不了"隐患/走流程"这类同义表达。
> 剩下 2 条是冲突仲裁。**没有一条是"模型能力不行"。**

- 不给出各模式的线上发生率（离线平台拿不到）；

## 1. 为什么需要模式库

`10-badcase归因.md` 解决的是"**这一轮** 27 条为什么失败"。它有一个 7 类归因框架，但只跑过一轮、只覆盖一个 Agent。

模式库要解决的是另外三件事：

| 问题 | 单轮归因 | 模式库 |
|---|---|---|
| 这次的错误属于哪一类 | ✅ | ✅ |
| 这类错误在 trace 里长什么样 | 🟡 | ✅ 检测信号 |
| 换个 Agent 还会不会犯 | ❌ | ✅ 跨范式 |
| 怎么保证修完不再犯 | 🟡 | ✅ 回归用例类型 |
| 哪些错误现在根本测不出来 | ❌ | ✅ 可观测性 |

JD 对这一点的要求很直接：

| JD | 原话 |
|---|---|
| #26 | 对 Agent 完整链路（模型、搜索、知识、Skill、MCP、Harness、评测）有理解，不能"说这是技术的事" |
| #38 | 基于 bad case 归因，**区分模型、知识、工具、流程或交互层问题** |
| #24 | 建立"评测 → 归因 → 策略建议 → 效果验证"的闭环 |
| #28 | 通过评测与监控识别它的**失败模式和断点** |

## 2. 归因原则：首因，不是末因

### 2.1 链路节点

```
route（意图/行为/路由）
  → filter（上下文筛选）
  → plan（工具选择与参数）
  → act（围栏校验 + 执行）
  → verify（结果校验）
  → respond（生成输出）
```

### 2.2 失败会传导

```
上下文污染 → 生成内容里出现无关风险 → judge 判"不忠于事实"
工具参数错 → 执行失败 → Agent 说"已完成" → 用户以为做了
意图判成 B6 → 不进入围栏 → 越权请求被放行
```

**如果只看最后一步，会修错地方。**

### 2.3 本项目的例子

`10-badcase归因.md` 的 27 条：

| 最终表现 | 条数 | 直接看会怎么修 | 真实根因 |
|---|---|---|---|
| 漏拦（B4 判成 B6） | 4 | 加围栏规则 | 意图分类没识别"走流程" |
| 超边界被误判 | 1 | 加拒绝关键词 | 通用词"一下"抢占 |
| 误拦（B2 判成 B6） | 12 | 放宽 B6 | 同义表达未覆盖 |
| 模糊指令被自动执行 | 6 | 收紧 B2 | LCS 匹配到"一下" |
| 决策被误判 | 4 | 调风险优先级 | 裸词"上线"抢占 |

**25 条的根因都是 F1（意图误判）**，其中 5 条进一步导致 F5（围栏漏拦）。

> 结论：**修 F1，F5 自然消失；只修 F5，F1 会换个地方再犯。**

### 2.4 归因操作规范

```
1. 打开 trace，从 seq=1 往后看
2. 找到第一个"与期望不符"的节点
3. 该节点即首因；后续节点的异常记为"传导"
4. 只对首因提修复方案
5. 把传导链写进报告，用于验证修复是否真的解决了下游
```

## 3. 12 个失败模式总表

> **离线可发现**：能否用现有离线用例与 trace 发现；**已观测**：本项目是否有真实数据。

| ID | 模式 | 节点 | 一句话定义 | trace 信号 | 责任方 | 离线可发现 | 已观测 |
|---|---|---|---|---|---|---|---|
| F1 | 意图误判 | route | 同义表达未覆盖、通用词抢占、冲突仲裁错 | `confidence` 低、`matched_phrase` 为通用词 | 规则 / 提示词 | ✅ | ✅ 27 条 |
| F2 | 上下文污染 | filter | 无关消息被保留并进入生成 | `dropped` 为空、无关消息出现在 `kept` | 筛选策略 | ✅ | ✅ drift 23.3% |
| F3 | 上下文缺失 | filter | 相关消息被筛掉或超窗截断 | `relevant_message_ids` 不在 `kept` | 筛选策略 | ✅ | ✅ recall 95.6% |
| F4 | 规划错误 | plan | 选错工具、参数缺失、步骤顺序错 | `tool` 不在 `available_tools`、`params` 缺字段 | 编排 / 提示词 | ✅ | 🟡 单工具，未充分 |
| F5 | 围栏漏拦 | act | 该拦没拦 | fence 全通过但语义应拦 | 规则 | ✅ | ✅ 5 条 |
| F6 | 围栏误伤 | act | 合法调用被拦 | fence 失败但 case 期望执行 | 规则 | ✅ | ✅ `false_block` |
| F7 | 工具失败未处理 | act / verify | 超时、错误、部分成功，无降级 | `tool_result.ok=false` 且无 fallback | 工具层 / 编排 | ✅ | 🟡 有故障注入 |
| F8 | 生成不实 | respond | 幻觉、无出处、超出上下文 | 陈述无 `[m_id]`；judge `factuality` 低 | 模型 / 提示词 | ✅ | ✅ 93.3% |
| F9 | 交接时机错 | route / verify | 该转人工没转、过早转、该追问却执行 | 实际 route ≠ `expected_route` | 规则 | ✅ | ✅ 100% |
| F10 | 状态不一致 | 全链路 | 声称已执行，实际没有 | 输出说"已提交"但 `act.executed=false` | 编排 | ✅ | 🟡 未系统覆盖 |
| F11 | 长链路累积 | plan → act × N | 第 N 步偏移，前序误差放大 | **无多步 trace**（当前单次调用） | 编排 | ❌ | ❌ |
| F12 | 成本 / 延迟超限 | 全链路 | token、步数、时长超预算 | **未采集** | 工程 | ❌ | ❌ |

## 4. 六个高优先级模式详解

### F1 意图误判

| 项 | 内容 |
|---|---|
| 定义 | 用户表达与意图库对不上，或被通用词抢占 |
| 典型 | "这次改动的隐患有哪些" → 判成 B6 追问；"把那个问题处理一下" → 判成 B2 自动执行 |
| trace 信号 | `confidence < 0.6`；`matched_phrase` 是"一下""这个"这类通用词；命中短语长度 ≤ 2 |
| 责任方 | 规则覆盖 / 提示词 / 分类器设计 |
| 修复 | 移除 LCS；显式短语 + 关键词；无命中默认 B6；LLM 主分类 + 规则兜底 |
| 回归 | 同义表达集，每类 ≥ 10 条 |
| 本项目数据 | 25 / 27 条 badcase |

### F2 / F3 上下文污染与缺失

| 项 | 内容 |
|---|---|
| 定义 | 筛选把无关的留下（F2），或把相关的丢了（F3） |
| 典型 | 把团建消息写进上线风险汇总；把"版本 3.1 下周发版"这条背景筛掉 |
| trace 信号 | `kept` / `dropped` 与 `relevant_message_ids` 对比；`strategy` 是 keyword 还是 semantic |
| 责任方 | 筛选策略、阈值、top_k |
| 修复 | 关键词 → 语义；阈值与 top_k 用独立数据校准；混合策略 |
| 回归 | 噪声注入 + 相关标注 |
| 本项目数据 | drift 23.3% → 17.2%；recall 100% → 95.6% |

> 这两类是一对**权衡**：降污染往往升缺失。所以必须同时报 `context_drift` 和 `context_recall`，只报一个就会自我欺骗。

### F5 / F6 围栏漏拦与误伤

| 项 | 内容 |
|---|---|
| 定义 | 该拦没拦（F5），或合法调用被拦（F6） |
| 典型 | 未定级就发起评审被放行；正常查询被误判为越权 |
| trace 信号 | `fence_checks` 的 `passed` 与 case 期望对比 |
| 责任方 | 围栏规则、前置条件 |
| 修复 | 补前置条件；但**先检查是不是 F1 传导过来的**（本项目 5 条都是） |
| 回归 | 对抗集（F5）+ 正常集（F6） |
| 本项目数据 | F5 5 条，F6 `false_block_rate`；消融：关掉围栏后 23/33 对抗用例执行高危写入（`09i`） |

### F8 生成不实

| 项 | 内容 |
|---|---|
| 定义 | 输出包含无法被给定消息支撑的陈述 |
| 典型 | 编造 CI 状态；把"可能相关"写成"确认" |
| trace 信号 | 陈述无 `[message_id]`；judge `factuality` 低；`violations` 命中 |
| 责任方 | 模型 / 提示词 |
| 修复 | 提示词要求逐条标来源；无法支撑时明确说不知道；用 `judge` 做离线拦截 |
| 回归 | 无出处断言类用例 |
| 本项目数据 | factuality 93.3%，1 条违规 |

### F9 交接时机错

| 项 | 内容 |
|---|---|
| 定义 | 该转人工没转、过早转、该追问却直接执行 |
| 典型 | 模糊指令"把那个问题处理一下"被自动执行；明确问题被反问 |
| trace 信号 | 实际 `route` ≠ `expected_route` |
| 责任方 | 规则（R1–R6） |
| 修复 | 默认追问；B3/B4/B5 强制确认/拒绝；连续失败 2 次转人工 |
| 回归 | 交接类用例 |
| 本项目数据 | `handoff_accuracy` 100%（B2 不评） |

## 5. 优先级矩阵：严重度 × 频次

| | 频次高 | 频次中 | 频次低 / 未知 |
|---|---|---|---|
| **严重度高**（事故 / 合规 / 资金） | **F1**（会传导成 F5） | **F5**、**F8** | **F10**、**F11** |
| **严重度中**（体验 / 返工） | F2、F3 | F9 | F7 |
| **严重度低**（效率） | — | F4 | F6、F12 |

**读法**：

- 左上角 F1 是唯一一个"高频 + 高危"的模式，必须优先；
- F10 和 F11 频次未知，但严重度高——**未知不等于没有**，要先补可观测性；
- F6 误伤严重度低但频次可能高，要看 `false_block_rate` 是否超过容忍线。

## 10. 面试怎么讲（60 秒）

> "我归因过 27 条 badcase，其中 25 条是同一个根因：分类器用 LCS 匹配，既会误命中'一下'这种通用词，又覆盖不了'隐患''走流程'这类同义表达。剩下 2 条是冲突仲裁。没有一条是'模型不行'。
>
> 这里面有个方法论：归因要**沿 trace 找第一个异常节点**，不是看最后错在哪。因为有 5 条最后表现为'漏拦'，如果只盯着围栏补规则，永远修不好——得修分类器。
>
> 我把这些整理成了 12 类失败模式，每类带 trace 信号、责任方和回归用例。但我得说清楚：12 类里 7 类有数据，2 类完全没测——长链路和成本。这两个是我下一步要补的。"

### 10.1 三个可能的追问

| 追问 | 应答 |
|---|---|
| 怎么区分模型问题和规则问题？ | "看 trace 的第一个异常节点。route 错了是分类问题，respond 错了才是生成问题。" |
| 长链路怎么归因？ | "现在做不了。我没有多步用例，也没有步级 trace 评分。要补三层：步级、任务级、恢复级。" |
| 失败模式库能复用到别的 Agent 吗？ | "结构可以，信号要重写。Sample B 我只做了规则版验证，还没做归因——这是明确的缺口。" |
