## 0. 文档导读

### 0.1 这份文档的目的

把项目从"分层罗列"改成**一条可追溯的链路**：

```
业务 Agent 投产瓶颈
  → 业务痛点
  → 平台缺口（P1–P4）
  → 平台模块
  → PRD 需求（FR）
  → 功能 / 代码
  → 单元测试
  → 评测指标 / 报告
  → 实现状态
```

任何一句"我做了 X"，都能在这条链上找到证据；任何一句"没做 Y"，也能定位到缺哪一层。

### 0.2 读者与使用方式

| 读者 | 怎么用 |
|---|---|
| 候选人 | 面试时按链路讲，不按模块堆功能 |
| 项目负责人 | 判断某个缺口是否真的闭环 |
| 后续迭代 | 从"状态"列找下一步 |

### 0.3 本文包含什么

```
§1 主链路
§2 P1 管控规则不可配置
§3 P2 过程不可观测
§4 P3 结果不可回归
§5 P4 评测基础设施不可复用
§6 汇总表
§7 状态总结
§8 术语修正
```

### 0.4 核心结论（30 秒版）

> 8 类投产瓶颈里，平台只解 4 类缺口：**管控、观测、回归、复用**。
> 这 4 个缺口分别落到规则/围栏、Harness/trace/context、用例/评测/Rubric、Adapter/双示例。
> 每个缺口都有对应的 FR、代码、测试、指标和报告；但**每一层都还有未完成的尾部**，见 §7。

## 2. P1 · 管控规则不可配置

### 2.1 链路

| 层 | 内容 |
|---|---|
| 瓶颈 | B 业务约束与合规；C 人机协同；E 工具与系统集成 |
| 痛点 | SOP 不遵守、越权、无法追溯；何时转人工不稳定；参数错误、链路传导 |
| 缺口 | 管控规则写死在产品里，业务不能配置交接/权限/工具边界 |
| 模块 | 规则引擎、工具围栏、人工确认 |
| FR | FR-13 权限围栏；FR-14 人工确认；FR-18 异常与重试（部分） |
| 代码 | `rules.py::decide`；`tools.py::ToolRegistry.check`；`samples/ticket/tools.py::TicketToolRegistry.check`；`feishu.py::build_confirmation_card`；`feishu_ws.py::on_card` |
| 测试 | `tests/test_tools.py`（F1–F5）；`tests/test_ticket_tools.py`（T1/T2/T5）；`tests/test_feishu.py`（卡片）；`tests/test_llm_agent.py`（确认） |
| 指标 | `fence_interception`、`false_block_rate`、`handoff_accuracy` |
| 报告 | `09`、`09e`、`09f`、`09h` |
| 状态 | 🟡 功能有；规则/围栏硬编码；无业务配置；无 30min 超时；R6 冲突仲裁未实现 |

### 2.2 当前的真实用法

- 工具围栏**不是**"用户注册工具时手动配置"；当前是代码写死的 `check()`。
- 目标设计才是：业务方注册工具时声明 schema、风险级、前置条件、确认要求；平台提供围栏引擎。
- 所以现在能演示"围栏能拦"，不能演示"业务能配围栏"。

## 3. P2 · 过程不可观测

### 3.1 链路

| 层 | 内容 |
|---|---|
| 瓶颈 | A 能力与确定性；D 上下文与知识；E 工具链路；G 成本（部分） |
| 痛点 | 同一输入结果不同、幻觉；群聊噪声、跨项目污染；工具失败；成本不可控 |
| 缺口 | 拿不到结构化中间状态，badcase 无法归因 |
| 模块 | Harness、TraceRecorder、ContextFilter、成本统计 |
| FR | FR-08 trace；FR-09 trace 查看；FR-17 成本统计；FR-18 超时/重试 |
| 代码 | `harness.py::run_case`；`trace.py::TraceRecorder.record`；`context.py::SemanticContextFilter.filter`；`llm.py`（未记 usage） |
| 测试 | `tests/test_core.py`（schema/trace）；`tests/test_context.py`（BGE）；`tests/test_harness.py`；`tests/test_langgraph_agent.py` |
| 指标 | `trace_completeness`、`context_recall`、`context_drift`、`factuality`、`source_support` |
| 报告 | `09d`、`09g` |
| 状态 | 🟡 trace/context 有；无 trace viewer、无 tokens/latency、无 timeout/retry、无持久化 |

### 3.2 关键澄清

- `context_drift` 实际是 **`1 - context_precision`**（无关上下文混入率），不是分布漂移；
- 建议展示名称改为"无关上下文混入率"，代码字段保留 `context_drift` 兼容；
- 平台级 trace 指标评平台；Agent 级 factuality/source 评 Agent。

## 5. P4 · 评测基础设施不可复用

### 5.1 链路

| 层 | 内容 |
|---|---|
| 瓶颈 | F 评测与迭代；H 组织与协作 |
| 痛点 | 每类 Agent 单独做评测、口径不一、重复造轮子 |
| 缺口 | 无统一 Adapter/Rubric/工具层，跨范式不可复用 |
| 模块 | Agent Adapter、Tool Adapter、Rubric、双示例 |
| FR | FR-01 Agent 注册；FR-02 版本；FR-05 Rubric；FR-12 Mock 工具；FR-15 Sample A；FR-16 Sample B |
| 代码 | `models.py::AgentMetadata`；`factory.py::build_agent`；`samples/rd_collab/adapter.py`；`samples/ticket/adapter.py`；`samples/ticket/tools.py`；`judge.py`；`langgraph_agent.py` |
| 测试 | `tests/test_factory.py`；`tests/test_llm_agent.py`；`tests/test_langgraph_agent.py`；`tests/test_ticket_agent.py`；`tests/test_ticket_dataset.py` |
| 指标 | Sample B 的 `pass_rate`/`fence_interception`；Rubric 可配置数；接入耗时（未测） |
| 报告 | `09f`、`09h` |
| 状态 | 🟡 双范式/Rubric 有；无注册表/版本持久化；Adapter 只实现 2 方法；无 HTTP Adapter；B1–B6 通用性未正式验证 |

### 5.2 关键澄清

- 每来一个 Agent，确实要写一个 Adapter，但只需要 `metadata()` + `run()` 两个薄方法；
- 平台（Harness/评测/工具层）不需要重写；
- 标准 HTTP Adapter 可以把"每个 Agent 写一个类"变成"配置一个 endpoint"。

## 8. 术语修正

| 旧说法 | 修正 |
|---|---|
| P1 管控不可编程 | P1 管控规则不可配置（避免"写代码"歧义） |
| Agent Adapter 3 个方法 | 设计 3 个，当前实现 `metadata` + `run`；`rubric()` 未用 |
| 上线门禁 | 围栏 + Rubric 硬门槛 + 回归对比的组合概念，不是独立模块 |
| 规则上下文 | 关键词/话题筛选（`--context rule`），不是规则引擎 |
| context_drift | 无关上下文混入率 = `1 - context_precision` |
| 公开语料改写 | 当前是 synthetic template + 2 条手写；公开语料未接入 |
| 业务配置层（人设/技能/权限/触发/审计） | 本项目未实现；只有 metadata/围栏/trace 的零散对应 |
