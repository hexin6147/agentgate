## 0. 文档导读

### 0.1 这份文档的目的

回答一个问题：**通用平台怎么判断"这个任务该自动、该确认、该追问还是该拒绝"？**

具体要定稿：

1. 为什么平台**不定义通用业务任务类型**；
2. 平台只定义 6 个**通用行为类别**（B1–B6）；
3. 业务意图如何由每个 Agent 自己声明；
4. 行为类别如何映射到规则 R1–R6；
5. 冲突仲裁、超时降级、配置格式、评测方式。

### 0.2 读者与使用方式

| 面试 | 用"行为类别 vs 业务意图"解释平台为什么能接不同 Agent |

### 0.4 核心结论（30 秒版）

> **通用平台不应该定义通用的业务任务类型**——客服的"查订单"、研发的"汇总风险"、财务的"审批报销"没有共同语义。
> 平台只定义 6 个**行为类别**：B1 读取/检索、B2 生成/汇总、B3 结论/定级、B4 写入/变更、B5 超边界、B6 信息不足。
> 每个 Agent 通过 Adapter 声明自己的**业务意图**，并把每个意图映射到一个行为类别。
> 规则引擎只看行为类别 + 风险等级 + 工具风险，因此同一套规则可以服务所有业务。

### 0.5 本文不解决什么

- 不定义具体业务的意图清单（由业务方在 Agent 配置中声明）；
- 不定义工具的具体业务规则（由 ToolAdapter 提供）；
- 不定义审批流、会签、代理审批；
- 不定义企业级权限体系。

## 1. 设计原则

| 原则 | 说明 |
|---|---|
| **平台定义行为，业务定义意图** | 平台只管"这是什么动作、风险多高"，不管"业务上叫什么" |
| **规则优先，LLM 辅助** | LLM 做意图匹配与语义理解，风险与动作由规则决定 |
| **可扩展** | 新业务只需注册意图，不改平台代码 |
| **可解释** | 每次判定记录 intent / behavior / rule / reason |
| **失败安全** | 无法判断时转人工或追问，不自动执行 |
| **可评测** | 意图、行为、规则命中都写入 trace |

> 一句话：**"平台管动作语义，业务管意图内容；LLM 管理解，代码管允许与终止。"**

## 2. 两层分类：平台行为类别 + 业务意图

### 2.1 为什么不做通用业务任务类型

如果平台硬编码 T1–T8（信息汇总、风险梳理、变更动作……），会遇到两个问题：

1. **覆盖不全**：客服的"查订单/查赔付规则/提交工单"、研发的"汇总风险/发起评审"、财务的"审批报销"、销售的"生成报价"，无法穷举；
2. **语义偏置**：一旦写死，平台就变成"为某个业务定制的平台"，失去通用性。

正确做法：

> **平台定义"动作语义"（behavior），业务定义"意图名称"（intent）。**
> 平台不关心你叫"汇总风险"还是"生成工单摘要"，只关心它是 B2（生成/汇总）还是 B4（写入/变更）。

### 2.2 平台行为类别 B1–B6

| 编号 | 行为类别 | 定义 | 典型动作 | 默认风险 |
|---|---|---|---|---|
| **B1** | 读取 / 检索 | 只读工具或已有上下文，返回事实 | 查群消息、查文档、查 CI、查订单 | 低 |
| **B2** | 生成 / 汇总 / 草稿 | 基于事实生成摘要、清单、草稿；人最终审核 | 汇总风险、整理待办、生成回复草稿 | 低–中 |
| **B3** | 结论 / 建议 / 定级 | 要求做出判断、评分、决策建议 | 能否上线、风险定级、能否赔付 | 高 |
| **B4** | 写入 / 变更 | 调用写入类工具，修改状态或创建对象 | 创建 Issue、发起评审、提交工单、改工单状态 | 高 |
| **B5** | 超边界 | 真实审批、资金、发布、越权访问 | 直接上线、批准赔付、访问其他项目 | 高 |
| **B6** | 信息不足 | 缺任务对象、范围或判断依据 | "把那个问题处理一下" | 低 |

**行为类别的通用性**：任何业务场景都能映射到 B1–B6 之一。平台不需要知道业务名词。

### 2.3 业务意图注册（由 Agent 声明）

每个 Agent 在 metadata 中声明自己的意图清单：

```yaml
agent_id: rd_collab
intents:
  - id: rd_risk_digest
    name: 汇总上线风险
    behavior: B2
    examples:
      - "汇总本次版本上线的风险"
      - "把群里提到的风险列一下"
  - id: rd_ci_query
    name: 查询 CI 状态
    behavior: B1
    examples: ["查一下 CI", "构建过了吗"]
  - id: rd_request_review
    name: 发起变更评审
    behavior: B4
    examples: ["发起评审", "提交变更"]
  - id: rd_go_live_decision
    name: 判断能否上线
    behavior: B3
    examples: ["这次能不能上线", "帮我定级"]
  - id: rd_out_of_scope
    name: 真实审批/发布/资金
    behavior: B5
    examples: ["直接上线", "批准赔付"]
```

**约束**：

- `id` 由业务方定义，平台不限制命名；
- 每个 intent 必须映射到 B1–B6 之一；
- `examples` 用于意图匹配与评测；
- 未声明的意图 → 走 B6 或 B5 的兜底逻辑。

### 2.4 两个示例的映射对照

| 业务 | 业务意图 | 行为类别 | 规则 |
|---|---|---|---|
| Sample A | 汇总上线风险 | B2 | R1 |
| Sample A | 查 CI | B1 | R1 |
| Sample A | 发起变更评审 | B4 | R5 |
| Sample A | 能不能上线 | B3 | R2 |
| Sample A | 直接上线/批准赔付 | B5 | R4 |
| Sample B | 查订单 | B1 | R1 |
| Sample B | 查赔付规则 | B1 | R1 |
| Sample B | 提交工单 | B4 | R5 |
| Sample B | 能不能赔 | B3 | R2 |
| Sample B | 直接赔付 | B5 | R4 |

> 这张表证明：**平台不需要通用业务任务类型，只需要 6 个行为类别**。同一个 R5 同时覆盖"发起评审"和"提交工单"。

## 3. 路由流程

### 3.1 总流程

```
用户 query
  ↓
① 意图匹配（在该 Agent 声明的 intents 中匹配）
  ↓
② 得到 intent_id → 查 behavior（B1–B6）
  ↓
③ 结合工具意图、风险等级、上下文
  ↓
④ 规则引擎 → action（auto / confirm / ask / reject）
  ↓
⑤ 写 trace（intent / behavior / rule / reason / confidence）
```

### 3.2 意图匹配

| 情况 | 处理 |
|---|---|
| 匹配到某个 intent | 使用其 behavior |
| 匹配到多个 intent | 取风险级最高的 behavior |
| 匹配不到 | 检查是否含 B5 关键词/工具意图 → B5；否则 B6 |
| 置信度 < 0.6 | B6（追问）或转人工 |
| LLM 与工具意图冲突 | **以工具意图为准**（如 LLM 判 B2，但调用 `request_review` → 校正为 B4） |

### 3.3 行为校正规则

| 信号 | 校正 |
|---|---|
| 调用写入类工具 | → B4 |
| 要求真实审批/资金/发布 | → B5 |
| 要求访问未授权项目 | → B5 |
| 缺任务对象/范围/依据 | → B6 |
| 要求给出结论/定级/建议 | → B3 |
| 只读工具 + 仅列事实 | → B1 |
| 基于事实生成草稿 | → B2 |

### 3.4 Trace 字段

```json
{
  "seq": 1,
  "node": "route",
  "intent_id": "rd_request_review",
  "behavior": "B4",
  "rule_hit": ["R5"],
  "risk_level": "high",
  "reason": "调用写入工具 request_review",
  "confidence": 0.85
}
```

## 4. 规则表 R1–R6

| 规则 | 行为类别 | 动作 | 风险级 |
|---|---|---|---|
| **R1** | B1 / B2（只读、基于事实、无结论、无写入） | **自动执行** | 低 |
| **R2** | B3（结论、定级、建议） | **人工确认** | 高 |
| **R3** | B6（信息不足） | **主动追问**，禁止编造 | 低 |
| **R4** | B5（超边界） | **拒绝并移交** | 高 |
| **R5** | B4（写入/变更） | **围栏校验 + 人工确认** | 高 |
| **R6** | 多规则同时命中 | 取最高风险级；同级按 R4 > R2 > R5 > R3 > R1 | — |

### 4.1 规则细化

**R1 自动执行的前提**：

- 只调用读工具；
- 输出基于上下文事实；
- 不包含结论性判断；
- 不触发任何写操作；
- 若 B2 草稿会被对外发布 → 升级为 B4/B5 处理。

**R2 确认的触发**：

- 输出会影响决策（能否上线、是否定级、是否赔付）；
- 人工可在卡片上选择：确认 / 驳回 / 补充信息。

**R3 追问的触发**：

- 缺少任务对象（哪个项目/哪次故障）；
- 缺少判断依据；
- 上下文冲突且无法自洽。

**R4 拒绝的触发**：

- 要求真实审批、资金、发布；
- 要求越权访问其他项目；
- 要求绕过人工确认。

**R5 确认 + 围栏**：

- 先过 Schema / 权限 / 前置条件；
- 围栏不通过 → 不弹确认，直接返回拒绝理由；
- 围栏通过 → 弹确认卡片；
- 人工确认后由 Harness 写入 `confirmation_token`，再执行 Mock 工具；
- 执行层若拿不到令牌，F2 拒绝，避免绕过确认。

## 5. 优先级与冲突仲裁

### 5.1 优先级

```
R4（拒绝） > R2（确认） > R5（确认+围栏） > R3（追问） > R1（自动）
```

### 5.2 仲裁示例

| 命中 | 结果 | 理由 |
|---|---|---|
| R1 + R2 | R2 | 涉及结论性判断 |
| R1 + R5 | R5 | 有写入工具调用 |
| R2 + R5 | R2（并叠加围栏） | 高风险优先，且工具仍需围栏 |
| R3 + R5 | R5 | 有明确写入意图时，先围栏/确认，再追问缺失字段 |
| 任何 + R4 | R4 | 超边界直接拒绝 |

> 记录：仲裁结果必须写入 trace 的 `rule_hit` 与 `reason`。

## 6. 判定条件

### 6.1 交接（转人工）

| 条件 | 阈值 |
|---|---|
| 置信度 | < 0.6 |
| 连续失败 | ≥ 2 次 |
| 人工确认超时 | 30min |
| 行为类别为 B3 / B4 / B5 | 强制 |
| 用户明确要求 | 立即 |

### 6.2 追问

| 条件 | 示例 |
|---|---|
| 缺任务对象 | "哪个项目？" |
| 缺时间范围 | "哪次发布？" |
| 缺判断依据 | "以什么标准定级？" |
| 上下文冲突 | "两个版本的结论不一致，以哪个为准？" |

### 6.3 拒绝

| 条件 | 回复 |
|---|---|
| 超边界 | "该操作需要真实审批权限，我不能执行，已转交人工。" |
| 越权 | "我没有访问该项目/群组的权限。" |
| 绕过确认 | "高风险操作必须经人工确认，不能跳过。" |

### 6.4 确认

| 条件 | 卡片内容 |
|---|---|
| B3 | 结论摘要 + 依据 + 确认/驳回 |
| B4 | 工具名 + 参数 + 围栏结果 + 确认/驳回 |

## 7. 超时与降级

| 场景 | 行为 |
|---|---|
| 人工确认 30min 未响应 | 标记 `EXPIRED`，通知发起人，任务终止 |
| 工具失败 1 次 | 重试 1 次 |
| 工具仍失败 | 降级为"告知失败原因 + 建议人工" |
| LLM 超时 | 重试 1 次，仍失败则 `FAILED` |
| 上下文过长 | 裁剪 + 摘要，记录裁剪策略 |
| 规则冲突无法仲裁 | 默认转人工 |
| 意图匹配不到 | B6 追问；含高风险关键词则 B5 拒绝 |

## 8. 确认交互

### 8.1 飞书卡片

```
┌──────────────────────────────┐
│ 需要确认：发起变更评审          │
│ 业务意图：rd_request_review    │
│ 行为类别：B4 写入/变更          │
│ 工具：request_review          │
│ 围栏：F1 未通过                │
│ [驳回] [补充信息] [确认]        │
└──────────────────────────────┘
```

- 回调：`card.action.trigger`；
- 动作映射：`approve` / `reject` / `supplement`；
- 3 秒内响应，耗时逻辑异步；
- 幂等：按 `task_id + action` 去重。

### 8.2 Streamlit 兜底

- 卡片不可用时，用 Streamlit 按钮完成确认；
- 结果写回同一 `task_id`；
- 面试时说明"飞书负责真实入口，本地工作台兜底"。

## 9. 配置格式

### 9.1 Agent 意图注册

```yaml
agent_id: rd_collab
intents:
  - id: rd_risk_digest
    name: 汇总上线风险
    behavior: B2
    examples: ["汇总本次版本上线的风险", "把风险列一下"]
  - id: rd_ci_query
    name: 查询 CI 状态
    behavior: B1
    examples: ["查一下 CI", "构建过了吗"]
  - id: rd_request_review
    name: 发起变更评审
    behavior: B4
    examples: ["发起评审", "提交变更"]
```

### 9.2 规则配置

```yaml
version: 1
rules:
  - id: R1
    when:
      behavior: [B1, B2]
      tools: [read_only]
    action: auto
    risk: low

  - id: R2
    when:
      behavior: [B3]
    action: confirm
    risk: high

  - id: R3
    when:
      behavior: [B6]
    action: ask
    risk: low

  - id: R4
    when:
      behavior: [B5]
    action: reject
    risk: high

  - id: R5
    when:
      behavior: [B4]
    action: confirm_and_fence
    risk: high

priority: [R4, R2, R5, R3, R1]
```

### 9.3 校验

- 每个 intent 必须映射到 B1–B6；
- 规则必须覆盖全部 6 个行为类别；
- priority 覆盖全部规则；
- 不允许删除 R4/R5。

## 10. 评测与命中记录

### 10.1 Trace 字段

```json
{
  "seq": 1,
  "node": "route",
  "intent_id": "rd_request_review",
  "behavior": "B4",
  "rule_hit": ["R5"],
  "risk_level": "high",
  "reason": "调用写入工具 request_review",
  "confidence": 0.85
}
```

### 10.2 指标

| 指标 | 计算 |
|---|---|
| 意图匹配准确率 | 匹配 intent 与标注 intent 一致 / 总数 |
| 行为分类准确率 | behavior 与标注一致 / 总数 |
| 规则命中准确率 | 命中规则与 expected_route 一致 / 总数 |
| 误拦截率 | 合法任务被确认/拒绝 / 合法任务总数 |
| 漏拦截率 | 应确认但自动执行 / 应确认总数 |
| 追问准确率 | 正确追问 / 信息不足 case |

### 10.3 评测用例

| 类型 | 期望 |
|---|---|
| B1 读取 | R1，AUTO |
| B2 汇总 | R1，AUTO |
| B3 结论 | R2，CONFIRM |
| B4 写入 | R5，CONFIRM + 围栏 |
| B5 超边界 | R4，REJECT |
| B6 信息不足 | R3，ASK |
| 冲突 | 按优先级裁决 |

## 11. 走查示例

### 示例 1：Sample A · 汇总风险（B2/R1）

```
用户：@Agent 汇总本次版本上线的风险
意图匹配：rd_risk_digest → B2
规则：R1 → AUTO
执行：search_chat_history → 提取事实 → 标注来源 → 回复
trace：route(intent=rd_risk_digest, B2, R1) → filter → plan → act(search) → verify → respond
```

### 示例 2：Sample A · 发起评审（B4/R5 + 围栏）

```
用户：@Agent 直接发起变更评审
意图匹配：rd_request_review → B4
规则：R5 → CONFIRM + FENCE
围栏：F1 故障未定级 → 不通过
结果：不弹确认，直接回复"需先定级"
trace：route(intent=rd_request_review, B4, R5) → act(request_review) → fence F1 false → executed false
```

### 示例 3：Sample A · 能否上线（B3/R2）

```
用户：@Agent 这次能不能上线？
意图匹配：rd_go_live_decision → B3
规则：R2 → CONFIRM
动作：生成结论摘要 + 依据 → 弹卡片
结果：人工确认/驳回
```

### 示例 4：Sample A · 超边界（B5/R4）

```
用户：@Agent 帮我批准这个赔付
意图匹配：rd_out_of_scope → B5
规则：R4 → REJECT
结果：拒绝并移交人工
```

```

### 示例 8：Sample B · 能否赔付（B3/R2）

```
