## 1. 只记三句话

1. **我做的是平台，不是单个 Agent**：平台统一基础设施，业务方自带用例与判定标准。
2. **LLM 负责理解，规则负责控制**：意图分类和摘要用 LLM，允许/确认/拒绝/终止用确定性规则。
3. **我用两类 Agent 证明通用性**：研发协作 + 售后工单，同一套 Harness、LangGraph、评测脚本。

> 如果面试只有 15 秒，就说这三句。

## 2. 30 秒电梯版

> "我做了一个 **Agent 上线门禁与离线评测平台**。它不是再做一个聊天机器人，而是解决 Agent 上线前的管控、观测、评测、回归。
>
> 平台用统一 Adapter 接入任意 Agent，用 B1–B6 行为分类和 R1–R6 规则决定自动、确认、拒绝还是追问，用结构化 trace 做行为级评测。
>
> 我在上面接了两类 Agent：研发协作和售后工单，用同一套 Harness 和评测脚本验证。规则版 held-out 只有 60%，接 LLM 后到 100%，但我明确知道这是 20 条小样本，不是线上结论。"

**要点**：

- 第一句定性质：平台，不是 Agent；
- 第二句讲机制：Adapter + 行为分类 + 规则 + trace；
- 第三句给证据 + 保留：双范式 + 60%→100% + 样本小。

## 3. 3 分钟版

> 讲法：按「瓶颈 → 痛点 → 缺口 → 模块 → 需求 → 代码 → 测试 → 指标 → 状态」讲，不按模块堆功能。

### 0:00–0:30 瓶颈与痛点

> "业务 Agent 从 Demo 到生产，卡的不是生成，而是四类：
> B 业务约束——SOP 不遵守、越权；
> C 人机协同——什么时候转人工不稳定；
> D 上下文——群聊噪声、跨项目污染；
> F 评测——无 golden、badcase 难归因、修 A 坏 B。"

### 0:30–1:05 缺口与模块

> "我把它收敛成 4 个平台缺口：
> P1 管控规则不可配置 → 规则引擎 + 工具围栏 + 人工确认；
> P2 过程不可观测 → Harness + trace + 上下文筛选；
> P3 结果不可回归 → 用例 + 评测 + 回归 + Rubric；
> P4 评测不可复用 → Adapter + 双示例。"

### 1:05–2:00 需求、代码、测试

> "每个缺口都有对应需求、代码和测试：
> P1 是 FR-13/14/18，代码在 rules.py、tools.py、feishu.py，测试在 test_tools、test_ticket_tools、test_feishu；
> P2 是 FR-08/09/17/18，代码在 harness.py、trace.py、context.py，测试在 test_core、test_context、test_harness；
> P3 是 FR-03 到 FR-11，代码在 schema、runner、evaluation、rubric，测试在 test_evaluation、test_rubric、test_dataset；
> P4 是 FR-01/02/05/12/15/16，代码在 factory、两个 sample，测试在 test_factory、test_ticket。
> LLM 只做意图分类和摘要；允许、确认、拒绝、终止由规则和围栏决定。"

### 2:00–2:40 指标与结果

> "指标也按层：
> P1 看 fence、false_block、handoff；
> P2 看 trace、recall、无关混入率、factuality；
> P3 看 pass_rate、behavior/route、Rubric 加权；
> P4 看 Sample B 通过率和 Rubric 可配置数。
> 结果：Sample A 规则版 held-out 60%，LLM 版 100%；BGE 把无关混入率从 23.3% 降到 17.2%；judge factuality 93.3%；Sample B 24/24；Rubric 0.887 和 1.000。同一套 Harness/评测脚本，只换 Adapter、工具和 Rubric。
> 另外，Agent 指标之外我还做了平台模块的消融：关掉围栏，33 条对抗用例里 23 条会真的执行高危写操作；打开是 0。这是我目前唯一一条平台级效果证据。"

### 2:40–3:00 保留

> "但 dev 的 100% 有 in-sample；held-out 只有 20 条，其中 5 条是探针；数据是 synthetic template；三轨判定里人评是 0，24 条 human_review 实际是 LLM 判的；平台是机制层通了，配置层和管理层没通。"

## 4. 5 分钟版

在 3 分钟版基础上，插入五段。

### 4.1 竞品与差异（约 50 秒）

> "竞品我只对标同类：大厂 Agent 平台（火山 / 美团 / 腾讯 / 阿里 / 华为）、LangSmith / LangFuse 这类评测与观测工具，以及团队自建脚本。
>
> 大厂把沙箱、接入、trace、用例、Rubric、回归都做了，但面向企业采购，个人跑不起来。
> LangSmith 强在 trace 和离线评测，但不做执行前拦截；Guardrails 强在拦截，但不做评测和回归。我的位置是把这两件事接在同一条 trace 上。
>
> Claude Tag / 豆包不是竞品，是需求侧证据——说明企业已经在部署 Agent，但执行链路封闭，所以才需要外部的管控层。"

### 4.2 关键设计决策（约 50 秒）

> "有三个决策值得讲：
> 第一，平台 vs 应用。如果只做一个 IM 机器人，面试官会把它当应用；做成平台，价值变成可复用底座。
> 第二，LLM + 规则。纯 LLM 做风险判断不可控，纯规则覆盖不了同义表达；所以 LLM 主分类、规则兜底和控边界。
> 第三，Mock 工具。不接真实 Jira/CI，是为了零副作用、可复现；评测对象是围栏逻辑，不是集成能力。"

### 4.3 迭代闭环（约 50 秒）

> "第一版规则分类器 dev 只有 68.6%，我归因出 5 类 27 条 badcase，把 LCS 换成显式短语 + 关键词，dev 到 100%；但 held-out 只有 60%，证明是同集调参。
> 接 LLM 后 held-out 到 100%，dev 复跑又发现 7 条语义偏移，加了写操作、模糊查询、汇总一致性三类护栏，dev 回到 86/86，held-out 没回归。
> 这个循环本身，就是我想展示的 AI PM 能力：**发现问题 → 归因 → 修复 → 回归**，而不是一次调好。"

### 4.4 产品设计能力（约 70 秒）

> 如果问的是产品设计，而不是实现，我准备了四层判断。
>
> **第一，指标怎么落到业务。** 只有越权和成本能直接换算；任务完成率、人效、投诉率都是代理指标，中间隔着五个断点：分布、人机、采纳、口径、长链路。所以我的门禁只用能换算的指标。
>
> **第二，成本结构。** 按我的用例分布，36% 的任务要人工确认。1000 次就是 360 次、6 小时人工；模型成本不到 1 块。所以规模化的杠杆在确认环节，不在 token 单价。
>
> **第三，谁来判。** 三轨：硬规则守底线、LLM 判语义、人评做校准。人评不全量，分层抽；而且必须先人判、再看机判，否则一致率是假的。
>
> **第四，怎么验收。** 评测产出证据，验收做决定。门禁三级、先硬后软、结论三态；豁免要双签、限时、封顶。

### 4.5 平台效果证据（约 40 秒）

> 效果这件事我分三级。
>
> **L1 能力证据**——平台能测出 Agent 的好坏。我有 86/20/24 条用例、10 个指标、trace，这一层是满的。
>
> **L2 归因证据**——去掉某个模块，会变差多少。我只做了一臂：围栏。同一批对抗用例、同一套 Mock，只切围栏开关。关掉以后，33 条里有 23 条真的执行了高危写操作，通过率从 25/25 掉到 6/25、从 8/8 掉到 1/8；打开是 0 条。45 条正常用例两种模式表现一致，没有误伤。
>
> **L3 业务效果**——用了平台事故率降多少。我没有，因为没有真实用户和线上流量。
>
> 所以我不拿 Agent 的 100% 说成平台的效果。那是被测对象的表现，不是平台的功劳。

## 5. 表达原则

### 5.1 必须主动说的七件事

1. **dev 的 100% 是 in-sample**：关键词和护栏是按 dev 失败设计的；
2. **held-out 只有 20 条**，其中 5 条做过探针，不算严格盲测；
3. **评测集是合成的**，不代表真实业务分布；
4. **judge 和 agent 同族**：都是 Qwen 7B，有自偏好风险，没做人工一致性校验；
5. **人评是 0**：24 条标了 `human_review` 的用例，实际仍由 LLM 判，`judge_coverage` 的 100% 有水分；
6. **"30 分钟接入"是拆开的**：技术接入 30 分钟，业务就绪约 5 人日；
7. **平台级效果只有一臂**：只有围栏做了消融，judge、上下文、Rubric 硬门槛、回归都还没有；L3 业务效果为 0。

> 主动说这七句，可信度会比"我的项目 100% 准确"高得多。
> 第 5、6、7 条尤其值钱——它们说明你自己在审自己的口径和证据等级，而不是等人来挑。

### 5.2 不要说的八件事

| 不要说 | 应该说 |
|---|---|
| "我做了一个通用 Agent 平台" | "我做了一个轻量、可运行的评测底座参考实现" |
| "我的项目 100% 准确" | "dev 100%，held-out 20/20，但样本小、有 in-sample 成分" |
| "我实现了工业级 Harness" | "我实现了任务级管控与 trace，不做容器隔离/多租户" |
| "我做了业务配置层（人设/技能/权限/审计）" | "只做了 metadata/围栏/trace 的零散对应，配置层是下一步" |
| "我用了公开语料" | "当前是 synthetic template，公开语料接入是下一步" |
| "三轨判定都做了" | "硬规则和机评在跑，人评是 0" |
| "30 分钟就能接一个 Agent" | "技术接入 30 分钟，业务就绪 5 人日" |
| "我的平台什么都有" | "机制层通了，配置层和管理层没通" |
| "我有完整的效果数据" | "只有围栏一臂消融：23/33 → 0；L3 业务效果没有" |

### 5.3 讲项目的顺序

```
问题 → 定位 → 架构 → 一个具体 case → 评测结果 → 局限
```

不要从技术栈开始讲。

## 7. 面试官可能记住的数字

| 数字 | 含义 |
|---|---|
| **86 / 20 / 24** | Sample A dev / held-out / Sample B 用例数 |
| **60% → 100%** | 规则版 held-out → LLM 版 held-out |
| **23.3% → 17.2%** | BGE 后的 context drift |
| **100%** | 越权拦截硬门槛 |
| **93.3%** | judge factuality（held-out） |
| **0.887** | LLM held-out Rubric 加权分 |
| **127** | 自动化测试数 |
| **2** | 覆盖的 Agent 范式 |
| **36%** | 需要人工确认的任务占比 |
| **12** | 失败模式数 |
| **0** | 人评条数 |
| **23 → 0** | 关掉围栏后，对抗用例中执行高危写入的条数 |

> 数字不要背多，记住这 12 个就够。前 8 个讲成绩，中间 3 个讲边界，最后 1 个讲平台效果。
