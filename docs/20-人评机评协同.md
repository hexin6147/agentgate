## 1. 为什么需要三轨

评测的判定项不是同一种东西，硬塞进一个 evaluator 一定出错：

| 判定项 | 性质 | 硬规则够吗 | LLM 够吗 |
|---|---|---|---|
| 围栏是否拦截 | 二值、可枚举 | ✅ 够 | 不需要 |
| 路由 / 行为类 | 可枚举，但有同义表达 | 🟡 覆盖不足 | ✅ 够 |
| 来源标注有无 | 可正则判断 | ✅ 够 | 不必要 |
| 事实是否被消息支撑 | 语义 | ❌ | ✅ 基本够 |
| 交接时机是否合理 | 主观、无唯一答案 | ❌ | 🟡 有偏差 |
| 是否违反业务红线 | 依赖业务定义 | 🟡 | 🟡 |
| 用户会不会觉得有用 | 无法离线判定 | ❌ | ❌ |

**设计原则**：

> 能用规则不用 judge，能用 judge 不用人；但**高危、主观、争议**三类必须有人。

## 2. 三类 Evaluator 的边界

| 维度 | 硬规则（rule） | LLM judge | 人评（human） |
|---|---|---|---|
| 输入 | case + trace 字段 | case + Agent 输出 | case + 输出 + trace + 判定指引 |
| 输出 | 二值 | 分数 / 布尔 / 违规列表 | 标签 + 备注 |
| 单条成本 | ≈ 0 | 一次模型调用 | 2–5 分钟 |
| 误差来源 | 规则覆盖不足 | 自偏好、提示敏感、同族偏差 | 主观、疲劳、锚定 |
| 可复现性 | 100% | 中（temperature=0 仍可能漂移） | 低 |
| 适用 | 硬门槛 | 语义质量 | 校准、争议、高危 |

> 当前实现：`judge.py` 输出 `factuality` / `source_support` / `handoff_correct` / `violations`；`evaluation.py` 用 `judge_type` 分流。
> 为什么用 case 级开关是错的、正确粒度是 metric 级路由，见 `22-Evaluator配置.md`。

## 3. 分工矩阵

| # | 判定项 | 默认 Evaluator | 人评介入条件 | 理由 |
|---|---|---|---|---|
| 1 | 围栏是否拦截 | 硬规则 | 仅争议（误拦申诉） | 二值、可枚举 |
| 2 | 行为类 / 路由 | 硬规则 + LLM | 两者不一致时 | 同义表达需要语义 |
| 3 | 事实性（factuality） | LLM judge | P0 类 100%，其余 10% 抽检 | 语义判定，机器够用但要校准 |
| 4 | 来源标注 | 硬规则（有无）+ LLM（对错） | 抽检 10% | 先判有无，再判对错 |
| 5 | 交接时机 | LLM judge | **100%** | 无唯一答案，人工复核一致率才是标准 |
| 6 | 越权 / 违规 | 硬规则 | 仅争议 | 一票否决，不允许 LLM 判 |
| 7 | 业务承诺（赔付、时效） | LLM judge | **100%** | 资金 / 合规后果 |
| 8 | 用户满意度 / 有用性 | 无 | 线上问卷 | 离线测不了 |

**一句话**：硬规则守底线，LLM 判语义，人评做校准和高危兜底——**三者不是替代关系，是分层**。

## 4. 抽样设计

### 4.1 全量机评 + 分层人评

| 层级 | 抽样比例 | 样本来源 | 目的 |
|---|---|---|---|
| P0 高危（越权、资金、承诺） | **100%** | 对抗集 + 业务红线类 | 兜底，不允许漏 |
| P1 主观（交接、结论） | 20% | 边界集 | 校准 judge |
| P2 常规（汇总、查询） | 10% | 正常集 | 抽检漂移 |
| 争议样本 | 100% | judge 判负或置信度低 | 仲裁 |

### 4.2 样本量

- 每一类至少 **20 条**才能粗算一致率；
- 30 条以下只做"发现问题"，不做统计结论；
- 全量 86 条全人评 = 4–7 小时，只在发布前做一次。

### 4.3 抽样的两个陷阱

| 陷阱 | 后果 | 避免方式 |
|---|---|---|
| 只抽 judge 判负的 | 高估 judge 精度 | 正负样本都抽 |
| 只抽容易的 | 一致率虚高 | 按难度分层抽 |

## 5. 一致性怎么算

### 5.1 三个指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 人机一致率 | 人标签 = judge 标签的 case / 总 case | judge 能不能替代人 |
| 双人一致率 | 两个标注者一致的 case / 总 case | 判定标准是否清晰 |
| Cohen's κ | 扣除偶然一致后的吻合度 | 更严格的一致性 |

### 5.2 阈值与动作

| κ | 解释 | 动作 |
|---|---|---|
| > 0.8 | 好 | judge 可用于全量 |
| 0.6–0.8 | 中 | judge 可用于趋势，P0 仍需人评 |
| < 0.6 | 差 | **先改定义，不是改标注者** |

> 关键原则：**一致性低，先怀疑判定标准写得不清楚，再怀疑标注者。**
> 如果两个人对"这条算不算越权"理解不同，那不是标注问题，是 Rubric 定义问题。

### 5.3 分歧的处理顺序

```
1. 看定义：Rubric 里这一项有没有可判定的描述？
2. 看样本：是不是 case 本身有歧义？
3. 看标注者：前两步都没问题，才做标注者校准
```

## 6. 争议仲裁

| 环节 | 谁 | 产出 |
|---|---|---|
| 提出分歧 | 任一标注者 | 争议记录（case + 两方理由） |
| 裁决 | 业务方 + 评测负责人 | 终判 + 理由 |
| 回写 | 评测负责人 | 更新 Rubric 定义 / 判定指引 |
| 沉淀 | 评测负责人 | 争议 case 进入回归集 |

**争议是资产**：每一个分歧都暴露了一处定义模糊。**没有争议记录的评测体系，通常是标准写得太粗。**

## 7. 一条人评任务长什么样

### 7.1 任务卡必须包含

| 区块 | 内容 | 为什么 |
|---|---|---|
| 输入 | query + 上下文消息 | 判断依据 |
| 输出 | Agent 的完整回复 | 判定对象 |
| trace | 路由、筛选、工具、围栏 | 判断"为什么这么做" |
| 待判项 | 明确到可点选，如"交接时机：正确 / 过早 / 过晚" | 避免自由发挥 |
| 备注 | 自由文本 | 收集定义模糊点 |
| **judge 结论** | **默认隐藏** | 防锚定 |

### 7.2 关键设计：先人判，后看机判

```
第一轮：只看 case + 输出 + trace → 独立打标
第二轮：展开 judge 结论 → 对比
第三轮：分歧 → 进入仲裁
```

> 如果先看 judge 结论再打标，一致率会虚高 10–20 个百分点——这不是 judge 准，是人被锚定了。

### 7.3 快捷标签示例

```
交接时机： [正确] [过早] [过晚] [不该交接]
事实性：   [全部有据] [部分无据] [编造] [无事实陈述]
来源标注： [齐全] [部分] [缺失] [标错]
违规：     [无] [有：______]
```

## 8. 人评的成本与配额

| 项 | 数值 |
|---|---|
| 单条人评耗时 | 2–5 分钟 |
| 86 条全量 | 4–7 小时 |
| 30 条抽检 | 1–2.5 小时 |
| 双人双盲 | ×2 |

**配额原则**：

1. 人评是稀缺资源，优先给**判不了的**和**判错的代价最大的**；
2. 判得了的（围栏、路由）不要人评，浪费；
3. judge 置信度低的样本优先（主动学习思路）；
4. 人评结果要能**回写 Rubric**，否则只是做了一次性检查。

## 9. 现状与缺口

| 项 | 状态 | 说明 |
|---|---|---|
| 三轨定义 | ✅ | `08` §? 已定义 rule / judge / human |
| 硬规则 | ✅ | 37 条 `hard_rule`，全自动 |
| LLM judge | ✅ | 25 条 `llm_judge`，`judge.py` 已实现 |
| **人评** | ❌ | **0 条** |
| `human_review` 用例 | ⚠️ | 24 条，**实际由 LLM judge 判定**（`evaluation.py:91`） |
| `judge_coverage` 口径 | ⚠️ | 把 `human_review` 也算进覆盖率，显示 100% 但人评为 0 |
| 人机一致率 | ❌ | 无数据 |
| 双人一致率 / κ | ❌ | 无数据 |
| 仲裁流程 | ❌ | 无 |

### 9.1 必须主动说的一句

> "我有 24 条用例标了 `human_review`，但现在实际是 LLM 在判。所以准确说，我的三轨只跑了两轨。`judge_coverage` 显示 100%，但这个口径把'有人判过'和'该由人判的由人判了'混在一起了，需要拆开。"

**这句话比"我做了人评"可信得多。**

### 9.2 口径修正建议

把 `judge_coverage` 拆成两个：

| 指标 | 定义 |
|---|---|
| `machine_coverage` | 被任一 evaluator 判过的 case / 应判 case |
| `human_coverage` | 被人评过的 case / 应人评 case（P0 100% + 抽检） |

## 10. 最小可执行方案（30 条）

### 10.1 选样

| 组 | 数量 | 来源 |
|---|---|---|
| A 组 | 10 | `llm_judge` 用例，正负各半 |
| B 组 | 10 | `human_review` 用例 |
| C 组 | 10 | judge 判负或置信度低的争议样本 |

### 10.2 执行

1. 两人独立标注，不看 judge 结论；
2. 计算人机一致率、双人一致率、κ；
3. 分歧进入仲裁，记录定义模糊点；
4. 产出 `09i-评测报告-人评一致性.md`。

### 10.3 预期产出

| 产出 | 用途 |
|---|---|
| 人机一致率 | 判断 judge 能否用于全量 |
| 双人 κ | 判断判定标准是否清晰 |
| 争议清单 | 回写 Rubric |
| 修正后的定义 | 下一轮评测的输入 |

> 时间成本：标注 2 人 × 1.5 小时 + 分析 2 小时。

## 11. 面试怎么讲（60 秒）

> "评测我分三轨：硬规则、LLM judge、人评。
>
> 但我要先说清楚：我现在只有两轨在跑。24 条标了 human_review 的用例，实际还是 LLM 判的，人评是 0 条。所以 `judge_coverage` 那个 100% 是有水分的。
>
> 人评的作用不是比机器准，是三件事：校准 judge、裁决争议、兜底高危。所以我不全量人评，我分层抽——P0 全量、P1 抽 20%、P2 抽 10%。
>
> 而且必须**先人判、后看机判**。先看机判再标，一致率能虚高十几个点，那不是 judge 准，是人被锚定了。
>
> 我的 judge 和 Agent 是同族模型，有自偏好风险。这个风险不靠换模型解决，靠人评校准。"
