## 1. 定位与竞品

### Q1. 这和 Claude Tag / 豆包工作伙伴有什么区别？

**结论**：它们不是竞品，是需求侧证据；真正的同类是 LangSmith 类工具和大厂评测平台。

**依据**：
1. Claude Tag / 豆包是 Agent 产品，开放业务配置层、封闭执行链路——说明企业已在部署 Agent，但外部拿不到 trace、不能回归；
2. 同类竞品是 LangSmith / LangFuse（强在观测与评测）和大厂平台（全栈但重、面向采购）；
3. 我的差异是把执行前围栏与回归门禁接在同一条 trace 上。

**保留**：成品在交互和开箱即用上远强于我。**类别不能错**——拿 Agent 产品当竞品，面试官会认为你没想清楚自己在做哪一层。

### Q2. 为什么不做成一个 Agent，而要做平台？

**结论**：单 Agent 是应用，平台能评不同范式，价值可复用。

**依据**：
1. 单 Agent 的面试叙事天花板是"一个 IM 机器人"；
2. 平台换的只是 Adapter、工具、Rubric，Harness 和评测脚本不动；
3. 我用 Sample A（协作）+ Sample B（工单）证明了这一点。

### Q3. 和火山 / 美团 / 腾讯的评测平台比，凭什么？

**结论**：不凭什么"更强"，凭更轻、可运行、可解释、双范式。

**依据**：
1. 它们面向企业采购，有容器沙箱、多租户、在线评测；我是单机 POC；
2. 我的价值是验证核心产品逻辑，不是能力对齐；
3. 我明确知道自己的简化点。

### Q4. 两个示例 Agent 是不是两个项目？

**结论**：不是。一个平台，两个被测样本。

**依据**：
1. Sample A/B 都实现同一个 Adapter；
2. 都跑同一套 Harness、LangGraph、评测脚本；
3. 换的是工具、红线、Rubric 和用例。

### Q5. 为什么选研发协作 + 售后工单？

**结论**：两类范式差异最大，最能验证通用性。

**依据**：
1. 研发协作：动态交接、多轮、无唯一答案；
2. 售后工单：静态红线、结果可判定、高危审批；
3. 如果平台只能评一种，说明它是为场景定制的。

### Q6. 为什么不用 LangSmith / LangFuse / 现成评测平台？

**结论**：它们是观测/追踪工具，不是"业务行为门禁"。

**依据**：
1. 它们擅长 trace 和 LLM 调用观测，不内置 B1–B6/R1–R6 这类业务行为分类；
2. 我需要"在工具执行前拦截"的围栏，不是事后看 trace；
3. 我的 Harness 与围栏是业务管控层，和观测工具互补。

### Q7. 这个项目的业务价值 / ROI 是什么？

**结论**：降低 Agent 上线后的行为风险与回归成本。

**依据**：
1. 越权/误执行是 B 端最贵的风险；
2. 回归门禁能防止"修 A 坏 B"；
3. 我没有真实业务流量，所以只讲机制，不编 ROI 数字。

**保留**：真实 ROI 需要企业数据和试点才能算。

## 2. 技术架构

### Q8. LangGraph 和 Harness 是什么关系？

**结论**：LangGraph 是 Agent 内层编排，Harness 是外层运行时管控。

**依据**：
1. LangGraph 管节点流转、interrupt、checkpointer；
2. Harness 管 run_id、超时、重试、异常隔离、trace 落盘、评测接口；
3. 两者不是一回事，不能说"LangGraph 就是 Harness"。

### Q9. 为什么用 LLM 又用规则？

**结论**：LLM 负责理解，规则负责允许与终止。

**依据**：
1. 同义表达、上下文依赖，规则覆盖不了长尾；
2. 越权、确认、拒绝、终止不能交给模型；
3. 我的规则还做三类一致性护栏：写操作、模糊查询、汇总一致性。

### Q10. 意图分类为什么不用纯 LLM？

**结论**：用了 LLM，但不是纯 LLM。

**依据**：
1. LLM 主分类，置信度低/输出非法/API 异常时回退规则；
2. 高风险写意图和模糊查询有确定性护栏；
3. 这样既保留泛化，又保留可解释和可复现。

### Q11. 为什么用 BGE，不用向量数据库？

**结论**：POC 规模不需要向量库。

**依据**：
1. 每个 case 只有几条到几十条消息，内存 cosine 足够；
2. BGE 通过本地 Ollama 调用，768 维；
3. 真要上规模，再换 FAISS/pgvector，接口不变。

### Q12. Mock 工具是不是不真实？

**结论**：Mock 的是工具契约和围栏，不是系统集成。

**依据**：
1. 评测对象是"Agent 会不会越权、参数是否合规、交接是否合理"；
2. 同输入同输出，回归才可复现；
3. Mock 模拟正常、业务错误、系统故障三类响应。

### Q13. trace 怎么保证完整？

**结论**：trace 是评测的唯一输入，缺字段直接判失败。

**依据**：
1. 每个节点、工具调用、围栏结果都写 trace；
2. 评测只依赖 trace，不解析自然语言日志；
3. 平台级硬门槛：trace 完整率 100%。

### Q14. 为什么只做单机 / CLI？

**结论**：POC 的成本边界。

**依据**：
1. 单机 + SQLite 足够验证产品逻辑；
2. 不做多租户、并发调度、容器隔离；
3. 这些是生产化增量，不是当前要证明的东西。

### Q15. 为什么不接真实 Jira / GitLab / CI？

**结论**：真实系统会引入权限、副作用和不可复现。

**依据**：
1. 变更类工具一旦真实执行，可能污染测试环境；
2. 项目目标是验证围栏逻辑，不是集成能力；
3. 接口层做了适配器，未来可替换真实实现。

## 3. 评测体系

### Q16. 指标怎么定的？是不是拍脑袋？

**结论**：分五类，不是拍一个百分比。

**依据**：
1. 硬门槛：越权 100%、trace 100%、可复现 100%；
2. 基线相对：上下文召回、规则准确率，先测基线再定；
3. 业务推导：误拦截、交接准确率；
4. 工程约束：接入耗时、步数；
5. 待校准：行为类百分比，G4 后校准。

### Q17. 100% 是不是过拟合？

**结论**：dev 是，held-out 不是。

**依据**：
1. dev 的关键词和护栏是按失败设计的；
2. 规则版 held-out 只有 60%，证明同集 100% 不可泛化；
3. LLM 版 held-out 20/20，但样本小、有 5 条探针。

### Q18. held-out 只有 20 条，可信吗？

**结论**：能证明方向，不能证明统计显著性。

**依据**：
1. 20 条足以暴露规则版的泛化问题（60%）；
2. 不足以给 LLM 版下"线上可用"的结论；
3. 下一步是 held-out2 + 真实数据。

### Q19. 越权拦截 100% 怎么保证？

**结论**：硬门槛 + 工具层围栏，不靠模型自觉。

**依据**：
1. F1–F5 / T1/T2/T5 在工具执行前校验；
2. 未通过就不执行，并写 trace；
3. 评测硬门槛：任意漏拦即整体失败；
4. **消融验证**：关掉围栏后，33 条对抗用例中 23 条真的执行了高危写操作；打开后 0 条。见 `09i`。

### Q20. 误拦截率怎么算？

**结论**：合法调用被围栏错误拦截的比例。

**依据**：
1. 对比正常用例的 expected route；
2. dev 规则版 32.4% → 修复后 0%；LLM 版 0%；
3. 阈值 ≤10%，但样本小，仍需真实数据校准。

### Q21. LLM-as-judge 怎么防漂移？

**结论**：做了最小实现，但防漂移还没完全落地。

**依据**：
1. `judge.py` + `--judge llm`，输出 factuality / source_support / handoff / violations；
2. held-out 上 factuality 93.3%，抓到 1 条硬规则漏掉的"纳入闲聊"；
3. 但 agent 和 judge 都是 `qwen2.5:7b-instruct`，有自偏好风险；
4. 更关键的是：24 条标了 `human_review` 的用例，**实际也是这个 judge 判的**，所以"人评"目前是 0；
5. 下一步按 30 条双盲算人机一致率与 κ；κ<0.6 先改判定定义，不是调阈值。

**主动承认**：同族、未人工校验、"人评"名存实亡，是当前 judge 的三个明确局限。

### Q22. 行为评测和文本评测的区别？

**结论**：行为评测看"做了什么/没做什么"，文本评测看"写得好不好"。

**依据**：
1. 行为：越权、路由、交接、工具参数；
2. 文本：事实忠实度、来源标注；
3. 我的硬门槛全部是行为指标。

### Q23. 数据从哪来？合规吗？

**结论**：当前是 synthetic template + 2 条手写；公开语料接入是下一步。

**依据**：
1. 86/20/24 条由生成器按协作/工单场景模板生成，`source.origin` 为 `synthetic_template` / `synthetic_ticket` / `heldout_manual`；
2. GH Archive、GitHub Issues、Public Jira、VOID 是计划/参考，**尚未下载**，`source.url` 为空；
3. 已做脱敏改写与来源字段，但"公开语料覆盖"目前不成立。

**主动承认**：这是当前数据侧最大的不足。

### Q24. Rubric 加权评分做了吗？

**结论**：做了。

**依据**：
1. `src/agentgate/rubric.py`：加载/校验 YAML、按权重算分、执行硬门槛；
2. 结果：规则 dev 0.882 通过；规则 held-out 0.621 被硬门槛拦下；LLM+BGE+judge 0.887；Sample B 1.000；
3. 缺失指标会重归一化，报告 `missing_metrics`。

**主动承认**：restricted 的 `answer_correctness` 还没定义，权重被重归一化；没有 per-case Rubric 与版本管理。

### Q25. 回归门禁怎么设计？

**结论**：硬门槛阻断 + 指标回归检查。

**依据**：
1. 越权拦截 <100%、P0 对抗失败、trace 不完整、可复现失败 → 阻断；
2. 行为准确率下降 >5pp → 阻断；
3. 新增失败 >5 条 → 人工评估。

## 4. 人机协同

### Q26. 什么时候自动、什么时候转人工？

**结论**：按 B1–B6 行为类别，不按业务名字。

**依据**：
1. B1/B2 自动；B3 确认；B4 围栏+确认；B5 拒绝；B6 追问；
2. 冲突时 R4 > R2 > R5 > R3 > R1；
3. 规则优先，LLM 只能辅助分类。

### Q27. 规则冲突怎么办？

**结论**：取最高风险级。

**依据**：
1. R4 拒绝 > R2 确认 > R5 确认+围栏 > R3 追问 > R1 自动；
2. 冲突结果写入 trace 的 `rule_hit` 与 `reason`；
3. 无法仲裁时默认转人工。

### Q28. 人工确认超时怎么办？

**结论**：设计是 30min 标记过期、任务终止；**当前代码未实现**。

**依据**：
1. `06` §7 定义了 `EXPIRED`、不自动放行、通知发起人；
2. 但 pending 仅存内存，无超时、无 `event_id` 幂等、审批结果不回写 trace；
3. Streamlit 兜底也未做。

**主动承认**：这是文档有、代码没有的典型项，不能说是已实现。

## 5. 生产与个人

### Q29. 上线还差什么？

**结论**：权限、多租户、真实系统、成本、并发、真实数据评测。

**依据**：
1. 当前单机、单租户、Mock 工具；
2. 没有企业身份、审计、配额、限流；
3. 没有真实流量和线上回归。

### Q30. 如果给你 3 个月，先补什么？

**结论**：先补评测可信度，再补管理外壳，最后才是生产化。

**依据**：
1. 人评一致性：30 条双盲，算 κ，校准 judge；
2. 真实脱敏数据 + held-out2，替换 synthetic；
3. 长链路：多步用例 + 步级/任务级/恢复级指标；
4. 成本与延迟采集：`usage`、`latency_ms`、预算线；
5. 管理层：注册、版本、CaseSet 冻结；
6. 最后才是多租户、权限、Streamlit。

**注意**：Rubric 加权已在 09h 完成，不在这份清单里。

### Q31. 4 个缺口都实现了吗？

**结论**：**机制层四个都通了，配置层和管理层没通**。

**依据**：
1. 机制层：P1 围栏+确认、P2 trace、P3 跑+比对、P4 Adapter+双范式，都跑通过；
2. 配置层：围栏写死在 `tools.py`，Evaluator 选择是 case 级开关，不是指标级路由；
3. 管理层：无注册表、无 AgentVersion、无 CaseSet 冻结；
4. 资源层：token/延迟/成本未采集。

**主动承认**：所以准确说法是"机制成立、管理缺失"，不是"四个各做了一半"。

### Q32. 每来一个 Agent 都要重写 Adapter 吗？

**结论**：比"写两个方法"要多——**要写一组钩子，而且接第三个 Agent 还要改平台代码**。

**依据**：
1. 最小契约是 `metadata()` + `run()`；
2. 但用 `LangGraphAgent` 包装时，平台会调用业务的 `classifier.match`、`_filter`、`_plan`、`_fence_message`、`_summarize`；
3. 注册在 `factory.py` 里是 `if kind == "ticket"`，接第三个必须改平台、重新部署；
4. 正确做法是定义正式 Protocol + entry point 注册，当前没做。

**主动承认**：这是抽象泄漏，也是"接入 30 分钟"做不到的根因。

## 6. 产品设计深挖

> 这一组不是考"你写了什么代码"，是考"你作为 PM 判断得对不对"。
> 每题都能落到一份文档：`17`–`25`。

### Q33. 这个平台到底解决了什么？

**结论**：让 Agent **可被验收**，不是让 Agent 变强。

**依据**：
1. 一条闭环走通了：接入 → 跑 → trace → 归因 → 修 → 回归 → 门禁；
2. 机制层四个缺口都通了：管控、观测、回归、复用；
3. 它不负责多步编排、模型能力、业务 SOP——那是 Agent 和业务方的事。

**主动承认**：配置层（可配围栏/Evaluator）和管理层（注册/版本/CaseSet）没通。

### Q34. 离线指标涨了，业务指标一定涨吗？

**结论**：不一定。只有极少数能直接换算。

**依据**：
1. 能直接换算的只有越权事故（`fence_interception`）和成本（token 加总）；
2. 任务完成率、一次解决率、人效、投诉率都只是**代理指标**；
3. 中间隔着五个断点：分布、人机、采纳、口径、长链路。

**主动承认**：所以我的门禁只用能换算的指标，代理指标只写进报告做趋势。

### Q35. 跑一次多少钱？规模化贵不贵？

**结论**：成本大头是人的时间，不是 token。

**依据**：
1. 用例分布里 B3+B4 = 36%，会触发人工确认；
2. 1000 次任务 = 360 次确认 ≈ 6 小时人工；模型成本不到 1 块；
3. 所以规模化的杠杆是降误拦、提确认接受率，不是谈 token 折扣。

**主动承认**：`LLMClient` 现在丢弃 `response.usage`，所以这是结构推算，不是账单。

### Q36. 人评和机评怎么分工？

**结论**：硬规则守底线、LLM 判语义、人评做校准；人评不全量，分层抽。

**依据**：
1. P0 高危 100% 人评，P1 抽 20%，P2 抽 10%；
2. 必须**先人判、后看机判**，否则一致率虚高 10–20pp；
3. κ > 0.8 可全量机评，0.6–0.8 只做趋势，< 0.6 先改定义。

**主动承认**：当前人评 0 条，一致性数据为空。

### Q37. `judge_coverage` 100% 可信吗？

**结论**：不可信，这个口径把两件事混了。

**依据**：
1. 24 条标 `human_review` 的用例，`evaluation.py` 里仍走 LLM judge；
2. 所以 100% 表示"有人判过"，不表示"该由人判的由人判了"；
3. 应拆成 `machine_coverage` 和 `human_coverage`。

**主动承认**：这是我自己发现的指标口径缺陷。

### Q38. 评测集怎么管？怎么防在测试集上调参？

**结论**：四层 + 四道闸；现在做到两道。

**依据**：
1. 四层：调参集 / 留出集 / 回归集 / 回流集；
2. 四道闸：生成隔离、使用隔离、记录隔离、探针标记；
3. dev 与 held-out 的 query **零重叠**，生成隔离做到了。

**主动承认**：使用隔离和记录隔离靠自觉，探针标记没实现——`09c` 里 5 条看过。

### Q39. 用例覆盖够吗？

**结论**：不够，有三个具体缺口。

**依据**：
1. Sample A 的 normal/boundary/adversarial **完全由行为类决定**，不是独立维度；
2. Sample B 没有 B2（汇总类）；
3. B5 超边界只有 9 条，是风险最高、样本最少的一类。

**主动承认**：扩样优先级是 B5 → Sample B 的 B2 → B3/B4 的 normal。

### Q40. 评测器怎么选？两个结论冲突听谁的？

**结论**：应该是**指标级路由**；冲突时硬门槛单向否决。

**依据**：
1. 现在是 case 级 `judge_type`，是开关不是路由；
2. rule 判失败、judge 判通过 → 以 rule 为准；
3. judge 判失败、rule 判通过 → 记 `judge_violation` 进争议队列。

**主动承认**：指标级配置只设计了，没实现。

### Q41. 没判的 case 算通过吗？

**结论**：不算。未判必须单列。

**依据**：
1. `pass_rate = 通过 / (通过 + 失败)`，分母不含未判；
2. 否则让 judge 挂掉就能提高通过率；
3. 报告必须单列未判数与覆盖率。

**主动承认**：当前 `judge_ok=None` 会被计数，但报告没有单列未判数。

### Q42. 出错了怎么归因？

**结论**：沿 trace 找**第一个**异常节点，不是看最后错在哪。

**依据**：
1. 27 条 badcase，25 条同一根因（分类器 LCS 匹配）；
2. 其中 5 条表现为"漏拦"，只修围栏永远修不好；
3. 整理成 12 类失败模式，每类有 trace 信号和责任方。

**主动承认**：12 类里 7 类有数据，长链路和成本两类完全没测。

### Q43. 长链路怎么评？

**结论**：要三层，我现在一层都不完整。

**依据**：
1. 步级成功率、任务级完成率、恢复率；
2. 不能用 `0.9^6` 算——错误会被 verify 拦住，也会传导放大；
3. 当前是单次工具调用，没有多步用例。

**主动承认**：长任务**编排**不是平台职责；长任务**评测**是，但没做。

### Q44. 谁批准上线？不通过怎么办？

**结论**：评测出证据，业务和平台双签；结论三态。

**依据**：
1. Go / Conditional Go / No-Go，不是二元；
2. 豁免要双签、≤30 天、带补偿措施、同一项连续 ≤2 次；
3. 越权、红线、trace、可复现四项**不可豁免**。

**主动承认**：判定逻辑有，签字和豁免流程没实现。

### Q45. "30 分钟接入"是真的吗？

**结论**：拆成两个指标才成立。

**依据**：
1. 技术接入（写 Adapter、跑通第一个 case）≤ 30 分钟；
2. 业务就绪（用例 + Rubric + 围栏 + 门禁）≈ 5 人日；
3. 而且现在连技术接入都做不到——注册要改 `factory.py`。

**主动承认**：把两个混成一个数字，就是承诺失真。
