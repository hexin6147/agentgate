### 0.4 核心结论（30 秒版）

> 按当前用例分布，**36% 的任务需要人工确认**。1000 次任务 = 360 次确认 ≈ 6 小时人工；模型调用成本不到 1 块钱。
> 所以规模化的瓶颈在**确认环节**，不在 token 单价。
> 延迟同理：模型 3–6 秒，人的响应 1–30 分钟——**人机协同的产品延迟由人决定**。
> 另一个必须承认的事实：POC 用例的平均上下文只有 32 个字，真实群聊会大一个量级，所以本文的成本模型是**参数化的**，不拿现在的数字外推。

- 不承诺任何单价，价格必须按当期报价替换；
- 不覆盖并发、缓存、批处理带来的折扣；

## 1. 为什么 PM 要管这件事

成本不是财务问题，是**产品边界问题**。它决定三件事：

1. **哪些能力默认开**：BGE 筛选每次多一次 embedding，但只降 6pp 无关混入——值不值？
2. **哪些能力只在离线跑**：LLM judge 质量最高，但每 case 多一次调用，能不能进线上链路？
3. **规模化的天花板在哪**：是模型太贵，还是人工确认太贵？

JD 对这件事的要求很直接：

| JD | 原话 |
|---|---|
| #13 | 整个岗位在解决"任务开始前预估消耗多少 Token" |
| #28 | "知道模型延迟、失败率、成本意味着什么，能把'模型在这里不行'翻译成可落地的工程约束" |
| #38 | "结合任务成功率、问题解决率、转人工率、准确性、时延、成本及用户满意度定位问题" |
| #40 | "成本核定""经营分析" |

## 2. 一次任务调用几次模型

| 路径 | 意图分类 | 上下文筛选 | 摘要 | judge | 合计 |
|---|---|---|---|---|---|
| 规则版 | 0 | 0 | 0 | 0 | **0** |
| LLM 版（关键词筛选） | 1 | 0 | 0–1（仅 B2） | 0 | **1–2** |
| LLM + BGE | 1 | 1（批量 embedding） | 0–1（仅 B2） | 0 | **2–3** |
| 离线评测（+judge） | — | — | — | 0–1（仅 `llm_judge`） | **+1** |

> 依据：`llm.py` 的 `LLMIntentClassifier.match`、`LLMSummarizer.summarize`；`context.py` 的 `embed_fn([query] + messages)`；`judge.py` 的 `judge()`。
> 摘要只在 `behavior == B2` 时触发（`adapter.py:276`）；judge 只对 `judge_type == llm_judge` 的用例触发。

## 3. 输入规模：先看真实数据

对 `eval/dataset/` 与 `eval/dataset_ticket/` 做了字符统计：

| 数据集 | 用例数 | 平均上下文（汉字） | 最大上下文 | 平均 query |
|---|---|---|---|---|
| Sample A | 86 | **32.0** | 45 | 7.4 |
| Sample B | 24 | **9.7** | 21 | 9.7 |

**这个数字很重要**：POC 的上下文极短，所以成本几乎全由**提示词模板**决定，而不是业务文本。真实研发群聊一天几百条消息，真实工单有几百字描述——规模会大一个量级。

**结论**：成本模型必须参数化。任何拿"平均 32 字"算出来的绝对数字，都不能对外说。

## 4. 单任务成本公式

```
单任务成本 =
    C_cls
  + [is_B2]      × C_sum
  + [use_BGE]    × C_emb
  + [offline]    × C_judge

C_x = P_in × T_in(x) + P_out × T_out(x)
```

### 4.1 Token 估算（基于现有提示词）

| 调用 | 输入 token | 输出 token | 说明 |
|---|---|---|---|
| 意图分类 | ≈ 300 | ≈ 40 | system 61 字 + 6 条 intent 描述 + query |
| 摘要 | ≈ 80 + 上下文 | ≈ 100 | 只对 B2；上下文字数 × 0.65 |
| BGE 筛选 | ≈ 10 × (消息数+1) | 0 | 批量调用，平均 3.3 条消息 |
| LLM judge | ≈ 500 | ≈ 120 | 只对 `llm_judge`，仅离线 |

> 换算假设：中文 ≈ **0.65 token / 字**。该系数随分词器变化，需用实际响应里的 `usage` 校准。

### 4.2 单价参数（示例，**必须替换为当期报价**）

| 部署形态 | 输入单价 | 输出单价 | 备注 |
|---|---|---|---|
| 本地 Ollama 7B | 0（机器摊销） | 0 | 电费与硬件另算 |
| 国内 API 轻量模型 | 示例值 | 示例值 | 按量计费 |
| 国际 API 中档模型 | 示例值 | 示例值 | 通常按美元计 |

> 本文不写具体价格，因为价格变动快、且不同渠道差异大。**面试时只说结构，不说单价**；被追问就答"按当期报价代入公式"。

## 5. 三种部署形态

| 形态 | 边际成本 | 延迟 | 数据合规 | 适合 |
|---|---|---|---|---|
| 本地 Ollama 7B | ≈ 0 | 2–6 s | 数据不出内网 | POC、内网、隐私敏感 |
| 国内 API | 低 | 1–3 s | 需评估 | 中小规模生产 |
| 国际 API | 高 | 1–2 s | 需评估 | 质量优先的场景 |

**选择原则**：先看合规（数据能不能出内网），再看延迟（用户能不能等），最后才看单价。**单价永远不是第一约束。**

---

## 6. 延迟分解

| 环节 | 典型范围 | 决定因素 |
|---|---|---|
| 意图分类（1 次 LLM） | 0.8–2.5 s | 输出约 40 token |
| BGE 筛选（1 次批量 embedding） | 0.05–0.3 s | 消息条数 |
| 摘要（1 次 LLM，仅 B2） | 1.5–4 s | 输出长度 |
| 工具调用（Mock） | < 10 ms | 本地 |
| 人工确认 | **1–30 min** | **人的响应** |
| 端到端（无需确认） | 2.5–7 s | 模型链路 |
| 端到端（需确认） | **分钟级** | 人 |

**关键判断**：

> 模型链路已经把延迟压到秒级；真正决定用户体验的是**确认环节**。
> 所以"让 Agent 更快"的产品动作不是换更快的模型，是**减少不必要的确认**。

## 7. 成本-效果曲线

| 配置 | 增量调用 | 增量成本 | 效果 | 结论 |
|---|---|---|---|---|
| 规则版 | 0 | 0 | held-out 60% | 基线 |
| + LLM 分类 | 1 / 任务 | 小 | held-out 60% → 100% | **必开** |
| + LLM 摘要 | 0.29 / 任务 | 小 | 摘要可读、可标来源 | 按需（仅 B2） |
| + BGE 筛选 | 1 / 任务 | 极小 | 无关混入 −6.1pp，召回 −4.4pp | **默认开** |
| + LLM judge | 0.29 / 任务（离线） | 中 | 质量可测 | **只在离线** |

> 数据来源：`09b`（规则版 60%）、`09c`（LLM 版 100%）、`09d`（BGE 前后对比）、`09g`（judge）。

**默认开关的判断标准**：

| 能力 | 默认 | 理由 |
|---|---|---|
| LLM 分类 | 必开 | 决定正确率，是质变 |
| BGE | 默认开 | 成本极低，收益 6pp |
| LLM 摘要 | 按需（仅 B2） | 只影响可读性，不影响正确性 |
| LLM judge | 只在离线 | 不进线上链路，不增加用户等待 |
| 规则兜底 | 永远保留 | LLM 失败时的降级路径 |

## 8. 规模化推演：成本大头是人

### 8.1 用例分布（实测）

| 行为类 | 数量 | 占比 | 是否需确认 |
|---|---|---|---|
| B1 读取 | 12 | 14% | 否 |
| B2 汇总 | 25 | 29% | 否 |
| B3 结论 | 12 | 14% | **是** |
| B4 写入 | 19 | 22% | **是** |
| B5 超边界 | 6 | 7% | 否（拒绝） |
| B6 信息不足 | 12 | 14% | 否（追问） |

> B3 + B4 = 31 / 86 = **36%** 的任务会触发人工确认。

### 8.2 规模推演

假设：每次确认 1 分钟、人工成本 ¥50/小时、模型单价按示例参数。

| 日任务量 | 模型调用 | 人工确认次数 | 模型成本 | 人工成本 | 谁主导 |
|---|---|---|---|---|---|
| 100 | ≈ 130 | 36 | 忽略不计 | ≈ 0.6 小时 | **人** |
| 1,000 | ≈ 1,300 | 360 | 忽略不计 | 6 小时 | **人** |
| 10,000 | ≈ 13,000 | 3,600 | 个位数 | 60 小时 ≈ 7.5 人日 | **人** |

**结论**：

> 在 36% 确认率下，**人工成本比模型成本高 2–3 个数量级**。
> 规模化能不能成立，取决于能不能把确认率降下来，而不是能不能拿到更低的 token 单价。

### 8.3 产品动作（按 ROI 排序）

| # | 动作 | 影响 | 对应指标 |
|---|---|---|---|
| 1 | 降低误拦 | 减少不必要的确认 | `false_block_rate` |
| 2 | 提升确认接受率 | 一次就对，减少反复 | 确认接受率 |
| 3 | 分级确认 | 低风险批量确认，高风险逐条 | 确认率 |
| 4 | 收紧确认范围 | 只对 B4 强制确认，B3 改为"建议 + 人工采纳" | 确认率 |
| 5 | 降低 token 单价 | 影响最小 | 单任务成本 |

> 第 5 项是很多人第一反应要做的，但按这个模型它排最后。

## 9. 预算与门禁

| 预算项 | 建议阈值 | 超了怎么办 |
|---|---|---|
| 单任务输入 token | ≤ 2,000 | 截断上下文，记录裁剪策略 |
| 单任务端到端延迟 | ≤ 10 s | 摘要降级为规则拼接 |
| 单 run judge 调用 | 可配置上限 | 超限跳过 judge，报告标注"未判" |
| 日预算 | 按业务定 | 告警 + 限流，不直接熔断 |

对应 `05-1-风险准入判定.md` §7 第 9 项"成本在预算内"——**这一项目前无法自动检查**，因为没采集 usage。

## 11. 最小实现清单（下一步）

1. `LLMClient.chat` 读取 `response.usage`，通过回调或返回值带回；
2. `TraceRecorder.record` 增加 `latency_ms` 与 `tokens` 字段；
3. `evaluation.aggregate` 聚合 `total_tokens`、`avg_latency_ms`、`estimated_cost`；
4. `score.py` 报告输出成本与延迟列；
5. 测试：mock 一个带 `usage` 的响应，断言聚合结果；
6. 用真实响应校准"0.65 token / 字"的换算系数。

## 12. 面试怎么讲（60 秒）

> "我先算的不是 token，是人的时间。
>
> 按我的用例分布，36% 的任务需要人工确认。1000 次任务就是 360 次确认，按 1 分钟算 6 小时；模型调用成本不到 1 块钱。
> 所以规模化的瓶颈在确认环节，不在单价。这就是为什么我把误拦率和确认接受率看得比 token 单价重——降 1pp 误拦，比谈 10% 折扣值钱。
>
> 另外我得说清楚：我的 POC 上下文平均只有 32 个字，真实群聊会大一个量级。所以成本模型是参数化的，我不拿现在的数字外推。"
