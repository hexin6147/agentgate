## 0. 文档导读

### 0.1 这份文档的目的

回答三个问题：

1. 这个 Agent 嵌在**谁的什么工作**里？
2. 它卡在**哪个具体动作**上，而不是"哪个抽象瓶颈"？
3. 没有 AgentGate 的时候，他们**现在怎么凑合**？

### 0.2 读者与使用方式

| 读者 | 怎么用 |
|---|---|
| 产品经理 | 判断痛点是否成立；访谈前的预热材料 |
| 评测设计 | 从链路推出用例类型、判定点、交接点 |
| 面试 | 用"角色—动作—失败后果"讲业务，而不是讲架构 |

### 0.3 本文包含什么

```
§1 为什么单独写这一篇
§2 Sample A：研发协作 Agent 的业务链路
§3 Sample B：售后工单 Agent 的业务链路

§5 证据台账：每条结论的证据等级

§7 从链路到需求：卡点 → 瓶颈 → 缺口 → 用例 → 指标
§8 面试怎么讲（90 秒）
```

### 0.4 核心结论（30 秒版）

> 两类 Agent 的链路都不是"用户提问 → 模型回答"的单步，而是**五到八个环节、三到四个角色、两次交接**。
> 真正卡住的不是生成质量，是三个动作：**给结论时没有依据、发起变更时没有前置校验、信息不足时不肯说不知道**。
> 现在的替代方案有四种，每一种在"单次可用"上都成立，缺的都是同一组东西：**可比、可追溯、可回归**。
> 本文所有结论都标注证据等级；访谈完成前，§2.7 和 §3.7 的卡点只能算**假设**。

> **证据声明（重要）**：本项目**尚无真实用户访谈**。本文的业务链路来自代码、公开资料、行业常识与 46 份 JD 的交叉推断；所有推断项在 §5 标为 C 级。访谈完成后须回填 §6.4，并逐条升级或推翻。

### 0.5 本文不解决什么

- 不做定量用户研究（样本量、显著性、转化率）；
- **不伪造访谈原话**——访谈未执行，§6 只给提纲与模板；
- 不覆盖多模态、端侧、语音 Agent；
- 不代表任何真实企业的实际流程，只代表一类可复现的**场景结构**。

## 1. 为什么单独写这一篇

`01-问题定义.md` 是**工程视角**的瓶颈归类（A 能力 / B 合规 / C 协同 / D 上下文 / E 工具 / F 评测 / G 成本 / H 组织）。本文是**业务视角**的链路还原。

差别用同一件事的两种说法说明：

| 01 的说法（归类） | 本文的说法（证据） |
|---|---|
| "人机协同没有标准答案" | "测试同学在群里问 CI 过了吗，Agent 回'已通过'，但实际只跑了单测——他要么给状态加依据，要么说不知道" |
| "上下文噪声大" | "群里同时在聊发版、团建、另一个项目的迁移，Agent 把另一个项目的风险写进了本次汇总" |
| "管控不可配置" | "研发说'帮我把这个提交评审'，Agent 直接调了 `request_review`，没有人检查故障是否已定级" |
| "评测不可回归" | "改了一次关键词表，dev 从 68.6% 到 100%，但 held-out 只有 60%——不跑 held-out 就发现不了" |

前者是分类，后者是**能被追问的细节**。面试官追问的是后者。

## 2. Sample A：研发协作 Agent

### 2.1 场景定义

一个 8–15 人的项目群，时间窗是**版本上线前 3 天到上线后 1 天**。群里有开发、测试、PM、SRE，同时存在与本次上线无关的闲聊和其他项目的讨论。

Agent 以"群成员"身份被 @，职责是：查状态、汇总风险、辅助上线判断、在授权范围内发起变更。

**为什么是"群"而不是"对话框"**：研发的真实协作发生在群里，信息是多话题、多人、异步、带噪声的。一对一对话框里不存在本文要解决的上下文问题。

### 2.2 角色与期待

| 角色 | 在链路里做什么 | 对 Agent 的期待 | 最怕什么 |
|---|---|---|---|
| 开发 | 提交变更、盯 CI、报风险 | 快速查状态、别漏风险 | Agent 编造 CI 状态或变更结果 |
| 测试 | 回归、发布验证、提缺陷 | 汇总风险，结论可核对 | 没定级就发起评审 |
| PM / PO | 排期、上线决策 | 结论 + 依据 + 出处 | 结论没出处，事后说不清谁拍的板 |
| SRE / 运维 | 故障处理、定级 | 定位、拉人、别越权 | 跨项目读数据、替人定级 |
| 群里其他人 | 闲聊、其他项目 | 不被打扰 | 乱插话、把无关内容写进汇总 |

### 2.3 业务链路

| # | 环节 | 谁做 | 输入 | 输出 | Agent 可介入 | 失败后果 |
|---|---|---|---|---|---|---|
| 1 | 变更产生 | 开发 | PR / 配置 / 迁移脚本 | 变更单 | 查状态 | 低 |
| 2 | 风险讨论 | 全员 | 群聊、文档、历史故障 | 风险清单 | 汇总、筛选、标出处 | 混入噪声、漏风险 |
| 3 | 上线判断 | PM / SRE | 风险清单、CI、定级 | 上线 / 延期 | 给结论（必须确认） | 越权拍板 |
| 4 | 变更执行 | 有权限者 | 评审单、变更单 | 发布 | 发起评审（必须过围栏） | 绕过前置、流程事故 |
| 5 | 事后复盘 | SRE / 全员 | 故障时间线 | 定级、改进项 | 汇总、初步归因 | 定级错、漏改进项 |

### 2.3.1 一次事故的时间线（构造示例）

> 以下是**为了说明链路而构造的示例**，不是真实事故，也不是访谈素材。

```
T-3d 21:40  开发 A：结算服务迁移脚本还没写回滚方案
T-3d 21:41  群里开始聊团建订餐
T-2d 10:15  测试 B：@Agent CI 过了吗
            Agent：已通过          ← 实际只跑了单测，集成测试未跑
T-2d 10:16  测试 B：那行
T-1d 16:00  PM C：@Agent 这次能上吗
            Agent：可以上线        ← 没有依据、没有署名、没有确认
T-0  09:00  发布
T-0  11:20  迁移失败，回滚耗时 40 分钟
```

这一条时间线里出现了本文要解决的全部四类问题：

| 时刻 | 问题 | 行为类 | 平台应对 |
|---|---|---|---|
| T-2d 10:15 | 编造状态 | B1 读取 | 工具返回什么就说什么，读不到就说读不到，带时间戳 |
| T-1d 16:00 | 越权下结论 | B3 结论 | 结论必须经人工确认，且带出处 |
| 全程 | 噪声与漏项 | B2 汇总 | 上下文筛选 + 来源标注 + trace |
| T-0 | 没有事前拦截 | — | 上线门禁：风险未闭环不允许上线 |

### 2.4 触发点 → 行为类

| 用户原话 | 真实意图 | 行为类 | 期望动作 | 失败后果 |
|---|---|---|---|---|
| "CI 过了吗" | 查状态 | B1 读取 | 直接查，带时间戳与范围 | 编造状态 |
| "这次上线有啥风险" | 汇总 | B2 生成 | 自动，但每条带 `message_id` | 混入无关、漏风险 |
| "能给个上线结论吗" | 判断 | B3 结论 | 人工确认 | 越权拍板 |
| "这个改动走个流程" | 变更 | B4 写入 | 围栏 + 确认 | 绕过前置 |
| "你直接批一下" | 越界 | B5 超边界 | 拒绝 + 转人工 | 合规事故 |
| "那个问题处理一下" | 指代不清 | B6 信息不足 | 追问 | 误执行 |

### 2.5 决策点与交接点

| 类型 | 节点 | 谁拍板 | Agent 能做到哪 | 越界信号 |
|---|---|---|---|---|
| 决策 | 风险是否阻断上线 | PM / SRE | 列风险、标出处、给候选结论 | 直接说"可以上" |
| 决策 | 变更是否发起 | 有权限者 | 校验前置条件、等待确认 | 自行调用 |
| 决策 | 故障定级 | SRE | 给候选级别与依据 | 替人定级 |
| 交接 | 信息不足 | Agent | 追问缺失字段 | 编造一个合理答案 |
| 交接 | 超边界 | Agent | 拒绝 + 转人工 | 硬做 |
| 交接 | 连续失败 | Agent | 2 次后转人工 | 无限重试 |

> 规则细节见 `06-人机协同规则.md` §6；工具分级见 `05-1-风险准入判定.md` §5。

### 2.6 工具与权限边界

| 工具 | 读 / 写 | 围栏 | 失败后果 |
|---|---|---|---|
| `search_chat_history` | 读 | F3 本项目 | 跨项目泄露 |
| `get_related_docs` | 读 | 项目权限 | 读到无权限文档 |
| `read_fault_logs` | 读 | 本服务 | 越界读日志 |
| `query_ci` | 读 | F4 只读 | 误触发构建 |
| `create_issue` | 写 | F5 必填 + F2 确认令牌 | 脏数据 |
| `request_review` | 写 | F1 故障已定级 + F2 | 流程事故 |
| `update_ticket_status` | 写 | F2 确认令牌 | 状态错乱 |
| `reply_message` | 写 | 输出审核 | 错误承诺 |

> 围栏定义见 `src/agentgate/tools.py`；当前为代码内硬编码，YAML 可配置是下一步。

### 2.7 卡点（假设，待访谈验证）

| 编号 | 卡点 | 具体表现 | 证据等级 |
|---|---|---|---|
| K1 | 汇总不可信 | 混入无关话题、漏关键风险、不带出处 | C |
| K2 | 结论越权 | 直接给"可以上线"，没有依据也没有署名 | C |
| K3 | 变更绕过前置 | 未定级就发起评审 | C |
| K4 | 信息不足时编造 | 不追问，直接给一个看起来合理的答案 | B |

## 3. Sample B：售后工单 Agent

### 3.1 场景定义

用户通过 IM 进线，围绕一个订单的售后问题（退款、换货、物流、赔付）。与 Sample A 的关键差别：**有标准答案、有资金动作、有明确红线**。

### 3.2 角色与期待

| 角色 | 在链路里做什么 | 对 Agent 的期待 | 最怕什么 |
|---|---|---|---|
| 用户 | 描述问题、提供单号 | 快、准、别让我重复说 | 被敷衍、被承诺后没兑现 |
| 一线客服 | 接管复杂工单 | 把简单问题挡掉、复杂问题给足上下文 | 接手后要从头问一遍 |
| 客服主管 | 审批超额、处理投诉 | 提前识别需要升级的工单 | 超额度承诺已经发出去了 |
| 财务 / 风控 | 资金与合规 | 每笔退款可追溯 | 重复退款、跨用户查询 |

### 3.3 业务链路

| # | 环节 | 谁做 | 输出 | Agent 动作 | 失败后果 |
|---|---|---|---|---|---|
| 1 | 进线 | 用户 | 问题描述 | 识别意图 | 答非所问 |
| 2 | 身份核验 | 用户 / 客服 | 已验证身份 | 发起核验 | 未核验就查单 |
| 3 | 查订单 | Agent | 订单状态、金额 | `query_order` | 查了别人的单 |
| 4 | 匹配政策 | Agent | 适用条款 | `lookup_refund_policy` | 用错政策 |
| 5 | 给方案 | Agent / 客服 | 退款 / 换货 / 拒绝 | 生成方案 | 超额度承诺 |
| 6 | 提交工单 | Agent | 工单号 | `submit_ticket` | 重复提交、错误提交 |
| 7 | 回复 | Agent | 用户可见话术 | 生成 | 承诺无法兑现 |
| 8 | 回访 | 客服 | 满意度 | — | — |

### 3.4 触发点 → 行为类

| 用户原话 | 真实意图 | 行为类 | 期望动作 | 失败后果 |
|---|---|---|---|---|
| "查下我的订单" | 查状态 | B1 读取 | 先核验身份，再查本人订单 | 隐私泄露 |
| "怎么还没到" | 查 + 解释 | B2 生成 | 查物流 + 给预期 | 编造时效 |
| "我要退款" | 变更 | B4 写入 | 确认 + 额度校验 | 超额度退款 |
| "你们必须赔我 500" | 判断 + 变更 | B3 / B4 | 超额度 → 转主管 | 越权承诺 |
| "帮我朋友也查一下" | 越界 | B5 超边界 | 拒绝 | 跨用户泄露 |
| "我的单号是……" | 信息不全 | B6 信息不足 | 追问缺失字段 | 用错单号 |

### 3.5 决策点与交接点

| 类型 | 节点 | 规则 | 失败后果 |
|---|---|---|---|
| 决策 | 身份是否已验证 | 未验证不允许查单 | 隐私事故 |
| 决策 | 退款额度 | 超 `refund_limit` 必须主管 | 资金损失 |
| 决策 | 政策是否覆盖 | 不覆盖则转人工 | 错误承诺 |
| 交接 | 用户情绪激烈 | 立即转人工 | 投诉升级 |
| 交接 | 同一问题 2 次未解决 | 转人工 | 用户流失 |

### 3.6 工具与围栏

| 工具 | 读 / 写 | 围栏 | 失败后果 |
|---|---|---|---|
| `query_order` | 读 | T1 身份已验证 + T5 同用户 | 隐私泄露 |
| `lookup_refund_policy` | 读 | 只读 | 用错政策 |
| `submit_ticket` | 写 | T1 身份 + T2 额度 + F2 确认 | 资金 / 重复工单 |

> 围栏定义见 `src/samples/ticket/tools.py`。

### 3.7 卡点（假设，待访谈验证）

| 编号 | 卡点 | 具体表现 | 证据等级 |
|---|---|---|---|
| K5 | 未核验就查单 | 用户报个单号就查，没验证身份 | B |
| K6 | 超额度承诺 | 为了安抚用户，先答应再走流程 | C |
| K7 | 跨用户查询 | "帮我朋友查一下"被当成合理请求 | B |
| K8 | 承诺无法兑现 | "明天到账"但实际 3–5 个工作日 | C |

### 3.8 两类范式的差别（为什么这个对照有价值）

| 维度 | Sample A 研发协作 | Sample B 售后工单 |
|---|---|---|
| 答案性质 | 无唯一答案 | 有标准答案 |
| 主要风险 | 流程 / 合规 | 资金 / 隐私 |
| 交接方式 | 动态判断（看上下文） | 静态红线（看规则） |
| 评测方式 | 行为 + LLM judge | 结果 + 硬规则 |
| 工具风险 | 写入内部系统 | 写入资金链路 |

> 同一套 Harness、trace、Rubric 引擎能同时承载这两类，才叫"通用"；只能接一类，就只是"一个 Agent 的测试脚本"。

## 4. 当前 workaround：没有平台时他们怎么解决

### 4.1 四种做法

| 编号 | 做法 | 具体形态 | 谁在用 | 单次成本 | 覆盖范围 | 失效点 |
|---|---|---|---|---|---|---|
| W1 | 人工盯群 | 群里 @ 人，人肉读上下文、手打汇总 | 小团队、早期项目 | 30–60 min / 次 | 全覆盖 | 不可复现、换人即失效、无法回归 |
| W2 | 手工 checklist / 多维表格 | 按 SOP 逐条勾选、填表 | 有 SOP 但没工程的团队 | 10–20 min / 次 | 流程类 | 靠自觉、无 trace、版本不可比 |
| W3 | 成品 SaaS | 飞书智能伙伴 / Coze / Dify 配人设、知识库、工作流 | 非技术团队 | 配置 1–2 天 | 单场景 | 执行链路封闭：无结构化 trace、不能换调度器、不能编程交接、无批量回归 |
| W4 | 自建脚本 | Python + LLM API + pytest，各团队自己写 | 有工程能力的团队 | 2–4 周 | 单团队 | 重复造轮子、口径不一、没有门禁、难复用 |

### 4.2 每种做法失效在哪（对应 P1–P4）

| 做法 | 主要失效 | 对应缺口 |
|---|---|---|
| W1 人工盯群 | 不可复现、不可比、无中间状态 | P2 过程不可观测 / P3 结果不可回归 |
| W2 手工 checklist | 靠自觉、无 trace、无法证明执行过 | P2 |
| W3 成品 SaaS | 执行链路封闭，拿不到可编程的中间状态 | P1 管控不可配置 / P2 / P3 |
| W4 自建脚本 | 每团队一套，口径不一，没有统一门禁 | P4 评测不可复用 |

### 4.3 诚实地说：什么时候"人工就够了"

如果同时满足四条，**不需要平台**：

1. 只读，没有任何写入或变更动作；
2. 单场景，短期不打算复制到别的团队；
3. 不上生产，输出只做参考；
4. 出错可撤回，代价可接受。

这正是 `05-1-风险准入判定.md` 里 L0 / L1 的来源。**平台的存在理由不是"所有 Agent 都该评测"，而是"一旦越过 L2，人工试用就不再成立"。**

### 4.4 判断表：什么时候该上平台

| # | 问题 | 如果"是" → 需要什么 |
|---|---|---|
| 1 | 有写入类动作吗？ | 围栏 + 人工确认 |
| 2 | 出错会影响别人，或产生资金 / 合规后果吗？ | 上线门禁 |
| 3 | 会持续迭代 prompt / 规则 / 模型吗？ | 回归对比 |
| 4 | 有第二个 Agent 或第二个团队要接吗？ | 统一接入（Adapter） |
| 5 | 需要向管理层证明"它能上线"吗？ | 报告 + 准入流程 |

> 5 条里命中 3 条以上，平台才有意义；只命中 1 条，用 W1 或 W2 更划算。

## 5. 证据台账

> 等级定义：**A** = 代码 / 测试 / 访谈原话可验证；**B** = 公开资料、产品文档、JD；**C** = 推断，未经证实。

| 编号 | 结论 | 证据 | 等级 | 来源 | 待验证方式 |
|---|---|---|---|---|---|
| E1 | 链路是 5–8 个环节、3–4 个角色、两次交接 | 代码中的路由、围栏、工具链可复现 | A | `src/agentgate/`、`src/samples/` | — |
| E2 | 研发群存在多话题并行与无关噪声 | 合成用例中已构造 | B | `eval/dataset/` | 访谈确认真实群是否如此 |
| E3 | 测试同学会直接问 CI 状态 | 研发协作常识 + JD #26 / #38 | B | 公开资料 | 访谈确认问法 |
| E4 | "未定级就发起评审"是真实风险 | `05-1` 判定 + 围栏 F1 的设计依据 | C | 推断 | 访谈确认是否发生过 |
| E5 | 人工盯群是当前主要替代方案 | 行业常识 | C | 推断 | 访谈确认 |
| E6 | 成品 SaaS 执行链路封闭 | `02-竞品对标.md` | B | 公开产品文档 | — |
| E7 | 单次人工汇总 30–60 min | 无 | C | 估计 | 访谈计时 |
| E8 | "改 A 坏 B"是常见问题 | `10-badcase归因.md`、`11-迭代记录.md` 有实例 | A | 项目内 | — |
| E9 | 评测集与真实分布不一致 | 数据为 synthetic template | A | `04-数据源盘点.md` §0.4 | — |
| E10 | 售后场景的额度 / 身份红线真实存在 | 公开售后政策 + T1 / T2 / T5 设计 | B | 公开资料 | 访谈客服主管 |

**使用方法**：面试被追问"你怎么知道"时，直接报编号。C 级条目要主动说"这是待验证的假设"。

## 6. 访谈设计（待执行）

### 6.1 选谁

3–5 人，覆盖两侧：

| 画像 | 人数 | 为什么选他 |
|---|---|---|
| 研发 / 测试（Sample A 用户） | 2 | 最接近 Agent 的日常使用者，能说清"哪一步被打断" |
| 研发 PM / 项目负责人 | 1 | 上线决策者，能说清"凭什么相信它能上" |
| 客服主管（Sample B 用户） | 1 | 能说清额度、身份、投诉的真实红线 |
| 平台 / 效能工程师（买家侧） | 1 | 能说清"为什么自建脚本不够" |

### 6.2 不要问

| 不要问 | 原因 |
|---|---|
| "你需要一个 Agent 评测平台吗？" | 引导性提问，得到的是需求不是痛点 |
| "你觉得 Agent 最大的问题是什么？" | 太抽象，得到的是观点不是事实 |
| "如果有这个功能你会用吗？" | 假设性问题，答案不可信 |
| "你们现在效率低吗？" | 暗示性提问，对方会顺着你说 |

### 6.3 要问（只问最近一次具体事件）

1. 上一次 Agent / 自动化工具给你**错误结论**，是什么时候？当时你在做什么？
2. 你是怎么发现它错了的？花了多久？
3. 发现之后你做了什么？有没有告诉别人、有没有改流程？
4. 你们现在上线一个 Agent 或自动化流程，要走哪些步骤？**谁签字**？
5. 改了一次 prompt 或规则之后，你怎么知道没变差？
6. 最近一次"改 A 坏了 B"，是什么情况？
7. 现在这件事你们用什么工具做？**为什么不用现成的**？
8. 如果明天要推广到另一个团队，会卡在哪？

> 追问句式："能举一个上周的例子吗？"——具体事件比观点有价值十倍。

### 6.4 记录模板

| 字段 | 内容 |
|---|---|
| 受访者编号 / 角色 | 如 R1 / 测试 |
| 最近一次事件 | 时间、场景 |
| 触发 | 谁说了什么 |
| 损失 | 时间 / 返工 / 事故 |
| 现有做法 | W1–W4 中的哪一种 |
| 原话 | **逐字记录，不改写** |
| 我的解读 | 与第 2/3 节的卡点对应编号 |
| 证据等级 | A / B / C |

### 6.5 反例区（必须填）

| 反例 | 谁说的 | 理由 | 对产品的影响 |
|---|---|---|---|
| （待填） | | | |

> **如果 5 个访谈里没有一个人说"不需要"，说明问法有问题，或者选人只选了支持者。**
> 反例是问题定义可信度的来源，不是需要藏起来的东西。

## 7. 从链路到需求

| 卡点 | 瓶颈 | 缺口 | 用例类型 | 对应指标 |
|---|---|---|---|---|
| K1 汇总不可信 | D 上下文 / F 评测 | P2 / P3 | 正常汇总 + 噪声注入 | `context_recall`、无关混入率 |
| K2 结论越权 | C 人机协同 | P1 | 结论类 | `handoff_accuracy`、`behavior_accuracy` |
| K3 变更绕过前置 | B 业务约束 | P1 | 对抗变更 | `fence_interception` |
| K4 信息不足编造 | C 人机协同 | P1 | 模糊指令 | `false_block_rate`、追问率 |
| K5 未核验查单 | B 业务约束 | P1 | 身份绕过 | 围栏 T1 拦截率 |
| K6 超额度承诺 | B 业务约束 | P1 | 超额退款 | 围栏 T2 拦截率 |
| K7 跨用户查询 | B / D | P1 | 越权查询 | 围栏 T5 拦截率 |
| K8 承诺无法兑现 | A 确定性 / C | P1 / P2 | 对外承诺 | `factuality` |

> 完整链路（瓶颈 → 痛点 → 缺口 → 模块 → FR → 代码 → 测试 → 指标）见 `16-全链路映射.md`。

## 8. 面试怎么讲（90 秒）

> "我先不讲平台，先讲一个场景。
>
> 版本上线前三天，一个十几人的项目群里，同时在聊发版、团建、和另一个项目的迁移。测试同学问 CI 过了吗，Agent 说过了——其实只跑了单测。PM 问这次能不能上，Agent 直接说能上，没有依据，也没有署名。研发说帮我把这个提交评审，Agent 调了接口，但故障还没定级。
>
> 这三个动作对应三类失败：**汇总不可信、结论越权、变更绕过前置**。
>
> 那现在他们怎么解决？四种：人工盯群、手工 checklist、买个成品 SaaS、或者自己写脚本。共同问题是——单次能用，但不可比、不可追溯、不可回归。
>
> 所以我做的不是一个更聪明的 Agent，是让这些动作**可被验证**的基础设施。而且我先划清了边界：只读、单场景、不上生产的 Agent，人工试用就够了，不需要我这套东西。"

**三个可选追问的应答**：

| 追问 | 应答 |
|---|---|
| 你怎么知道群里是这样？ | "链路是从代码和公开资料推出来的，证据等级我标了；真实访谈还没做，所以卡点部分是假设——这是我下一件要做的事。" |
| 这四种做法真的都不行吗？ | "单次都行。不行的是：换个提问方式就不可复现、换了人就失效、改了规则不知道有没有变差。" |
| 为什么不做成一个 Agent？ | "因为卡点不在单个 Agent 的能力，在它周围的人、规则和验收。做 Agent 只解决其中一个角色的问题。" |
