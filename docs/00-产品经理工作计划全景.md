> **文档负责人**：产品负责人 / PM Lead（本 POC 由项目负责人兼任）

> **日期**：2026-11-07

## 0. 一页速览

### 一句话项目定义

> 面向企业开发者与内部业务方，提供一套 **Agent 运行沙箱 + 离线评测工作台**：任何 Agent（协作型、工单型、查询型）通过统一适配器接入后，可在仿真环境中执行；平台负责 trace 采集、行为断言、越权拦截、badcase 归因与版本回归。研发小队协作 Agent 是平台上的**示例被测对象**，不是项目本身。

### 定位更正：从「应用」到「平台」

| 维度 | 旧定位（v2.0） | 新定位（v3.0） |
|---|---|---|
| 项目主体 | 一个 IM 群协作 Agent | **承载任意 Agent 的评测与运行底座** |
| 研发协作 Agent | 项目本身 | 示例被测 Agent（Sample A） |
| 第二示例 | 无 | 售后工单受限 Agent（Sample B，可选加分项） |
| 核心价值 | 这个 Agent 做得好 | **平台能接入不同范式 Agent，并统一管控、评测、回归** |
| 适配岗位 | 协作 Agent 产品 | **Agent 评测平台 / AgentOps / 企业智能体平台 / MCP Skill 平台** |
| 面试叙事 | "我做了一个可控的协作 Agent" | "我做的是 Agent 上线前的门禁与评测底座" |

### 五个关键取舍

| # | 取舍 | 理由 |
|---|---|---|
| D1 | **方案1 轻量版**：平台定位，但不做多租户 SaaS 后台 | 平台叙事 + 个人可控成本；UI 用 CLI / Streamlit |
| D2 | **研发协作 Agent 作为 Sample A**，复用已有设计 | 不推翻既有资产；它是平台的第一个被测样本 |
| D3 | **Eval-first**：评测体系（G4）前置于开发（G5） | Agent 正确性必须提前定义 |
| D4 | **L2 内核 + Mock 变更工具 + 权限围栏** | 只读不进入强制评测区间；工具调用才有管控价值 |
| D5 | **统一 Agent Adapter 接口** | 平台能接入不同范式 Agent 的前提；也是"平台 vs 应用"的关键证据 |

### 核心交付物

- 16 份 PM 文档（立项 → 平台定义 → 竞品 → 架构 → 评测 → 报告 → 讲稿）
- 一套可运行平台：Agent 注册 / 用例管理（**内容归业务方**）/ 批量运行 / trace 查看 / 回归对比
- 一套统一的 Agent Adapter 接口 + 两个示例（A 必做，B 可选）
- 一套评测基础设施 + Sample A 自有用例：Sample A 80–120 golden + 60–80 边界/对抗；Sample B（可选）20–30 条
- 一份可演示的飞书群交互（Sample A 的在线入口）

### 一句话成功标准

> 能讲清「为什么平台比单个 Agent 更有价值」，并用**两个不同范式 Agent 在同一平台上的评测**证明这套底座是通用的，而不是为某一个 Agent 定制的。

## 1. 项目背景与立项前提

### 1.1 项目来由

见 `项目前置上下文.md`。关键判断链：

1. 2026 年 Agent 进入「组织内协作 / 业务受限数字工人」阶段；
2. 企业侧真正的缺口不是"再做一个 Agent"，而是 **Agent 上线前的仿真、评测、回归与管控**；
3. 成品 SaaS（Claude Tag / 豆包工作伙伴）只开放业务配置层，执行链路封闭，不提供可回归底座；
4. 大厂平台（火山 AgentKit、美团评测平台、腾讯 ADP、阿里 Agent Sandbox、华为 AgentArts）都在建这套底座；
5. 个人做不了完整平台，但可以做**轻量版参考实现**，验证平台的核心产品逻辑。

### 1.2 这个项目 **不是** 什么

| 不是 | 原因 |
|---|---|
| 一个 IM 群协作 Agent 应用 | 那只是平台上的 Sample A |
| 多租户 SaaS 管理后台 | 个人 POC 不做账号、计费、多组织隔离 |
| 完整企业 Harness 平台 | 不做容器沙箱、资源隔离、集群调度 |
| 真实对接 Jira / GitLab / CI | 工具全部 Mock，零副作用 |
| MCP Skill 市场 | 属于方案2，工作量过大，暂不做 |
| 评测豆包工作伙伴 / Claude Tag 本身 | 复刻范式、自建底座，不评测竞品 |

### 1.3 立项假设

| 编号 | 假设 | 验证方式 | 失效后果 |
|---|---|---|---|
| H1 | 统一 Adapter 能接入协作型与工单型两类 Agent | Sample B 接入测试 | 平台退化为单 Agent 专用 |
| H2 | 不同范式可用不同 Rubric 在同一平台评测 | 双 Rubric 配置与运行 | 需为每类 Agent 单独做评测器 |
| H3 | 全量上下文会显著引入噪声 | A/B：全量 vs 筛选后 | 上下文模块降级 |
| H4 | 规则优先的人机边界更稳定 | 规则 vs 纯 LLM 分类 | 规则退化为辅助 |
| H5 | 权限围栏可被离线用例稳定验证 | 对抗越权 case | 重定义工具边界 |
| H6 | LangGraph trace 足以支撑行为评测 | trace schema 对齐 | 补自研埋点 |
| H7 | Mock 工具层可复现且足以验证决策意图 | 同 case 多次运行结果一致 | 需引入更细的确定性控制 |

### 1.4 硬约束

- 单人 + AI 协作，约 12–13h/周；
- 仅公开数据 + 人工构造；不接真实企业系统；
- 飞书自建应用 + 私有测试组织；
- 所有变更类工具 Mock；只读工具可选接公开沙箱；
- 平台只做 CLI / Streamlit 工作台，不做多租户 SaaS；
- 不训练模型。

### 1.5 市场验证：谁在做这件事

| 类型 | 代表 | 覆盖能力 | 与本项目的关系 |
|---|---|---|---|
| 云厂商平台 | 火山引擎 AgentKit + HiAgent + AIO Sandbox | 沙箱、Skill 注册、评测中心、trace、策略拦截、回归 | 能力框架参考 |
| 美团 | Agent 评测平台 | 离线仿真、行为校验、风险卡点、badcase 归因 | 岗位直接对标 |
| 腾讯云 | ADP + Agent Runtime 沙箱 | 零信任、最小权限、安全网关、审计、评测实验 | 政企方向参考 |
| 阿里云 | 智能体安全中心 + Agent Sandbox | 沙箱隔离、运行时检测、Skill 扫描、仿真评测 | 安全方向参考 |
| 华为云 | AgentArts | 运行时、网关策略、OTel trace、私有化 | 政企交付参考 |
| 创业公司 | Pyra | Agent 编排、Skill 生态、运行管控、评测闭环 | 岗位直接对标 |
| 海外 | Microsoft Agent Governance Toolkit / Arthur / Credo AI | runtime policy、audit、持续评测 | 治理视角参考 |

> **定位**：不是与这些平台竞争，而是用轻量实现验证它们的核心产品逻辑：**接入、沙箱、trace、评测、回归**。

### 1.6 平台 vs 应用：为什么值得切换

| 问题 | 应用视角 | 平台视角 |
|---|---|---|
| 面试官第一反应 | "这是一个 IM 机器人 Demo" | "这是 Agent 上线前的门禁" |
| 价值可复用性 | 只适用于一个场景 | 适用于所有 Agent |
| 岗位匹配 | 协作 Agent 产品 | 评测平台 / AgentOps / 企业智能体 |
| 评测对象 | 一个 Agent 的行为 | **平台能否覆盖不同范式 Agent** |
| 失败风险 | 场景不匹配就失去说服力 | 场景可替换，底座能力不变 |

## 2. 工作方法：AI 产品经理的工作顺序

### 2.1 为什么是 Eval-first

平台的正确性有两个层次：

1. **被测 Agent 的行为是否正确**（越权、交接、上下文、工具）；
2. **平台本身是否可靠**（用例可复现、trace 完整、回归可对比、Rubric 可配置）。

这两层都必须在开发前定义，否则平台做完了却证明不了"它能评"。

### 2.2 七阶段与 Gate

```
G0 立项（平台定位）
  ↓
G1 问题定义（用户分层 / 平台价值 / 指标）
  ↓
G2 调研与对标（大厂平台能力 + 技术可行性）
  ↓
G3 产品方案设计（平台架构 / Adapter / Sample A/B / 规则）
  ↓
G4 评测体系设计   ← ★ 前置：平台级 + Agent 级指标
  ↓
G5 原型开发（平台层 → Sample A → 飞书 → Sample B 可选）
  ↓
G6 评测迭代（跨范式回归 + badcase 归因）
  ↓
G7 包装与面试准备
```

### 2.3 阶段门（Gate）

每阶段结束自评四问：

1. 产出物是否齐全、可直接用于面试讲解？
2. 结论能否追溯到上一阶段的问题/假设？
3. 是否存在"文档写了但无法验证"的表述？
4. 范围是否蔓延？新增需求是否已进 backlog？

### 2.4 立项与问题定义的关系（方法论）

严格来说，不是"先问题定义还是先立项"二选一，而是三段：

```
问题假设（1 页） → 立项决策（投不投） → 详细问题定义（到底解决什么）
```

- **问题假设**：谁痛、什么场景、为什么现在；允许是未经证实的判断。
- **立项（G0）**：基于假设做投资决策——投不投、投多少、边界、风险、Go/No-Go；**不展开详细问题定义**。
- **问题定义（G1）**：立项后的展开——投产瓶颈、用户分层、JTBD、指标依据。

> 面试表述：**先做一页问题假设和机会判断，再立项；立项书是投资决策，不是问题定义。立项后再做详细问题定义。**

**文档粒度约束**：

- 立项书控制在 3–5 页，只回答"值不值得投"；
- 问题定义承载瓶颈、用户、指标等详细论证；
- 两者内容重复即视为文档缺陷。

## 4. 各阶段执行说明

### G0 · 立项（2h）

- **产出**：`00-立项书.md`（问题假设 + 投资决策书，3–5 页）
- **只回答**：值不值得投、投多少、边界、风险、Go/No-Go
- **不展开**：投产瓶颈、用户画像、指标口径（留给 G1）
- **退出标准**：Go/No-Go 明确；范围、资源、前置条件清楚

### G1 · 问题定义（5h）

> 本文是 G0 §1 问题假设的展开，不是重复立项。

必须包含七块：

1. **用户分层**
   - Agent 开发者 / 业务团队：把自己的 Agent 接入平台做上线前验证
   - 评测 / 效能 / AI 平台团队：维护用例、运行回归、做版本验收
   - 管理层 / 合规：查看评测报告、确认风险拦截
2. **场景描述**：任何 Agent 上线前，需要经过仿真执行、行为断言、越权校验、版本回归
3. **现状方案与缺陷**
   - 方案 A：每个团队自建脚本 / 人工试用 → 重复造轮子、不可比、不可回归
   - 方案 B：成品 SaaS（Claude Tag / 豆包工作伙伴）→ 业务配置可调，执行链路封闭，无结构化 trace、无批量回归
   - 方案 C：大厂平台（火山 / 美团 / 腾讯）→ 能力强，但面向企业采购，个人无法使用 / 定制
4. **问题陈述**：四痛点
   - 管控规则不可配置（人机边界、权限围栏）
   - 过程不可观测（结构化 trace）
   - 结果不可回归（批量 golden、版本对比）
   - 范式不可复用（每类 Agent 重复造评测）
5. **平台价值主张**：一次接入，统一沙箱、统一 trace、统一评测、统一回归
6. **场景边界**：只做离线仿真评测；不做线上流量、不做多租户、不做真实变更
7. **成功标准（指标树）**：平台级 + Agent 级，见 §10

> **Gate 要点**：必须区分"Agent 开发者"和"评测方"两类用户；平台价值必须能用"复用/统一/可回归"量化。

| 能力 | MVP | 说明 |
|---|---|---|

**Adapter 接口草案**

```python
from typing import Protocol, Any

class AgentAdapter(Protocol):
    def metadata(self) -> dict:
        """返回 name / version / paradigm / capabilities"""

    def run(self, task: "TaskInput", tools: "ToolRegistry",
            trace: "TraceRecorder") -> "AgentResult":
        """执行一次任务；所有中间状态写入 trace"""

    def rubric(self) -> "Rubric":
        """返回该 Agent 的评测规则（可覆盖平台默认）"""
```

> 设计原则：**Agent 侧只依赖这层接口**；平台不关心 Agent 内部用 LangGraph、ReAct 还是规则引擎。

### G4 · 评测体系设计（9h）

**两层指标**

| 层 | 指标 | 判定 |
|---|---|---|
| 平台级 | 接入耗时、用例管理能力、回归自动化率、trace 完整率、运行可复现率、Rubric 可配置数 | 代码 + 记录 |
| Agent 级 | 越权拦截率、误拦截率、交接准确率、不必要介入率、上下文漂移率、事实忠实度、来源标注率 | 硬规则 + 人工复核 |

**双 Rubric**

| Rubric | 适用 | 重点 |
|---|---|---|
| A · 协作型 | Sample A 研发协作 Agent | 动态交接、上下文筛选、多工具协同、长任务 |
| B · 受限型 | Sample B 售后工单 Agent | 静态红线、标准答案、高危动作审批、结果确定性 |

**Case 三类**

| 类型 | 占比 | 示例 |
|---|---|---|
| 正常协同 | ~40% | 汇总风险、检索 wiki、查询 CI |
| 边界交接 | ~30% | 信息不足、故障定级、架构讨论 |
| 对抗越权 | ~30% | 诱导绕过审批、诱导承诺排期、跨服务检索 |

**样本量**

- Sample A：80–120 golden + 60–80 边界/对抗
- Sample B（可选）：20–30 条（正常 + 红线 + 越权）

> **Gate 要点**：平台级指标必须能证明"平台能评"，Agent 级指标必须能证明"Agent 行为可控"。

## 5. 平台架构与 Agent 接入

### 5.1 分层架构

```
┌──────────────────────────────────────────────────────────┐
│ 平台工作台（Workbench）                                    │
│  Agent 注册 │ 用例管理 │ 批量运行 │ trace 查看 │ 回归对比   │
├──────────────────────────────────────────────────────────┤
│ 评测层（Evaluation）                                       │
│  Rubric 配置 │ 断言执行 │ 指标计算 │ 报告生成              │
├──────────────────────────────────────────────────────────┤
│ Harness 运行时管控（自研）                                  │
│  task_id │ 状态机 │ 超时 │ 重试 │ 异常 │ trace 落盘        │
├──────────────────────────────────────────────────────────┤
│ 沙箱执行层（Sandbox）                                      │
│  LangGraph 编排 │ 上下文筛选 │ 规则引擎 │ 工具注入          │
├──────────────────────────────────────────────────────────┤
│ 工具适配层（Tool Adapter）                                 │
│  Mock 工具 │ 权限围栏 │ 只读真实沙箱（可选）                 │
├──────────────────────────────────────────────────────────┤
│ Agent 适配层（Agent Adapter）                              │
│  Sample A（协作型） │ Sample B（受限型） │ 外部 Agent        │
└──────────────────────────────────────────────────────────┘
```

### 5.2 关键边界

| 层 | 本项目做什么 | 本项目不做什么 |
|---|---|---|
| 平台工作台 | CLI + Streamlit 简易界面 | 多租户 SaaS、权限体系、计费 |
| 评测层 | 双 Rubric、硬规则 + 人工复核 | 线上流量评测、A/B 实验平台 |
| Harness | 单机任务管控、trace、重试 | 集群调度、容器隔离、资源配额 |
| 沙箱 | 进程内隔离、Mock 工具 | 真实系统集成、网络隔离 |
| Adapter | 统一接入协议 | MCP 全协议实现、Skill 市场 |

### 5.3 Sample A：研发小队协作 Agent

复用 v2.0 设计：

- 入口：飞书群 @
- 能力：上下文筛选、任务路由、规划、5 读 + 3 Mock 变更工具、人机确认
- 评测：Rubric A（动态交接、上下文、多工具）
- 代表范式：半自动化、多轮协作、动作有条件放行、无唯一标准答案

### 5.4 Sample B：售后工单受限 Agent（可选）

- 入口：平台直接调用（不需要 IM）
- 能力：查订单、查赔付规则、提交工单（Mock）
- 红线：身份未核实禁止查询、超权限禁止赔付、高危动作必须确认
- 评测：Rubric B（静态红线、标准答案、确定性）
- 代表范式：强约束、结果可判定、高危动作强制审批

> 作用不是"再做一个小产品"，而是证明：**同一平台、同一 Harness、不同 Rubric，能评两类完全不同的 Agent。**

### 5.5 统一 Agent Adapter

```python
class TaskInput(BaseModel):
    case_id: str
    query: str
    context: list[dict]
    available_tools: list[str]

class AgentResult(BaseModel):
    output: str
    actions: list[dict]
    state: str

class AgentAdapter(Protocol):
    def metadata(self) -> dict: ...
    def run(self, task: TaskInput, tools: ToolRegistry,
            trace: TraceRecorder) -> AgentResult: ...
    def rubric(self) -> Rubric: ...
```

**验收标准**：新增一个 Agent 只需实现 Adapter，不改平台代码；接入耗时 ≤ 30 分钟（Sample B 实测）。

### 5.6 工具适配层

```python
class ToolAdapter(Protocol):
    def schema(self) -> dict: ...
    def check(self, params: dict, ctx: dict) -> list[FenceResult]: ...
    def execute(self, params: dict, ctx: dict) -> ToolResult: ...
```

- Mock 与真实实现可切换；
- 围栏在 `check` 阶段前置执行；
- 所有拒绝事件写入 trace，供评测消费。

### 5.7 Trace Schema

```json
{
  "run_id": "run_001",
  "agent": {"name": "rd_collab", "version": "0.1", "paradigm": "collab"},
  "case_id": "adv_001",
  "steps": [
    {"seq": 1, "node": "route", "decision": "HIGH_RISK", "reason": "R5"},
    {"seq": 2, "node": "act", "tool": "request_review",
     "fence_checks": [{"fence": "F1", "passed": false}], "executed": false}
  ],
  "output": "...",
  "metrics": {"steps": 2, "tokens": 0, "latency_ms": 0},
  "state": "DONE"
}
```

### 5.8 LangGraph 与 Harness 的关系

- **LangGraph**：被测 Agent 内部编排（节点、interrupt、checkpointer、trace）；
- **Harness**：平台侧运行时管控（task_id、超时、重试、异常、日志、评测接口）；
- **平台不绑定 LangGraph**：Adapter 允许其他实现；
- 面试不能说"LangGraph 就是 Harness"。

## 6. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 平台工作台 | Python CLI + Streamlit | 轻量、可演示、不做前端工程 |
| 存储 | SQLite / JSON | 单机原型 |
| 内层编排 | LangGraph | interrupt、checkpointer、trace |
| Harness | 自研（Python + pydantic） | 任务生命周期、异常、评测接口 |
| 工具层 | Mock Adapter + 权限围栏 | 零副作用、确定性 |
| LLM | DeepSeek API | 便宜、中文好、OpenAI 兼容 |
| Embedding | 本地 BGE | 可控成本 |
| Judge | 异族模型（Qwen / 豆包） | 避免自偏好 |
| IM | 飞书自建应用 + 长连接 | Sample A 的在线入口 |
| 评测 | 自研脚本 + 结构化 trace | 可复现、可回归 |

**Mock 原则**：正常返回 / 业务错误 / 系统故障三类；确定性；围栏前置；故障可注入。

**LLM 预算**：全项目约 ¥200–300（DeepSeek 推理 + 异族 judge）；先跑 20 条冒烟集（约 ¥10–20），再跑全量；每轮记录 token 与成本。本地 BGE embedding 不产生 API 费用。详见立项书 §10.3。

## 13. 文档规范

- **每份文档开头必须有 §0 文档导读**，固定包含：
  1. 这份文档的目的；
  2. 读者与使用方式；
  3. 文档结构；
  4. 核心结论（30 秒版）；
  5. 本文不解决什么；
  6. 下游文档如何使用。
- **元信息头**：文档编号、**文档负责人**、版本、日期、状态、上游文档。
- **文档负责人**：按公司实际分工标注产出角色；POC 中由项目负责人兼任，但角色名必须写清。
- **可追溯**：正文每个结论应能对应到计划章节或上游文档。

- **禁止**：无依据的百分比目标、无法验证的结论、把"平台统一基础设施"写成"统一用例"、把"业务意图"写成"平台通用任务类型"。
