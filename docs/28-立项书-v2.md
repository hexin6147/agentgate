## 0. 一句话

> **一个研发协作 Agent**：挂 9 个工具（指标、日志、发布、diff、用例、历史故障、文档、负责人、群聊），覆盖四个场景——**故障排查、转测范围、需求澄清、新人上手**。
> 其中**故障排查是真正的 Agent 场景**（路径不可枚举），其余三个是工具编排场景。

---

## 1. 用户

> 依据：一次真实研发组访谈（N=1，团队 51 人：产品 8、研发 30、测试 5、运维 3、设计 5；双周迭代）。

| 角色 | 主用场景 | 他要什么 |
|---|---|---|
| **开发（主）** | 故障排查、需求澄清 | 不用翻日志/翻记录；根因有证据 |
| **测试（次）** | 转测范围 | 知道这次改了什么、回归哪些 |
| **产品** | 需求澄清、验收 | 争议时能查到依据 |
| **新人** | 新人上手 | 知道怎么做、找谁 |
| 运维 | 故障排查（只读） | 定位快，交接清楚 |

## 2. 场景

### 2.1 四个场景

| # | 场景 | 用户会怎么问 | 步骤 | 交付物 | 本质 |
|---|---|---|---|---|---|
| **S1 故障排查** | "支付服务 14:00 起 5xx 升高，为什么？" | 指标 → 日志 → 发布 → 历史故障 → 结论 | 根因 + 证据链 | **Agent**：路径随证据变 |
| **S2 转测范围** | "这次改了什么？回归哪些？" | diff → 用例 → 历史故障 → 群聊口径 | 回归清单 + 依据 | Workflow：3–4 步固定 |
| **S3 需求澄清** | "这个需求还缺什么？" | 群聊 → 文档 → 类似需求 → gap | gap 清单 + 澄清问题 | 半 Agent：读→比→问 |
| **S4 新人上手** | "这个服务怎么部署？找谁？" | 文档 → 历史故障 → 群聊 → 负责人 | 步骤 + SOP + 联系人 | RAG：检索 + 模板 |

### 2.2 Agent 纯度（必须说清）

| 场景 | 路径可枚举吗 | Agent 纯度 |
|---|---|---|
| 故障排查 | ❌ 因症状而异 | **高** |
| 需求澄清 | 🟡 半固定（读→比→问） | 中 |
| 转测范围 | ✅ 固定 3–4 步 | 低 |
| 新人上手 | ✅ 检索 + 模板 | 低 |

> **对外只把故障排查讲成 Agent**；另三个讲成“工具编排”，不混着说。

## 3. 痛点

### 3.1 痛点结构

| # | 用户 | 场景 | 问题 | 现在怎么做 | 为什么不够 | 代价 | 证据 |
|---|---|---|---|---|---|---|---|
| **P1** | 开发 | 澄清会后（群里 5–50 条） | 决策散在对话里 | 手抄发群/邮件 | 只写不读、文档滞后 | 转测 GAP 加班补 | 访谈 |
| **P2** | 测试 | 转测前 | 不知道最终口径与边界 | 问开发/看旧文档 | 开发忙、文档不可信 | 用例按旧理解，返工 | 访谈 |
| **P3** | 产品 | 验收争议 | 找不到"当时谁定的" | 翻群/问人 | 记录不全 | 验收不认、扯皮 | 访谈 |
| **P4** | 新人 | 入职/接手 | 不知道怎么做、找谁 | 问老人/翻文档 | 老人忙、文档散 | 上手慢 | 推断 C |
| **P5** | 开发/运维 | 线上故障 | 定位靠人、信息分散 | 连机器看日志、问开发 | 日志/发布/历史故障不在一个地方 | 定位慢、复盘质量不稳 | 访谈（运维） |
| P6 | 团队 | 同类问题反复 | 无沉淀 | 靠个人经验 | 人走了就断 | 效率低 | 推断 C |

### 3.2 访谈原话

- "按流程应该由产品补充到需求里，但实际上是由开发自己总结留档发到群里或者群发邮件"
- "官方是看需求文档，实际是得跟开发去确认细节"
- "转测之后，测试发现方案有 GAP……基本都得开发加班补"
- 运维："复现、虚拟机连上去看日志、定位到对应开发、找开发一起定位"

## 4. 现有方案与不足

| 办法 | 现在怎么做 | 为什么不够 |
|---|---|---|
| IM 搜索 | 群里搜关键词 | 字面匹配；5–50 条里找结论靠翻 |
| 云文档 | 需求、wiki 放项目群云空间 | 更新滞后；不绑代码仓 |
| bug 单 | 产品改单补需求 | 最终定义跨三处 |
| 会议记录 | 开发写、发邮件 | 只写不读 |
| 连机器看日志 | SSH + grep + 问开发 | 跨服务、跨发布对不上；靠经验 |
| 问人 | 问上一个开发/值班 | 人一走就断 |

**根因**：信息分散在六类系统里，检索靠关键词，关联靠人脑。

## 5. 方案：9 个工具 + 4 个场景

### 5.1 工具目录

| # | 工具 | 类型 | 参数 | 返回 | 场景 |
|---|---|---|---|---|---|
| 1 | `query_metrics` | 结构化 API | service, metric, start, end, step | 时间序列 + 异常点 | S1 |
| 2 | `query_logs` | 结构化 API | service, level, start, end, keyword, limit | 日志行 + `file:line` | S1 |
| 3 | `list_deploys` | 结构化 API | service, start, end | 版本、时间、MR、变更模块 | S1、S2 |
| 4 | `get_diff` | 代码 API | mr_id / commit_range | 文件、增删行、**变更模块、直接依赖** | S1、S2 |
| 5 | `list_tests` | 测试库 | module / tag | 用例 ID、描述、覆盖点 | S2 |
| 6 | `search_incidents` | RAG + 结构化 | query / service / window | 历史故障 + 根因 + 时间线 | S1、S3、S4 |
| 7 | `search_docs` | RAG | query, top_k | 文档片段 + 引用 | 全部 |
| 8 | `get_owner` | 组织 API | module / service | 负责人、值班人 | 全部 |
| 9 | `search_chat` | RAG | query, group, window | 群消息 + 引用 | S2、S3、S4 |

### 5.2 场景 × 工具

| 场景 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| S1 故障排查 | ✅ | ✅ | ✅ | ○ | | ✅ | ✅ | ✅ | |
| S2 转测范围 | | | ✅ | ✅ | ✅ | ✅ | ✅ | ○ | ✅ |
| S3 需求澄清 | | | | | | ✅ | ✅ | ✅ | ✅ |
| S4 新人上手 | | | | | | ✅ | ✅ | ✅ | ✅ |

共享度：`search_docs` / `search_incidents` / `get_owner` 覆盖 4/4；`search_chat` 3/4。

### 5.3 技术点覆盖

| 技术点 | 深度 | 落点 |
|---|---|---|
| **RAG 全链路** | 很高 | 文档、历史故障、群聊、代码 diff 四类语料 |
| **上下文工程** | 高 | 200 行日志裁剪；5–50 条群聊；跨场景上下文 |
| **记忆** | 高 | 故障↔变更↔需求互引：查变更时引用上次故障 |
| **Prompt 工程** | 高 | 根因归纳、gap 检测、回归清单、SOP |
| **工具调用** | 高 | 9 个工具，参数校验、超时、重试、截断 |
| **任务规划 / ReAct** | 高 | 故障排查路径随证据变；证据不足继续查 |
| **评测 / 回归 / 归因 / 观测** | 高 | 每场景 gold set + 轨迹 + trace |
| **MCP / Function Calling** | 中高 | 指标/日志/发布走 MCP；本地工具走 FC |

### 5.4 分阶段范围

| 阶段 | 场景 | 工具 | 目标 |
|---|---|---|---|
| **P0** | AgentGate 可运行 | — | 日志 / SQLite / usage / git+tag / issue |
| **P1** | S1 故障排查 | 1、2、3、6、7、8（6 个） | 把 Agent 主场景做深 |
| **P2** | S2 转测、S3 需求 | 加 4、5、9（共 9 个） | 工具编排 + 跨场景记忆 |
| **P3** | S4 新人、数字员工 | 复用 9 个 | SOP、自动记录员、多 Agent |

> P1 不做扎实，不进 P2。

### 5.5 AgentGate 的边界：评测模块，不是评测平台

> 按 12 份工程 JD 统计：**评测出现 9/12，但“建评测平台”出现 0/12。**
> 工程岗要的是“用评测改进 Agent”，不是“做评测产品”。

| 保留（够用） | 砍掉（平台化） |
|---|---|
| 离线评测集 | Case 管理平台 |
| 指标（任务成功率/正确性/效率） | 门禁/签字/豁免 |
| Trace / span / usage | 人评/机评队列 |
| 轨迹评测（步级/工具选择/恢复） | Evaluator 配置 |
| BadCase 归因（简化） | Agent 注册/版本 |
| 回归对比 | 多租户/权限/控制台 |
| LLM judge（轻量） | Rubric 版本/灰度 |

**“够用”的标准**：能回答“这版比上版好还是差、错在哪一类、证据够不够”，就够了。
不需要回答“谁能上线、谁签字、多团队怎么隔离”。

## 6. 不做什么

- 不做多项目、多租户；
- 不做代码修改、发布；
- 不做真实日志平台接入（Mock）；
- 不做模型训练；
- 不做通用助手（不问天气、不写文案）；
- 不做设计评审、发布检查（暂时）。

## 7. 怎么算成功

| 场景 | 指标 | 目标 |
|---|---|---|
| S1 故障排查 | 根因命中率 / 证据链完整率 | 80% / 90% |
| S2 转测范围 | 回归覆盖率 / 误报率 | 85% / ≤15% |
| S3 需求澄清 | gap 召回率 / 澄清问题有效率 | 80% / 70% |
| S4 新人上手 | 步骤完整率 / 可执行性 | 85% / 4 分（5 分制） |
| 通用 | 引用准确率 | ≥95% |

> 个人项目，N=30/场景，访谈 N=1；不外推。

## 8. 假设与风险

| 假设 | 不成立会怎样 | 验证 |
|---|---|---|
| 故障数据能合成得像真的 | 演示不可信 | 先造 1 个故障跑通 |
| 根因能 gold 标注 | 评测不可信 | 每个故障写标准根因 + 证据 |
| 四个场景共享工具够用 | 需要更多工具 | 用 5.2 矩阵检验 |
| 跨场景记忆有真实用途 | 记忆退化成检索 | 变更时引用故障，做进 demo |

| 风险 | 应对 |
|---|---|
| 四场景摊薄 | P1 只做故障排查 |
| 路由风险（四场景变路由器） | 每个场景内部路径仍动态，不靠分类 |
| 数据合成量大 | 先 1 个服务、1 个故障、5 个模块 |
| 根因主观 | 标准答案 + 证据链双判 |
