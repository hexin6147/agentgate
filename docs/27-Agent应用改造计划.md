## 1. 产品定义

### 1.1 一句话

> **一个研发协作 Agent**：挂 9 个工具，覆盖故障排查、转测范围、需求澄清、新人上手。
> 故障排查是 Agent 主场景，其余三个是工具编排。

### 1.2 用户

| 角色 | 主用场景 |
|---|---|
| 开发（主） | 故障排查、需求澄清 |
| 测试 | 转测范围 |

### 1.3 四个场景

| # | 场景 | 步骤 | 交付物 | 本质 |
|---|---|---|---|---|
| S1 | 故障排查 | 指标 → 日志 → 发布 → 历史故障 → 结论 | 根因 + 证据链 | **Agent** |
| S2 | 转测范围 | diff → 用例 → 历史故障 → 群聊口径 | 回归清单 | Workflow |

## 2. 技术栈与选型考量

> **JD 关注度**：★★★ 面试必问；★★ 高频；★ 加分。

| 层 | 选型 | 为什么选它 | 放弃了什么 | JD 关注度 |
|---|---|---|---|---|
| 语言 | **Python 3.12** | 生态最全；JD 多数要求 Python | Java/Go 的并发与类型优势 | ★★ |
| Agent 编排 | **LangGraph** | 显式状态机、interrupt、checkpointer | AutoGen 的开箱即用；AgentExecutor 的黑盒循环 | ★★★ |
| API | **FastAPI + SSE** | 异步、流式、OpenAPI | WebSocket 双向 | ★★ |
| 参数校验 | **Pydantic** | 工具参数、证据链 schema | 手写 dict 校验 | ★★ |
| 存储 | **SQLite** | 零运维；故障/变更/决策一张图 | Postgres 的并发与多租户 | ★ |
| 向量 | **FAISS** | 本地、无服务、10 万 chunk 够用 | Milvus/pgvector 的元数据过滤 | ★★ |
| Embedding | **BGE**（Ollama） | 中文、本地、零成本 | OpenAI embedding 的质量与出境 | ★★ |
| Rerank | **bge-reranker** | 本地、与 BGE 同源 | Cohere 的外部依赖 | ★ |
| LLM | **OpenAI 兼容接口** | 本地/云端一套代码，便于讲路由与降级 | 单厂商 SDK 的特有能力 | ★★★ |
| 协议 | **MCP SDK** | 指标/日志/发布走 MCP | 自研协议 | ★★ |
| 前端 | **Streamlit** | 半天出页面 | React 的交互精度 | — |
| 交付 | **Docker + GitHub Actions** | JD 明确 CI/CD | 手工部署 | ★★ |
| 测试 | **pytest** | 回归基础，已有 127 条 | — | ★ |

### 2.1 三个会被追问的选型

**① 为什么是 LangGraph**

- 故障排查需要显式状态机：每步查到什么、下一步查什么都要落 trace；
- 需要 interrupt：高风险操作（如触发回滚）前暂停；
- 需要 checkpointer：一次排查跨多轮，能恢复。

**② 为什么 OpenAI 兼容接口**

- 本地 Qwen 与云端 DeepSeek 同一套代码；
- 可讲模型路由与降级，对应 AI 网关方向。

**③ 为什么 FAISS**

- 四类语料总量 < 10 万 chunk，单机够用；
- 代价是没有元数据过滤，要主动说清。

## 3. 现状与差距

| 能力 | 现状 | 差距 |
|---|---|---|
| 工具层 | 围栏 + 执行（Mock 变更工具） | 无指标/日志/发布/diff/用例/群聊工具 |
| Agent 循环 | 固定流水线，单次工具调用 | 无 ReAct、无重规划、无停止条件 |
| RAG | BGE 只筛聊天消息 | 无文档/故障/代码入库，无混合检索 |
| 记忆 | 无 | 无故障/变更/需求互引 |
| 评测 | 行为指标、Rubric | 无根因命中、证据链、回归覆盖 |
| 可观测 | 节点级 trace | 无 span、token、latency |

## 4. 开发前的卡点与应对

| # | 卡点 | 为什么会卡 | 应对 | 降级 |
|---|---|---|---|---|
| 1 | **故障数据合成** | 日志/指标/发布要像真的 | 一个服务、5 模块、3 故障；先做 1 个 | 只做 1 个故障 |
| 2 | **根因 gold 主观** | 标准答案难定 | 每个故障写根因 + 证据链；人工双判 | 只评证据链 |
| 3 | **9 个工具 Mock 量大** | 每个都要参数和 fixture | 先 6 个（P1），P2 加 3 个 | 工具合批，减少接口 |
| 4 | **四场景摊薄** | 每个都做一层皮 | P1 只做故障排查 | 砍到 2 个场景 |
| 5 | **路由风险** | 四场景变路由器 | 每场景内部路径仍动态 | 只讲一个 Agent 场景 |
| 6 | **RAG 语料不统一** | 文档/故障/群聊/diff 结构差异大 | 先文档+故障，群聊/diff 后加 | 两类也能跑 |
| 7 | **跨场景记忆设计** | 没有现成模型 | 以服务/模块为键，串故障/变更/需求 | 先单场景记忆 |
| 8 | **评测三套 gold** | 标注工作量大 | 每场景 10 题，先故障 | 只报故障 |
| 9 | **代码 diff/用例数据** | 需要 mock 仓库 | 用一个 pay-service 仓库 + 5 模块 | 只做文件级 diff |
| 10 | **GAP 证明** | 只有从现在开始的提交 | 提高提交密度 + 每阶段一篇技术文 | 用 demo 补 |

## 5. 分阶段开发计划

### P0 · 让 AgentGate 跑起来（评测模块，不是平台）

> 目标：**让 AgentGate 能真实运行、留下可查的数据。** 不做平台化。

| 项 | 内容 |
|---|---|
| **功能** | 结构化日志（trace_id）、SQLite 存 run/report/trace、采集 usage/latency、git init + tag、issue/backlog |
| **做到什么程度** | ① 每次 run 能查到历史；② 日志能按 trace_id 串起来；③ 发布有 tag；④ bug 有 issue |
| **交付物** | 一份真实运行记录；日志/存储/usage 的 schema |
| **技术点** | 可观测、持久化、成本采集 |
| **改动模块** | 新增 `logging.py`、`store.py`、`usage.py`；改 `harness.py`、`trace.py`、`llm.py`；`git init` |
| **DoD** | 能回答"这次 run 为什么失败、上一版指标多少、最近发布了什么" |

### P1 · 故障排查 Agent（6 工具）

> 目标：**把唯一真正的 Agent 场景做深。** 不做转测、不做需求、不做新人。

| 项 | 内容 |
|---|---|
| **场景** | S1 故障排查：指标 → 日志 → 发布 → 历史故障 → 根因 |
| **工具** | `query_metrics`、`query_logs`、`list_deploys`、`search_incidents`、`search_docs`、`get_owner` |
| **做到什么程度** | ① 路径随证据变（先查指标还是先看发布由 Agent 决定）；② 工具超时重试；③ 日志截断与摘要；④ 每条结论带证据（日志行/发布号/文档 ID）；⑤ 10 个故障任务评测 |
| **交付物** | mock 世界（服务/模块/故障/发布/文档）；Agent 循环；10 题评测报告；3 条 trace；demo |
| **技术点** | Agent 循环、工具系统、RAG（文档+历史故障）、上下文工程、Prompt、评测、可观测、MCP |
| **改动模块** | 新增 `tools/`（metrics/logs/deploys/incidents/docs/owner）、`agent/loop.py`、`rag/`；改 `trace.py`、`evaluation.py`、`cli.py` |
| **DoD** | 根因命中 ≥80%，证据链完整 ≥90% |
| **卡点** | 1、2、3、6、10 |

### P2 · 转测与需求（9 工具）

> 目标：**用同一套工具做工具编排，并让跨场景记忆成立。**

| 项 | 内容 |
|---|---|
| **场景** | S2 转测范围、S3 需求澄清 |
| **新增工具** | `get_diff`、`list_tests`、`search_chat` |
| **做到什么程度** | ① 转测：diff → 用例 → 历史故障 → 群聊口径，输出带依据的回归清单；② 需求：群聊+文档+类似需求，输出 gap 清单；③ 跨场景记忆：查变更时引用上次故障，查需求时引用历史故障 |
| **交付物** | 两个场景 demo；两套 gold（各 10 题）；回归清单与 gap 清单 |
| **技术点** | 工具编排、代码/群聊 RAG、跨场景记忆、评测 |
| **改动模块** | 新增 `tools/diff.py`、`tools/tests.py`、`tools/chat.py`、`scenarios/transfer.py`、`scenarios/requirement.py`；扩展 `memory.py` |
| **DoD** | 回归覆盖 ≥85%，误报 ≤15%；gap 召回 ≥80% |
| **卡点** | 3、7、8、9 |

### P3 · 新人与数字员工

> 目标：**从“能查”到“能自动产出”。**

| 项 | 内容 |
|---|---|
| **场景** | S4 新人上手；数字员工（故障记录员） |
| **做到什么程度** | ① 新人问“怎么部署/找谁”，输出步骤 + 负责人 + 引用；② 故障处理完后自动生成复盘初稿；③ 可选：多 Agent（定位/复核） |
| **交付物** | SOP demo；自动复盘初稿；架构图 |
| **技术点** | SOP 生成、触发器、权限与审计、多 Agent（可选） |
| **改动模块** | 新增 `scenarios/onboarding.py`、`agents/recorder.py` |
| **DoD** | SOP 可执行（人工 4/5）；复盘初稿可采纳 |
| **卡点** | 4、5 |

## 6. 完成后掌握的技术点与深度

| 技术点 | 深度 | 能讲清什么 |
|---|---|---|
| **开放路径 Agent** | 能独立实现 | 路径随证据变、停止条件、失败重规划 |
| **工具系统** | 能实现生产级 | 9 工具、参数校验、超时、重试、截断、MCP/FC 分工 |
| **异构 RAG** | 能独立实现并调优 | 文档/历史故障/群聊/diff 四类语料 |
| **上下文工程** | 能设计 | 200 行日志、5–50 条群聊、token 预算 |
| **记忆** | 能设计并实现 | 故障↔变更↔需求互引，服务/模块为键 |
| **评测** | **强于多数候选人** | 根因命中、证据链、回归覆盖、轨迹评测 |
| **可观测** | 能实现 | span、token、latency、跨场景串链 |
| **SOP / 数字员工** | 能设计 | 从知识到流程到自动执行的抽象 |

**不能声称**：模型训练/PEFT/RLHF、K8s、分布式训练。

## 7. 简历与 GAP 叙事

### 7.1 项目定位

> 「**研发协作 Agent**」：9 个工具、4 个场景；故障排查是唯一真正的 Agent 场景。

### 7.2 三条 bullet 方向

1. **开放路径 Agent**：故障排查，9 工具动态编排，路径随证据变。
2. **异构 RAG 与跨场景记忆**：文档/故障/群聊/diff；查变更引用历史故障。
3. **评测与工具治理**：根因命中、证据链、回归覆盖；超时/重试/截断/MCP。

### 7.3 GAP 证据链

| 证据 | 怎么给 |
|---|---|
| 提交记录 | 连续、有功能增量 |
| demo | 3 分钟：输入一个故障现象 → Agent 自己查指标/日志/发布 → 根因 + 证据链 |
| 技术文章 | 每阶段一篇：开放路径 Agent、异构 RAG、跨场景记忆 |
| 测试与 CI | 测试数、CI 绿标 |

> 话术："这 15 个月做了两件事：系统补工程栈，以及独立开发这个研发协作 Agent。代码、demo、文档都能查。"

## 8. 取舍

| 取舍 | 原因 |
|---|---|
| 评测只做模块，不做平台 | JD 里评测 9/12，平台化 0/12 |
| P1 只做故障排查 | 它是唯一 Agent 纯度高的场景 |
| 四场景但只讲一个 Agent | 避免把编排场景说成 Agent |
| 不做真实日志平台 | Mock 足够演示，零副作用 |
| 不做代码修改/发布 | 风险高，且不是评测重点 |
| 多 Agent 放 P3 | 不影响前两阶段深度 |
| 不设固定周数 | 深度优先，P1 不扎实不进 P2 |
