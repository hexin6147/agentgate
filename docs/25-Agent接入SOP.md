### 0.4 核心结论（30 秒版）

> "新增 Agent 接入 ≤ 30 分钟"这句话，**必须拆成两个指标**：
> **技术接入**（Adapter 跑通第一个 case）≤ 30 分钟；**业务就绪**（用例 + Rubric + 围栏 + 门禁跑通）≈ 5 人日。

- 不承诺任何业务的接入排期。

## 1. 接入是什么：四类契约

接入不是"接一个 API"，是**把 Agent 放进一套运行、观测、判定契约里**。四类契约缺一不可：

| 契约 | 内容 | 谁实现 | 缺了会怎样 |
|---|---|---|---|
| **Agent 契约** | `metadata()` + `run()` | 业务开发 | 平台调不起来 |
| **工具契约** | `ToolRegistry.check/execute`，返回 `FenceResult` | 业务 / 平台 | 无法拦截、无法审计 |
| **用例契约** | Case Schema + 期望行为 + 判定方式 | 业务方 | 无法评测 |
| **Rubric 契约** | 指标、权重和为 1、硬门槛清单 | 业务方 | 无法判定通过与否 |

> 只做第一类，叫"接进来了"；四类都做，才叫"被管住了"。

## 2. 契约现状：隐式、鸭子类型、依赖私有方法

### 2.1 实际契约比文档写的多

`05-2` 写的是两个方法：`metadata()` 和 `run()`。但用 `LangGraphAgent` 包装时，平台会调用业务的这些成员：

| 成员 | 类型 | 必需 |
|---|---|---|
| `metadata()` | 方法 | ✅ |
| `run(case, tools, trace, ctx)` | 方法 | ✅（独立运行时） |
| `classifier.match(query)` | 属性 + 方法 | ✅（LangGraph 包装时） |
| `_filter(case)` | 私有方法 | ✅ |
| `_plan(case, match, behavior, ctx)` | 私有方法 | ✅ |
| `_fence_message(fences)` | 私有方法 | ✅ |
| `_summarize(case, kept, behavior)` | 私有方法 | ✅（B2） |
| `context_filter` | 可选属性 | 🟡 |
| `summarizer` | 可选属性 | 🟡 |

### 2.2 这说明什么

> **平台的包装器在调用业务的私有方法**，说明抽象还没做干净。
> 正确做法是定义一个正式的 `AgentAdapter` Protocol，把 `_filter` / `_plan` / `_summarize` 变成公开契约；现状是"能跑，但边界靠默契"。

### 2.3 注册点也是硬编码的

```python
# factory.py
def build_agent(kind: str = "rule", context: str = "rule"):
    if kind not in ("rule", "llm", "ticket"):
        raise ValueError(f"unknown agent kind: {kind}")
    if kind == "ticket":
        return LangGraphAgent(RuleBasedTicketAgent())
    ...
```

接第三个 Agent，必须改这个文件、重新部署平台。**这不是接入，这是给平台提需求。**

## 3. 平台提供 vs 业务提供

| 类别 | 平台提供 | 业务提供 |
|---|---|---|
| Agent | 契约定义、包装器、执行沙箱 | **Agent 实现、意图与行为声明** |
| 工具 | Mock 工具基类、围栏框架、trace 记录 | **工具契约、fixture、前置条件** |
| 用例 | Schema、标签体系、版本机制、执行 | **case 内容、golden、期望行为** |
| Rubric | 引擎、权重校验、硬门槛执行 | **维度、权重、目标值** |
| 门禁 | 判定逻辑、报告结构 | **风险接受、签字** |
| 数据 | 存储、对比、归档 | **脱敏与合规** |

> 一句话：**平台管机制，业务管内容。** 这条边界在 `01` §4.2 已经定过，接入 SOP 是它的执行版。

## 4. 六步接入流程

| # | 步骤 | 输入 | 输出 | 负责人 | 耗时 |
|---|---|---|---|---|---|
| 1 | 准入评估 | 业务场景描述 | 风险等级 L0–L3 | 业务 + 平台 | 0.5 人日 |
| 2 | 声明意图与行为 | 业务任务清单 | `IntentSpec[]`，映射到 B1–B6 | 业务 PM | 0.5 人日 |
| 3 | 实现 Agent 契约 | 已有 Agent | `metadata()` + 钩子 | 业务开发 | 0.5–2 人日 |
| 4 | 接工具与围栏 | 工具清单、权限规则 | `ToolRegistry` + fences | 业务 + 平台 | 1–2 人日 |
| 5 | 建用例与 Rubric | 业务样本 | Case 集 + Rubric YAML | 业务 + 评测 | 2–3 人日 |
| 6 | 跑门禁、出报告 | 以上全部 | 验收报告 | 评测 | 0.5 人日 |

**合计：5–8 人日。**

### 4.1 第 2 步是最容易被跳过的一步

很多接入直接写代码，跳过"意图 → 行为类"的声明。后果：

- 行为类由模型自由判断，规则引擎无从下手；
- 跨业务无法对比（每个业务一套自己的分类）；
- 围栏没有挂载点。

> **行为类声明不是文档工作，是接入的前置条件。**

### 4.2 第 4 步的边界

| 谁做 | 做什么 |
|---|---|
| 业务 | 列出工具、参数、前置条件、失败后果 |
| 平台 | 提供 `FenceResult` 结构、把围栏挂在执行前 |
| 业务 | 决定"什么情况必须拦" |

> 围栏的**判定内容**归业务，**执行机制**归平台。当前围栏硬编码在 `tools.py`，这个分工还没落地。

## 5. 30 分钟 vs 1 周：把指标拆开

`01` §1.5 写的成功标准是"新增 Agent 接入 ≤ 30 分钟"。这句话有歧义，必须拆：

| 指标 | 定义 | 目标 | 现状 |
|---|---|---|---|
| **技术接入耗时** | 从拿到模板到第一个 case 跑通 | ≤ 30 min | 🟡 可做到，但需改 `factory.py` |
| **业务就绪耗时** | 从立项到门禁跑通 | ≤ 5 人日 | 🟡 未实测 |
| **全量接入耗时** | 从立项到 Go | ≤ 8 人日 | 🟡 未实测 |

### 5.1 为什么必须拆

> "30 分钟接入"听起来很有吸引力，但它只覆盖"代码能跑"。
> 真正的成本在**用例、Rubric、围栏**——这些是业务判断，不可能 30 分钟完成。
> 对外说"30 分钟接入"，等于把 90% 的工作藏起来了。

### 5.2 现状诚实评估

| 环节 | 能否 30 分钟 |
|---|---|
| 写一个符合钩子的 Adapter | ✅ 可以（照 Sample B 抄） |
| 注册进平台 | ❌ 要改 `factory.py` |
| 跑通第一个 case | ✅ 可以 |
| 有意义的评测 | ❌ 需要用例与 Rubric |

**结论**：技术接入的"写代码"部分 30 分钟可行；"不改平台代码就能接入"目前做不到。

## 6. 分工（RACI）

| 活动 | 业务 PM | 业务开发 | 平台 | 评测 |
|---|---|---|---|---|
| 准入评估 | A | C | R | C |
| 意图与行为声明 | **R/A** | C | C | C |
| Adapter 实现 | C | **R** | A | I |
| 工具与围栏 | A | R | **R** | I |
| 用例与 Rubric | A | C | C | **R** |
| 门禁与报告 | C | I | A | **R** |
| 上线签字 | **A** | I | A | R |

> R = 执行，A = 最终负责，C = 咨询，I = 知会。
> 注意：**"最终负责"始终在业务侧，平台不替业务承担业务风险。**

## 7. 七种反模式

| # | 反模式 | 表现 | 后果 |
|---|---|---|---|
| 1 | 平台里写业务分支 | `if agent_id == "rd_collab"` | 平台越接越重，最后不可维护 |
| 2 | 业务逻辑写进 Adapter | 在 `run()` 里做意图判断和业务规则 | 换平台就废，逻辑不可复用 |
| 3 | 围栏写在 Adapter 里 | 在 Agent 内 `if 金额 > 200: return` | 无法审计，无法统一 |
| 4 | 用例只写 happy path | 24 条全是正常流程 | 越权类零覆盖 |
| 5 | Rubric 权重凑 1 | 权重和为 1，但目标值是拍的 | 分数好看，没有意义 |
| 6 | 接入后不冻结用例 | 每次失败就改期望 | 版本之间不可比 |
| 7 | Mock 工具直连真实系统 | 为了"真实"，接真实 Jira | 有副作用、不可复现 |

> 第 1 条现在**真实存在**（`factory.py` 的 `if/else`）。这是一个必须主动说的已知问题。

## 8. 接入自检清单（DoD）

接入完成的定义，不是"能跑"，是下面 10 条全过：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 风险等级已判定 | L0–L3 有记录 |
| 2 | 意图已映射到行为类 | 每个 intent 有 `behavior` |
| 3 | `metadata()` 完整 | name / version / paradigm / intents |
| 4 | 工具已声明前置条件 | 每个写入类工具有围栏 |
| 5 | 围栏可被测试 | 有对抗用例且能拦截 |
| 6 | 用例覆盖三类 | 正常 / 边界 / 对抗齐全 |
| 7 | Rubric 权重和为 1 | 脚本校验通过 |
| 8 | 硬门槛清单完整 | 越权 / 红线 / trace / 可复现 |
| 9 | 用例已冻结 | 有版本号与冻结时间 |
| 10 | 门禁跑通并出报告 | 有结论与签字 |

## 9. 现状与缺口

| 能力 | 状态 | 说明 |
|---|---|---|
| Agent 契约 | 🟡 | 鸭子类型，无 Protocol |
| 包装器 | 🟡 | 依赖业务私有方法 |
| 工具契约 | ✅ | `ToolRegistry` + `FenceResult` |
| 注册机制 | ❌ | `factory.py` 硬编码 |
| 接入模板 / 脚手架 | ❌ | 无 |
| 接入耗时实测 | ❌ | 30 min 未验证 |
| 自检 CLI | ❌ | 无 `agent validate` |
| HTTP Adapter | ❌ | 仅 Python |

**对外表述**：

> "我的接入契约是能跑通的，两个范式都验证过。但它是隐式的——没有 Protocol，注册要改平台代码。所以'30 分钟接入'现在只能做到写 Adapter 那一步，做不到不改平台就接入。"

## 10. 面试怎么讲（60 秒）

> "接入这件事，我踩过一个坑：一开始我把'接入 30 分钟'当成一个指标，后来发现它是两件事。
>
> **技术接入**——写 Adapter、跑通第一个 case——30 分钟可以。
> **业务就绪**——用例、Rubric、围栏、门禁跑通——大概 5 人日。
>
> 把这两个混成一个数字，就是承诺失真。而且我现在连技术接入都做不到 30 分钟，因为接第三个 Agent 要改 `factory.py` 里的 if/else。那是平台代码，不是配置。
>
> 所以接入 SOP 在我看来不是文档工作，它决定平台能不能规模化——接入成本曲线是平的还是随 Agent 数线性上涨，就看这一步。"

### 10.1 三个可能的追问

| 追问 | 应答 |
|---|---|
| 为什么不做成插件机制？ | "应该做。现在 `factory.py` 是硬编码，改成 entry point 或配置加载就能做到不改平台代码。" |
| 30 分钟接入是真的吗？ | "技术接入可以，业务就绪不行。我把指标拆成三个，分别定目标，不混着说。" |
| 接入最难的是哪一步？ | "意图到行为类的声明。很多团队想跳过，直接写代码，结果规则引擎没有挂载点。" |
