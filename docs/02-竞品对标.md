## 0. 文档导读

### 0.1 这份文档的目的

回答三个问题：

1. 国内外有哪些玩家在做「Agent 运行治理 + 评测底座」，各自做到什么程度；
2. 我们的项目与它们的**真实差异**在哪，哪些能力是必做、哪些可以不做；
3. 哪些设计可以借鉴，哪些话说出去会被面试官追问穿。

### 0.2 读者与使用方式

| 读者 | 怎么用 |
|---|---|
| 项目负责人 | 判断项目的差异化是否成立，锁定 MVP 能力 |
| G3 方案设计 | 借鉴评估模型、Adapter、策略引擎的设计 |
| 面试讲稿 | 用能力矩阵证明"我知道大厂做到哪，也知道自己只做什么" |

### 0.3 本文包含什么

```

§2 竞品全景与能力矩阵（含工具类竞品）

§4 参照：成品 SaaS 的分层可控边界（需求侧证据）
§5 差异化定位
§6 对标结论与项目输入
附录：能力矩阵、信息来源
```

### 0.4 核心结论（30 秒版）

> 先分清角色：**竞品**是大厂平台与 LangSmith/LangFuse 这类工具；**成品 SaaS（Claude Tag/豆包）不是竞品，是需求侧证据**。
> 大厂平台已经把「沙箱 + 接入 + trace + 用例管理 + Rubric + 回归」做成了产品，能力远超个人 POC。
> **但它们的产品化重点也是"评测基础设施"，不是内置万能用例**——Case/Dataset 管理、Rubric 配置、Evaluator 配置、回归对比才是它们的核心功能。这验证了 G1 的判断。
> 我们的空间不在"做得更大"，而在"把执行前围栏与回归门禁接在同一条 trace 上，并用双范式示例证明它成立"。

### 0.5 本文不解决什么

- 不做逐功能拆解（没有账号、无法实测）；
- 不评价商业定价、市场份额；
- 不证明我们能达到大厂能力；
- 不替代技术可行性验证（见 `03-可行性预研.md`）。

## 1. 对标目的与方法

### 1.1 为什么对标

1. **确认方向不是自嗨**：如果大厂都在建同类能力，说明问题真实存在；
2. **确认差异不是幻觉**：如果大厂已经覆盖我们的全部价值，项目就没有必要做；
3. **借用成熟设计**：评估集/评估器/实验的组织方式、运行时分层、策略引擎，都可以借鉴；
4. **准备防守**：面试官很可能问"你和火山/美团有什么区别"。

### 1.2 对标对象选择

先分清角色，避免把"需求侧证据"当成"竞品"：

| 角色 | 对象 | 为什么放在这一类 |
|---|---|---|
| **直接竞品（平台）** | 火山 AgentKit、美团 Agent 评测平台、腾讯 ADP、阿里 Sandbox、华为 AgentArts、PYRA | 同类产品，会抢同一笔预算 |
| **直接竞品（工具）** | LangSmith、LangFuse、Braintrust、Arize Phoenix、W&B Weave | 开发者自选的评测/可观测工具，最常被拿来比较 |
| **相邻竞品** | Guardrails AI、NeMo Guardrails、Lakera | 只做运行时护栏，不做评测与回归 |
| **替代方案** | pytest + 自研 runner、各团队脚本 | 不买产品、自己做的真实替代 |
| **需求侧证据** | Claude Tag、豆包工作伙伴 | 证明企业已在规模化部署业务 Agent，**不构成替代方案** |

> **为什么把成品 SaaS 单列**：它是 Agent 产品，不是管控/评测平台。
> 拿它当竞品是**类别错误**——就像拿"被评测对象"去对标"评测工具"。
> 它的价值是证明"外部管控层"的需求真实存在：企业已经在部署 Agent，但执行链路封闭。

### 1.3 信息来源与可信度分级

| 级别 | 来源 | 使用方式 |
|---|---|---|
| A | 官方产品文档 | 可直接引用能力描述 |
| B | 官方博客 / 发布会 / 开源仓库 | 可引用，标注"官方发布" |
| C | 招聘 JD / 第三方报道 | 可引用，标注"公开报道" |
| D | 推测 / 待核实 | 必须标注，不作为结论 |

> 本文所有能力描述均标注来源级别；具体功能以官方文档为准。

> 结论：**能力维度上我们远不如大厂；差异在"轻量、可运行、开源式、双范式示例"**。

### 2.2.1 工具类竞品矩阵

> 证据级别 B/C，按官方文档与公开资料整理，**待逐项核实**；本节只做定位，不做能力排名。

| 能力 | LangSmith | LangFuse | Guardrails AI | 本项目 |
|---|---|---|---|---|
| trace / 观测 | ✅ | ✅ | ❌ | ✅ |
| 离线评测 / 数据集 | ✅ | ✅ | ❌ | ✅ |
| 执行前拦截 | ❌ | ❌ | 🟡 输出校验为主 | ✅ 工具级围栏 |
| 回归门禁（硬门槛 + 加权判定） | 🟡 有 eval，无门禁判定 | 🟡 | ❌ | ✅ |
| 业务行为分类（B1–B6） | ❌ | ❌ | ❌ | ✅ |
| 双范式示例 | ❌ | ❌ | ❌ | ✅ |

> 结论：三类工具各缺一块——LangSmith 强在观测与评测、不做执行前拦截；Guardrails 强在拦截、不做评测与回归。
> **本项目的定位不是"更强的 LangSmith"，也不是"更全的 Guardrails"，而是把「拦得住」和「评得准」接在同一条 trace 上。**

### 2.3 关键发现：大厂的产品化重点也是"评测基础设施"

从火山和美团的产品结构看，它们的核心不是"内置一套万能测试用例"，而是：

- **Case / Dataset 管理**：让业务方导入自己的用例；
- **Rubric / 标签体系**：让业务方配置判定标准；
- **Evaluator 配置**：选择或组合评估器；
- **人评 / 机评协同**：人工标注与自动判分结合；
- **回归对比**：版本间指标 diff 与 case 变化。

> 这直接验证了 G1 §4.2 的判断：**平台统一的是基础设施，用例内容归业务方。** 我们不是"因为做不了万能用例才这么说"，而是这本来就是平台产品的正确形态。

## 3. 逐个对标

### 3.1 火山引擎 AgentKit（最完整的能力参照）

| 项 | 内容 |
|---|---|
| 定位 | 企业级 Agent 全生命周期平台：开发、部署、运行、观测、评测 |
| 公开能力 | Identity、Runtime、Sandbox、Gateway、Memory、Knowledge、Observability、Evaluation、Guardrails 等模块 |
| 沙箱 | AIO Sandbox：浏览器/Shell/文件/VSCode 一体化；公开报道称支持约 12 万/分钟并发、<150ms 启动、快照/休眠/恢复、兼容 E2B API |
| 评测 | Evaluation Sets + Evaluators + Experiments；离线/在线双轨；过程/结果双维；50+ 官方评估器；公开报道称服务 2,000+ 内部团队、10,000+ Agent、200,000+ 次评测 |
| 目标客户 | 企业开发者、业务团队、平台团队 |
| 可借鉴 | ①「评估集 + 评估器 + 实验」三元组；②过程与结果双维评测；③Skill 评测的版本对比与准入门禁 |
| 与本项目差异 | 我们是单机轻量实现，无多租户、无容器沙箱、无在线评测；不做 Skill 市场 |
| 证据级别 | A/B（官方文档 + 官方发布） |

**对我们的启发**：评测产品的最小抽象不是"一个评测报告"，而是 **集合（Sets）→ 评估器（Evaluators）→ 实验（Experiments）→ 对比（Comparison）**。我们的平台层应该对齐这个结构，即使实现很轻。

### 3.2 美团 Agent 评测平台（目标岗位直接对标）

| 项 | 内容 |
|---|---|
| 定位 | 面向内部多业务线的 Agent 评测平台 |
| 公开能力（来自 JD） | 评测任务管理、Case/数据集管理、Rubric/标签体系、Evaluator 配置、人评/机评协同、结果分析、回归对比 |
| 闭环 | 评测 → 归因 → 策略建议 → 效果验证 |
| 覆盖对象 | 小团 Agent、客服 Agent、内部效能 Agent；另有 LongCat / CatPaw 团队评测 OpenClaw、Claude Code 等 |
| 可借鉴 | ①「评测→归因→策略→验证」闭环；②人评/机评协同；③回归对比作为平台标配 |
| 与本项目差异 | 我们只做单机、单业务样例；不做多业务线、不做平台运营 |
| 证据级别 | C（招聘 JD / 公开报道） |

**对我们的启发**：面试讲平台能力时，直接对齐这五个词——**任务管理、Case/数据集、Rubric、Evaluator、回归对比**——比讲"我做了个 Agent"更贴近岗位语言。

### 3.3 腾讯云 ADP / Agent Runtime

| 项 | 内容 |
|---|---|
| 定位 | 企业级 Agent 开发与运行平台（AgentOps） |
| 公开能力 | Agent Runtime：VM 级隔离、零信任、零凭证、每任务独立 VM、会话快照；ADP 4.0 覆盖构建/部署/连接/治理；RBAC、多租户、Skill/工具生命周期、全链路审计、内容安全 |
| 沙箱 | Cube 沙箱引擎（Rust VMM），会话与实例绑定，公开报道称 <100ms 冷启动、60 万/分钟创建 |
| 可借鉴 | ①「零信任 + 零凭证」的权限模型；②工具网关与身份绑定；③全链路审计 |
| 与本项目差异 | 我们只在应用层做 Mock 围栏，不做 VM 隔离、身份体系、网络隔离 |
| 证据级别 | A/B（官方文档 + 官方技术文章） |

**对我们的启发**：权限围栏的产品语言可以借用"零信任、最小权限、零凭证"，但实现上必须诚实说明是**应用层策略校验**，不是 VM 级隔离。

### 3.4 阿里云 ACS Agent Sandbox / Agent Security Center

| 项 | 内容 |
|---|---|
| 定位 | 生产级 Agent 沙箱 + Agent 安全中心 |
| 公开能力 | ACS Agent Sandbox：MicroVM 级隔离、独立内核、15,000/分钟创建、亚秒冷启动、Checkpoint/Clone、兼容 E2B、K8s Sandbox CR、兼容 AgentScope/LangGraph；Agent Security Center：Prompt 注入、内容安全、DLP、幻觉检测、运行时行为拦截、Skills 扫描、AI 红队 |
| 可借鉴 | ①安全责任共担模型（平台管隔离，业务管代码/凭证/策略）；②运行时安全插件分层 |
| 与本项目差异 | 我们只做离线的越权/幻觉基础检查，不做运行时 eBPF/进程级检测 |
| 证据级别 | A/B |

**对我们的启发**：把"安全插件"设计成**可插拔的通用检查**（幻觉、敏感内容、越权意图），业务方可以配置开关；这与平台"统一基础设施、内容归业务方"的定位一致。

### 3.5 华为云 AgentArts

| 项 | 内容 |
|---|---|
| 定位 | 政企/私有化 Agent 开发平台（智果） |
| 公开能力 | 三平面：开发 / 运行 / 运维；运行面含 Agent Runtime、Code Sandbox、Guard；容器/轻量 VM 隔离；IAM 集成；`agentarts-sdk` 框架无关（LangChain/LangGraph/AutoGen/CrewAI/Google ADK）；HTTP `/invocations`、`/ping`、WS `/ws` |
| 可借鉴 | ①框架无关的 Runtime 接口（`/invocations`、`/ping`）；②开发/运行/运维三平面；③私有化交付 |
| 与本项目差异 | 我们不做 K8s/私有化，只做本地进程；Adapter 接口可以参考其 HTTP 形态 |
| 证据级别 | A（官方文档 + SDK） |

**对我们的启发**：Agent Adapter 不一定要是 Python Protocol，也可以抽象成 **HTTP/WS 契约**（`/invocations`、`/ping`）。这会让"平台能接任意 Agent"的叙事更强，也便于未来接外部 Agent。G3 可以两种都保留：Python 进程内 Adapter + HTTP Adapter。

### 3.6 Microsoft Agent Governance Toolkit（开源治理参照）

| 项 | 内容 |
|---|---|
| 定位 | 开源运行时安全治理工具包（MIT） |
| 公开能力 | Agent OS 策略引擎（YAML/OPA/Cedar）、意图授权（declare→approve→execute→verify）、执行沙箱（4 级权限环）、kill switch、CapabilityGuardMiddleware、执行审计；覆盖 OWASP Agentic AI 10 类风险；公开报道称 p99 <0.1ms |
| 重要限制 | 官方明确说明是**应用层治理**，不是 OS 内核隔离；策略引擎与被治理 Agent 同进程 |
| 可借鉴 | ①策略引擎与执行层分离；②工具 allow/deny；③意图授权与审计 |
| 与本项目差异 | 我们只做规则表 + 工具围栏 + trace，不做策略语言、权限环、kill switch |
| 证据级别 | A/B（开源仓库 + 官方博客） |

**对我们的启发**：我们的"权限围栏"可以借鉴 **CapabilityGuard** 的思路——在工具执行前做 allow/deny 和前置条件校验；但要在文档里明确"应用层策略校验，不是内核隔离"。

### 3.7 PYRA（验收模型的参照）

| 项 | 内容 |
|---|---|
| 定位 | 面向付费任务的 Agent 工作平台 |
| 公开能力 | Job Spec（任务规格）→ Evidence Receipt（交付证据）→ Acceptance Decision（验收决策）→ 结算；H2A 已上线，A2A 在开发 |
| 可借鉴 | **「任务规格 → 证据 → 验收决策」** 这条链，非常适合用来组织我们的 run record 与评测报告 |
| 与本项目差异 | 我们不做支付/结算，只借用验收模型 |
| 证据级别 | C（公开资料，产品文档较少） |

**对我们的启发**：平台的交付物可以设计成三件套——**Run Spec（跑什么）、Evidence（trace + 工具记录）、Acceptance Report（通过/失败/风险）**。这比单纯的"评测报告"更有产品感。

### 3.8 需求侧证据：Claude Tag / 豆包工作伙伴

> **注意：这一节不是竞品分析，是需求侧证据。** 它们是 Agent 产品，不卖评测/管控平台。

| 项 | 内容 |
|---|---|
| 阶段 | Claude Tag：Enterprise/Team 付费 Beta；豆包工作伙伴：企业定向共创 |
| 企业可配置 | 人设、角色目标、边界约束、技能清单、小队协作规则、权限范围、@触发、自动跟进、知识库、审计日志、额度 |
| 企业拿不到 | 结构化中间状态 trace、替换调度器/状态机、可编程人机交接规则、原生批量 golden 回归、第三方 Agent 接入 |
| 与本项目关系 | **证明需求存在**：企业已经在部署业务 Agent；**不构成替代**：它们不做对外评测与管控 |
| 可借鉴 | 业务配置层的信息架构（人设/技能/权限/触发）——这是平台未来"配置层"的参照 |
| 证据级别 | B/C（官方资料 + 公开报道） |

> 面试时不要说"它们是黑盒"，要说"**业务配置层开放、执行链路层封闭**"。

## 4. 参照：成品 SaaS 的分层可控边界

> 这一节对比的是**能力分层**，不是产品竞争。成品 SaaS 开放业务配置层、封闭执行链路，这正是外部管控层的切入点。

| 层 | 成品 SaaS（Agent 产品） | 本项目 |
|---|---|---|
| 业务配置层 | ✅ 人设、角色、技能、权限、@触发、审计、额度 | ✅ 可配 |
| 执行链路层 | ❌ 无结构化 trace | ✅ 全链路 JSON |
| 调度层 | ❌ 不可替换状态机、不可编程交接 | ✅ LangGraph + 自研 Harness |
| 回归层 | ❌ 无原生批量 golden 回归 | ✅ 100% 自动 |
| 接入层 | ❌ 不能接第三方 Agent | ✅ 统一 Adapter |

## 5. 差异化定位

### 5.1 我们做什么

| 做 | 说明 |
|---|---|
| 轻量平台 | 单机 CLI / Streamlit，不做 SaaS 后台 |
| 统一 Adapter | 接入不同范式 Agent |
| 沙箱 + Mock 工具 | 零副作用、可复现 |
| trace | 全链路结构化中间状态 |
| 用例/Rubric 管理 | 平台给骨架，内容归业务方 |
| 回归对比 | 版本 diff、case 变化 |
| 双范式示例 | Sample A 协作型 + Sample B 受限型 |

### 5.2 我们不做什么

- 不做容器/VM 级隔离、多租户、集群调度；
- 不做线上流量、灰度、A/B 实验平台；
- 不做真实 Jira/GitLab/CI 集成；
- 不做 Skill 市场、MCP 全协议；
- 不做跨业务通用用例库。

### 5.3 与主要竞品的差异

| 对象 | 它们的优势 | 我们的差异 |
|---|---|---|
| 火山 AgentKit | 全栈、企业级、评测成熟 | 我们轻量、可运行、可解释；只验证核心逻辑 |
| 美团评测平台 | 多业务线、平台化运营 | 我们单业务样例、个人可复现 |
| LangSmith / LangFuse | trace 与离线评测成熟、生态好 | 我们多了执行前围栏与硬门槛门禁，且把两者接在同一条 trace 上 |
| Guardrails AI / NeMo | 运行时护栏成熟 | 我们同时提供评测、回归与门禁判定 |
| 自建脚本 | 贴合单团队 | 我们统一 Adapter/用例/Rubric/回归口径 |

> 成品 SaaS 不在这张表里——它是需求侧证据，不是竞品。

### 5.4 我们的不可替代性（POC 层面）

1. **可运行**：不是 PPT，能跑通端到端；
2. **可解释**：每个决策、每次围栏、每条 trace 都能讲清；
3. **双范式**：同一平台评两类 Agent，证明通用性；
4. **诚实**：明确简化点与工业补齐项，不吹"对标大厂"。

### 5.5 风险：不要吹"对标大厂"

| 不要说 | 应该说 |
|---|---|
| "我做了个 Agent 评测平台，对标火山/美团" | "我参考了火山/美团的产品结构，做了一个轻量、可运行的参考实现，验证核心产品逻辑" |
| "我有沙箱隔离" | "我做的是应用层 Mock 与策略校验，不是容器/VM 隔离" |
| "我有权限体系" | "我只做工具级围栏，不做企业级 RBAC/身份体系" |
| "我能替代成品 SaaS" | "成品适合直接用；我补的是执行链路的可观测与回归" |

### 6.2 设计借鉴清单

| 借鉴点 | 来源 | 怎么用 |
|---|---|---|
| Evaluation Sets + Evaluators + Experiments | 火山 | 平台层的数据模型：用例集 / 评估器 / 运行实验 / 对比 |
| 过程 + 结果双维评测 | 火山 | trace 评过程，golden 评结果 |
| Case/Dataset + Rubric + Evaluator + 回归 | 美团 | PRD 的能力清单直接对齐 |
| Runtime / Sandbox / Gateway / Guard 分层 | 腾讯/华为 | 平台架构分层参考 |
| CapabilityGuard（工具 allow/deny） | 微软 | 权限围栏的工具级实现 |
| Job Spec → Evidence → Acceptance | PYRA | 运行记录与报告结构 |
| 框架无关的 `/invocations`、`/ping` | 华为 | Adapter 的 HTTP 形态备选 |

### 6.3 面试话术

> "我对标了火山 AgentKit、美团评测平台、腾讯 ADP、阿里 Agent Sandbox、华为 AgentArts 和微软的 Agent Governance Toolkit。它们的共同点是：都在做**运行沙箱、接入、trace、用例管理、Rubric、回归**这套基础设施，而且都不内置万能用例——用例和判定标准由业务方提供。
> 我的项目不是去复刻它们的规模，而是用轻量实现验证这套产品逻辑，并且用两类不同范式的 Agent 证明基础设施的通用性。我明确知道自己在沙箱隔离、多租户、在线评测上是简化的。"
