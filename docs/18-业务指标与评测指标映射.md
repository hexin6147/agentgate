## 0. 文档导读

### 0.1 这份文档的目的

回答一个问题：**平台离线测出来的分数，业务方凭什么信？离线涨了，业务一定涨吗？**

具体要给出：

1. 业务方、一线、平台三方各看哪层指标；
2. 每一层之间能不能换算、换算强度多高；
3. 换算不了的断点在哪、断点怎么处理；
4. 不同阶段（门禁 / 灰度 / 全量）分别看哪层。

### 0.2 读者与使用方式

| 读者 | 怎么用 |
|---|---|
| 业务方 | 知道自己该看哪层，不被"pass_rate 100%"误导 |
| 评测 / 算法 | 知道哪些平台指标是代理指标，不能对外承诺 |
| 面试 | 回答"你怎么把评测结果翻译成业务价值" |

### 0.3 本文包含什么

```
§1 为什么单独写
§2 三层指标：谁看什么
§3 映射表：业务指标 ← 平台指标
§4 五个断点：为什么离线 ≠ 线上
§5 分阶段用哪层指标
§6 指标责任分工
§7 现状与缺口
§8 面试怎么讲
```

### 0.4 核心结论（30 秒版）

> 业务指标和评测指标不是同一层东西，**只有极少数能直接换算**。
> 越权 / 违规事故 ≈ `fence_interception`，可以进硬门槛；
> 任务完成率、一次解决率、人效、投诉率，**只能做代理指标，不能做业务承诺**。
> 中间隔着五个断点：分布、人机、采纳、口径、长链路。
> 所以我的门禁只用质量层做**准入判断**，业务结果层必须等灰度后才有数——这不是能力不足，是评测的边界。

### 0.5 本文不解决什么

- 不做线上埋点接入（当前是离线平台）；
- 不承诺任何"事故率下降 X%"的换算系数；
- 不替代业务方对自己指标的最终解释权；
- 不覆盖多模态、语音、端侧场景的指标。

## 1. 为什么单独写这一篇

`08-评测体系.md` 回答的是**怎么算**：指标定义、公式、数据来源、硬门槛。
本文回答的是**谁关心、能不能换算、换算不了怎么办**。

两者的差别，用一句话说：

> 08 告诉你 `fence_interception = 100%`；
> 本文告诉你，业务方听到这句话会问"那我今年的越权事故会降到几次"，而**这个问题现在答不了**。

JD 里对这件事的要求非常直接：

| JD | 原话 |
|---|---|
| #20 | 跟踪准确率、幻觉率、业务处理效率等指标，验证 AI 是否真正为业务降本增效 |
| #38 | 结合任务成功率、问题解决率、转人工率、准确性、时延、成本及用户满意度定位问题 |
| #32 | 定义各环节的产品指标与效果衡量标准 |
| #24 | 建立"评测 → 归因 → 策略建议 → 效果验证"的数据驱动闭环 |
| #28 | 知道模型延迟、失败率、成本意味着什么，能把"模型在这里不行"翻译成工程约束 |

## 2. 三层指标：谁看什么

### 2.1 业务结果层（业务方 / 管理层看）

| 指标 | 定义 | 典型目标 |
|---|---|---|
| 任务完成率 | 用户发起且被完整解决的任务 / 总任务 | 越高越好 |
| 一次解决率 | 无需二次进线或转人工即解决 / 总任务 | 越高越好 |
| 人效 | 单均处理时长（分钟）或人均日处理量 | 越低 / 越高越好 |
| 单均成本 | 单次任务 token + 调用 + 人工兜底成本 | 在预算内 |
| 投诉率 | 投诉单 / 总单 | 越低越好 |
| 事故数 | 越权、误操作、资金差错 | 0 |

### 2.2 业务过程层（一线 / 主管看）

| 指标 | 定义 | 用途 |
|---|---|---|
| 转人工率 | 转人工任务 / 总任务 | 衡量 Agent 覆盖度 |
| 确认接受率 | 人工点"确认" / 总确认请求 | 衡量 Agent 的建议质量 |
| 平均轮次 | 完成任务所需对话轮次 | 衡量效率 |
| 升级率 | 升级到主管 / 总任务 | 衡量边界是否清晰 |
| 平均步数 | 完成任务所需工具调用 / 节点数 | 衡量链路长度与成本 |

### 2.3 平台质量层（评测 / 算法看）

| 指标 | 定义 | 来源 |
|---|---|---|
| `pass_rate` | 通过 case / 总 case | `evaluation.py` |
| `behavior_accuracy` | 行为类判定正确 / 总 case | `evaluation.py` |
| `route_accuracy` | 路由正确 / 总 case | `evaluation.py` |
| `fence_interception` | 被拦截的越权 / 总越权 | 围栏日志 |
| `false_block_rate` | 误拦 / 总合法调用 | 围栏日志 |
| `handoff_accuracy` | 交接决策正确 / 交接类 case | `judge` + 人工复核 |
| `factuality` | 有来源支撑的陈述 / 总陈述 | `judge` |
| `context_recall` | 命中 relevant / 总 relevant | 标注比对 |
| `source_citation` | 带出处陈述 / 总陈述 | 脚本 + `judge` |
| `trace_completeness` | 必填字段齐全的 step / 总 step | 脚本校验 |

## 3. 映射表：业务指标 ← 平台指标

> **映射强度**：**直接** = 可进硬门槛；**代理** = 可做趋势参考，不能做承诺；**不可测** = 离线平台拿不到。

| # | 业务指标 | 平台代理指标 | 强度 | 主要断点 | 能否进门禁 |
|---|---|---|---|---|---|
| 1 | 越权 / 违规事故数 | `fence_interception` | **直接** | 用例覆盖 | ✅ 能（必须 100%） |
| 2 | 高危动作误放行 | `fence_interception` + `behavior_accuracy` | **直接** | 对抗集质量 | ✅ 能 |
| 3 | 任务完成率 | `pass_rate` | 代理 | 分布断点 | ❌ 只做参考 |
| 4 | 一次解决率 | `pass_rate` + `handoff_accuracy` | 弱代理 | 采纳断点 | ❌ |
| 5 | 转人工率 | `1 - handoff_accuracy`（反向） | 中 | 阈值设定 | 🟡 部分 |
| 6 | 平均处理时长 | 平均步数 × 单步时延 | 弱代理 | 人机断点 | ❌ |
| 7 | 单均成本 | token × 单价 + 调用次数 | **中强** | 缓存 / 并发 | ✅ 能做预算线 |
| 8 | 投诉率 | `factuality` + `fence_interception` | 弱代理 | 长尾 | ❌ |
| 9 | 幻觉率 | `factuality`（judge） | 中 | judge 偏差 | 🟡 参考 |
| 10 | 承诺兑现率 | `factuality` + 外部系统状态 | 弱 | 口径断点 | ❌ |
| 11 | 用户满意度 | 无 | **不可测** | — | ❌ |

**读法**：

- 只有 #1 #2 可以直接写进硬门槛，因为它们是**二值事件**（拦住了 / 没拦住），不依赖分布假设；
- #7 成本可以进预算线，因为它是**加总**，不是概率；
- 其余全部是代理指标。代理指标能回答"有没有变好"，不能回答"业务涨多少"。

## 4. 五个断点：为什么离线 ≠ 线上

### 4.1 分布断点

**现象**：离线 `pass_rate` 100%，线上任务完成率 60%。

**原因**：评测集是 synthetic template（86 / 20 / 24），覆盖的是"设计时想到的表达"。真实群聊里 60% 的说法不在用例里。

**证据**：`04-数据源盘点.md` §0.4 已声明数据为合成；`09b` 显示规则版 held-out 只有 60%——**换一批没见过的表达，分数就掉 40pp**。

**处理**：把 held-out 当"分布探测"，不当"能力证明"；上线后必须用真实流量做回流集。

### 4.2 人机断点

**现象**：离线 `pass_rate` 100%，因为所有 B4 写入都被确认环节拦住了；线上转人工率 40%，业务觉得"不如人工"。

**原因**：确认环节把错误挡在了评测之外——**评测测的是"Agent 自己做得对不对"，线上看的是"人机合起来做得快不快"**。

**处理**：把"确认接受率"作为独立指标；确认率过高说明 Agent 建议质量差，确认率过低说明确认形同虚设。

### 4.3 采纳断点

**现象**：输出正确，但用户不看、不信、绕过。

**原因**：正确 ≠ 可读 ≠ 可执行。研发看到 10 条风险里 3 条是废话，下次就不看了。

**处理**：过程层加"采纳率"（输出被引用 / 被转发的比例），离线测不了，只能灰度测。

### 4.4 口径断点

**现象**：评测说 `pass_rate 96%`，业务说"我们单均差错率 8%"。

**原因**：分母不是一个东西。

| 维度 | 评测口径 | 业务口径 |
|---|---|---|
| 单位 | 1 个 case | 1 个工单 / 1 次上线 / 1 天 |
| 成功 | 行为 + 内容符合 golden | 用户没投诉、流程走完 |
| 失败 | case 判负 | 事故 / 返工 / 投诉 |

**处理**：对外沟通时必须写清"这是 case 级通过率，不是单均差错率"；换算需要线上联合分析，不能拍系数。

### 4.5 长链路断点

**现象**：单步准确率 90%，6 步任务的成功率是多少？

**常见错误算法**：

- `0.9^6 = 53%` —— 假设每步独立，但真实里错误会被 verify 拦住，也会传导放大，两个方向都不独立；
- `平均 90%` —— 把"部分完成"和"完全失败"算成一样，掩盖了长任务的真实体验。

**正确处理**：长任务要三层指标。

| 层 | 指标 | 回答什么问题 |
|---|---|---|
| 步级 | 单步成功率、单步错误率 | 哪一步最容易坏 |
| 任务级 | 任务完成率、部分完成率 | 用户能不能拿到结果 |
| 恢复级 | 失败后恢复率、平均恢复步数 | 坏了能不能救回来 |

> **现状（诚实）**：当前 86 / 20 / 24 条用例全是**单轮任务**，`plan → act → verify → respond` 只产生一次工具调用，没有多步串联。所以上表三层里，只有"步级"有部分数据，任务级和恢复级是空的。长链路评测是明确的下一步，不是已完成项。

**处理**：先补多步用例（同一任务 3–6 步、中途注入工具失败），再谈任务级指标。

## 5. 分阶段用哪层指标

| 阶段 | 看哪层 | 判据 | 谁看 |
|---|---|---|---|
| **离线门禁** | 质量层 + 硬门槛 | 硬门槛 100%；`pass_rate` 不低于基线 | 评测 / 平台 |
| **灰度 5%** | 过程层 | 转人工率、确认接受率、平均轮次在阈值内 | 业务主管 |
| **全量** | 结果层 | 完成率、人效、投诉率 | 业务方 / 管理层 |
| **回滚** | 任一硬指标恶化 | 越权 > 0，或投诉率环比 +X%，或转人工率突破上限 | 值班 |

**关键原则**：

> **门禁只用能直接换算的指标（越权、成本），不用代理指标（完成率、满意度）。**
> 代理指标可以写进报告做趋势，但不能作为"能不能上线"的唯一依据——否则就是用离线数据替业务做承诺。

## 6. 指标责任分工

| 指标层 | 定义方 | 采集方 | 目标设定方 | 异常处理方 |
|---|---|---|---|---|
| 业务结果 | 业务方 | 业务系统 | 业务方 + 管理层 | 业务方 |
| 业务过程 | 业务方 + 平台 | 线上日志 / 平台 trace | 业务主管 | 业务 + 平台 |
| 平台质量 | 平台 | 平台评测脚本 | 平台 + 评测 | 平台 / 算法 |

**一句话**：平台不替业务定目标，只保证口径一致、数据可复现。

## 7. 现状与缺口

| 层 | 状态 | 说明 |
|---|---|---|
| 平台质量层 | ✅ 已实现 | 10 个指标有定义、有脚本、有报告 |
| 业务过程层 | 🟡 部分 | `handoff_accuracy` 可算；转人工率、确认接受率、平均轮次未采集 |
| 业务结果层 | ❌ 未接入 | 离线平台拿不到线上数据 |
| 映射关系 | ✅ 本文首次给出 | 可用 / 不可用、断点、责任人 |
| 长链路指标 | ❌ 空 | 无多步用例、无步级/任务级/恢复级指标 |

**对外表述**：

> "我的评测覆盖质量层，过程层部分覆盖，结果层明确不覆盖。所以我只说'这个 Agent 能不能过门禁'，不说'它能提升多少业务指标'——后者需要灰度数据。"

## 8. 面试怎么讲（60 秒）

> "业务指标和评测指标不是一层东西。
>
> 比如越权事故，它可以和围栏拦截率直接对应，所以我把它写进硬门槛，要求 100%。
> 但任务完成率不行。我离线测的是 86 条 case 的通过率，业务看的是单均完成率。中间隔着五个断点：评测集是合成的、确认环节替 Agent 挡了错、用户可能根本不看输出、分母不是一个东西、长任务的成功率也不是单步相乘。
>
> 所以我的门禁只用能直接换算的指标，代理指标只写进报告做趋势。
>
> 这不是能力不足，是评测的边界。谁要是拿离线 pass_rate 给你承诺业务提升，那是没想清楚。"

### 8.1 三个可能的追问

| 追问 | 应答 |
|---|---|
| 那你的评测有什么用？ | "它保证已知的失败模式不再复发，这是回归的价值；它不保证未知的长尾，那是线上监控的事。" |
| 怎么把代理指标变准？ | "接线上埋点，用真实流量做回流集，再和业务指标做相关性分析。现在没做，因为平台是离线的。" |
| 长链路怎么评？ | "要三层：步级、任务级、恢复级。我现在只有单轮用例，所以这一层是空的，下一步补多步用例和故障注入。" |
